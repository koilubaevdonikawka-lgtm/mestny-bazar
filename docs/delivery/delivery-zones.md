**Модуль:** Delivery Management & Pricing — География
**Статус в коде:** частично существует — `delivery_zones` (плоский список), `AddressDTO.city`/`AddressDTO.district` (свободный текст)
**Роли с доступом:** Admin (полный доступ к CRUD), Покупатель (только чтение активных зон)

> Этот документ описывает исключительно **географическую модель**: где именно платформа доставляет и как адрес сопоставляется с зоной. Цена и условия доставки внутри зоны — `delivery-pricing.md`.

## Назначение

Дать платформе понятие географического покрытия, достаточное для: (а) нескольких городов, (б) нескольких точек отгрузки (магазинов/складов) внутри города, (в) деления города на зоны и районы, (г) сопоставления произвольного адреса покупателя с конкретной зоной без ручного вмешательства администратора на каждый новый адрес.

## Уже существующая модель (не переизобретается)

- `public.delivery_zones`: `id, name, price, free_from, sort_order, is_active` — плоский список зон без города/магазина. `SupabaseDeliveryZoneRepository` (`server/adapters/supabase/delivery-zone.repository.ts`) — единственный адаптер, уже за портом `IDeliveryZoneRepository`.
- `AddressDTO` (`shared/contracts/delivery.ts`) уже содержит `city: string | null`, `district: string | null`, `zoneId: string | null` — **свободный текст** для города/района (не FK), `zoneId` — выбирается покупателем/резолвится сегодня без формального правила сопоставления район↔зона.
- Покупатель уже выбирает зону при указании адреса — сам факт связи «адрес → зона» существует, механизм автоматического определения — нет.

## Спроектированная модель

### City (Город)

Верхнеуровневая единица географического покрытия. Нужна, чтобы зоны/магазины/тарифы могли осмысленно группироваться при выходе платформы за пределы одного города.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID | |
| `name` | text | «Бишкек», «Ош» |
| `slug` | text | Для URL/фильтров |
| `timezone` | text | Для будущих сезонных/временных коэффициентов (`delivery-future-roadmap.md`) |
| `isActive` | boolean | Город обслуживается платформой |

### Store (Магазин / точка отгрузки)

Физическая точка, откуда стартует доставка. Сегодня платформа неявно однородна (один виртуальный склад — `products.stock`, без понятия местоположения). Store — точка расширения для мультимагазинности, не привязана к существующей модели остатков (`warehouse.md` явно фиксирует: остаток сегодня — плоское число на товар, без понятия склада-местоположения; связка Store ↔ конкретный остаток — отдельное, не входящее в этот этап решение, зависящее от эволюции `warehouse.md`).

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID | |
| `cityId` | UUID → City | |
| `name` | text | «Склад на Токтогула» |
| `address` | text | Физический адрес |
| `coordinates` | `{ lat, lng }` (nullable) | Нужны для расчёта по расстоянию (`delivery-pricing.md`) — nullable, пока провайдер геокодирования не выбран |
| `isActive` | boolean | |

Сегодня, при единственном магазине, `storeId` на Зоне — **nullable**: `null` означает «зона обслуживается платформой в целом», без привязки к конкретной точке — это сохраняет полную обратную совместимость с текущей однородной моделью без обязательной миграции данных при переходе на мультимагазинность.

### Delivery Zone (Зона доставки)

Географическая область покрытия. **Не хранит цену** — цена принадлежит Тарифу (`delivery-pricing.md`), одна Зона может иметь несколько применимых Тарифов одновременно (см. Rule Engine, `delivery-rule-engine.md`).

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID | Совпадает с сегодняшним `delivery_zones.id` — миграция аддитивна |
| `cityId` | UUID → City | |
| `storeId` | UUID → Store, nullable | `null` = зона не привязана к конкретному магазину (сегодняшнее поведение) |
| `name` | text | Как сегодня |
| `sortOrder` | int | Как сегодня |
| `isActive` | boolean | Как сегодня |

**Важное архитектурное решение:** `price`/`free_from` **удаляются** с Зоны в пользу Тарифа. Это не техническая косметика — это ровно то изменение, которое делает возможным «несколько тарифных сеток» (сезонные/корпоративные тарифы на одну и ту же зону) без дублирования зоны. Миграционный путь (без выполнения в этом этапе) — `delivery-future-roadmap.md`/`IMPLEMENTATION_ORDER.md`, Этап 2: существующие `price`/`free_from` каждой зоны становятся одной записью «стандартный тариф» на эту зону, данные не теряются.

### District (Район)

Более мелкое деление внутри Зоны — то, что сегодня существует только как свободный текст `AddressDTO.district`.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID | |
| `zoneId` | UUID → Delivery Zone | Район принадлежит ровно одной зоне |
| `name` | text | «Джал», «Восток-5» |
| `isActive` | boolean | |

**Зачем район как отдельная сущность, если он принадлежит зоне (у которой уже есть цена через тариф)?** Два независимых применения: (1) UI-подсказка при вводе адреса (список районов вместо свободного текста — устраняет опечатки и рассинхронизацию, уже отмеченную как риск в `AddressDTO.district`); (2) точка расширения на случай, если в будущем один и тот же экономический тариф должен применяться к нескольким зонам, но UI должен показывать более мелкий, знакомый покупателю район — район остаётся стабильным идентификатором адреса даже при переразметке зон администратором.

## Сопоставление адреса с зоной

Сегодня: покупатель сам выбирает `zoneId` из списка при вводе адреса (`CreateAddressRequest.zoneId?`) — ручной, не автоматический процесс.

Спроектировано (без реализации в этом этапе): `DeliveryZoneService.resolveZoneForAddress(address)` — доменный метод, инкапсулирующий стратегию сопоставления (сначала: точное совпадение `District`; затем: попадание координат в границу зоны, если координаты и границы заданы — оба поля nullable сегодня; затем: явный выбор пользователя как раньше, не заменяется, а остаётся резервным путём). Это чисто доменная логика, не Rule Engine (не decision «можно/нельзя» — это разрешение сущности, ближе к `CatalogService.getProductBySlug`, чем к `PaymentPolicyService`).

## Поддержка нескольких городов и нескольких магазинов

- Несколько городов: `City` — независимая сущность, `Store`/`Delivery Zone` ссылаются на конкретный `cityId`. Переключение города на витрине — вопрос UI (вне этого этапа), не архитектуры: `listDeliveryZonesFn` уже спроектирован с параметром `cityId` (см. `delivery-api.md`).
- Несколько магазинов: `Store.cityId` допускает много магазинов на город; `DeliveryZone.storeId` — какой магазин обслуживает зону. Явно поддержана ситуация «одна зона — один магазин» (сегодняшняя, через `null`) и «несколько зон на один магазин» (через одинаковый `storeId` у разных зон) без дополнительной сущности связи many-to-many — она не требуется, поскольку зона по определению обслуживается ровно одним магазином (двух магазинов, доставляющих в одну зону, платформа сегодня не проектирует — не запрошено).

## Инварианты

- ❌ Зона без города (`cityId` обязателен, `storeId` — нет).
- ❌ Район, ссылающийся на зону из другого города, чем сам район подразумевает (проверяется на уровне доменного сервиса при создании района, не только FK).
- ❌ Цена, хранящаяся на Зоне напрямую (принадлежит только Тарифу — см. `delivery-pricing.md`).
