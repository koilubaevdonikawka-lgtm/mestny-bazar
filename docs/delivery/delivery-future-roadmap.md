## Уже предусмотренные точки расширения

Ничего из перечисленного ниже не требует изменения уже спроектированной в этом этапе модели данных или Rule Engine — каждый пункт **надстраивается**, что и является целью этого документа: доказать, что фундамент (Этап 1) действительно достаточен для Этапа 3, не потребует пересмотра.

| Возможность | Как уже предусмотрена |
|---|---|
| **Динамическое ценообразование** | `DeliveryCoefficient.type: LOAD` + `condition: jsonb` — точка расширения уже существует в модели данных (`delivery-pricing.md`); алгоритм расчёта нагрузки (сколько активных заказов на курьера/зону) — не спроектирован здесь, это Domain-логика Этапа 3, читающая уже существующие данные `CourierOrderService`/`courier_status`, не новую сущность |
| **Корпоративные тарифы** | `DeliveryTariff.tariffType: CORPORATE` + `DeliveryTariffPolicyContext.customerSegment` + `CorporateTariffRule` — полностью специфицированы в `delivery-rule-engine.md`, не требуют новой модели |
| **Праздничные тарифы** | `DeliveryTariff.tariffType: HOLIDAY` + `validFrom`/`validTo` + `HolidayTariffRule` — полностью специфицированы |
| **Погодные коэффициенты** | `DeliveryCoefficient.type: WEATHER` — модель данных готова; сам источник погодных данных — внешний провайдер, см. «Кандидаты на ADR» ниже |
| **Коэффициенты нагрузки** | `DeliveryCoefficient.type: LOAD` — модель данных готова, источник — внутренний (уже существующие данные о заказах/курьерах), внешний провайдер не требуется |
| **Стоимость по расстоянию** | `DeliveryTariff.pricingModel: BY_DISTANCE` + `pricePerKm` — формула специфицирована (`delivery-pricing.md`); `distanceKm` — требует провайдера геокодирования, см. ниже |
| **ETA** | `DeliveryFeeQuote.eta: { minMinutes, maxMinutes }` — поле уже в контракте (`delivery-pricing.md`); алгоритм расчёта (фиксированный по зоне на Этапе 2, зависящий от расстояния/нагрузки на Этапе 3) — не заморожен, оставлен открытым намеренно |
| **Несколько городов / несколько магазинов** | `City`/`Store` — специфицированы полностью в `delivery-zones.md`, включая nullable-путь для сегодняшней однородной модели |
| **Несколько тарифных сеток** | Уже основа всей модели `delivery-pricing.md` — не будущее, а часть фундамента этого этапа |

## Кандидаты на ADR

Ни одно из решений ниже **не принимается** в этом документе — фиксируется только сам факт, что решение обязательно потребуется до соответствующей части реализации (по критериям Принципа 14: новый внешний провайдер, изменение потока данных).

| # | Кандидат | Почему требует ADR | Когда нужен |
|---|---|---|---|
| 1 | **Провайдер геокодирования и маршрутизации** (например, Яндекс.Карты, 2GIS API, Google Maps Platform) | Принцип 14: «Новый внешний провайдер — Да». Затрагивает `Store.coordinates`, `pricingModel: BY_DISTANCE`, `distanceKm` в контексте Rule Engine — новый адаптер за новым портом (`IGeocodingProvider`), секреты (`PL-07`), стоимость запросов у провайдера | До активации `pricingModel: BY_DISTANCE` (Этап 3) — не раньше |
| 2 | **Источник данных о погоде** для `DeliveryCoefficient.type: WEATHER` | Тот же критерий — новый внешний провайдер | До активации погодных коэффициентов (Этап 3) |
| 3 | **`DeliveryCoefficientRegistry` как новый класс механизма** (не Rule Engine в смысле Принципа 12 — см. обоснование в `delivery-pricing.md`, «Почему коэффициенты — не тот же Rule Engine») | Новый, ранее не существовавший в проекте паттерн композиции правил — по духу Принципа 14 (значимое архитектурное решение, влияющее на будущие модули, которые тоже могут захотеть «накопление», а не «выбор одного») заслуживает того же уровня фиксации, что и Rule Engine Standard в своё время | До реализации Этапа 3 (сами тарифы/зоны Этапа 2 коэффициентов не требуют) |
| 4 | **Формула композиции нескольких коэффициентов** (умножение vs. сложение, округление, нижняя граница) | Не архитектурное решение в строгом смысле (не меняет границы слоёв), но зафиксировано здесь как открытый вопрос, чтобы не потерялось — продуктовое/бизнес-решение, ADR не обязателен, но фиксация обязательна | До реализации `DeliveryCalculator` с более чем одним коэффициентом (Этап 3) |
| 5 | **Семантика `delivery.tariff.activated`/`delivery.tariff.expired`** (частота публикации — см. `delivery-events.md`, «Открытый вопрос») | Не требует ADR (не меняет границы слоёв/поток данных между модулями, только частоту публикации внутри уже спроектированной событийной модели) — но требует явного решения до реализации, фиксируется здесь по той же причине, что и №4 | До реализации Этапа 3 (может быть не реализовано вовсе в Этапе 2 без потери функциональности) |

## Явно НЕ являющееся частью Этапа 1 или предметом этого проектирования

- Курьерское PWA само по себе — отдельная подсистема (`docs/admin-platform/couriers.md`), Delivery Management & Pricing проектируется как её будущий поставщик данных (зона, ETA), не как её часть.
- Расчёт компенсации/себестоимости доставки для отчётности Финансов (`finance.md`) — не входит в объём; при появлении такой задачи она читает уже спроектированный `DeliveryFeeQuote`/`order.deliveryFee`, не требует новой модели здесь.
- Мультивалютность тарифов — платформа сегодня работает в одной валюте (`currency` на уровне заказа/товара уже существует как поле, не бизнес-функция) — не проектируется отдельно, наследует существующее поведение без изменений.
