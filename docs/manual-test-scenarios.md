# Ручное тестирование потоков, требующих Supabase

Подготовлено на момент отсутствия рабочего `SUPABASE_SERVICE_ROLE_KEY` в среде разработки. Все сценарии ниже требуют реального ключа и применённых миграций (`supabase/migrations/`) на реальном проекте Supabase — ни один не был и не мог быть выполнен в этой сессии. Каждый сценарий указывает, какой именно фикс этой сессии он проверяет, чтобы не выполнять их вслепую.

## Перед началом

- [ ] Все 19 миграций в `supabase/migrations/` применены (`supabase migration list` — сверить с локальным списком файлов)
- [ ] `SUPABASE_SERVICE_ROLE_KEY` и `SUPABASE_URL` заданы в окружении
- [ ] Есть тестовые пользователи с ролями `customer`, `admin`, `warehouse`, `courier`, `seller` (см. `user_roles`)
- [ ] `FEATURE_CATALOG_SOURCE=platform` — иначе каталог обслуживается Shopify-адаптером, не Supabase

---

## 1. Чекаут и создание заказа

**Проверяет:** атомарность создания заказа (`create_order_with_items`), атомарное резервирование стока (`reserve_product_stock`), границу отката резерва после создания заказа, идемпотентность.

1. Добавить товар в корзину, оформить заказ (CASH, гость без аккаунта)
   - **Ожидается:** заказ создан, сток товара уменьшен ровно на количество в заказе
2. Повторить тот же запрос создания заказа с тем же `idempotencyKey` (например, дважды быстро нажать «Оформить»)
   - **Ожидается:** создаётся ровно один заказ, не два; сток уменьшается один раз
3. Оформить заказ на товар с остатком меньше запрошенного количества
   - **Ожидается:** `InsufficientStockError`, заказ не создан, сток не изменён
4. Оформить заказ с 100 позициями в корзине (граница, установленная валидацией)
   - **Ожидается:** заказ создаётся успешно (это максимум, разрешённый схемой)
5. Оформить заказ со 101 позицией
   - **Ожидается:** запрос отклонён на этапе валидации (400), заказ не создан

## 2. Управление статусами заказа (admin/warehouse/courier)

**Проверяет:** optimistic concurrency (`updateStatus` с `fromStatus`/`toStatus`), защиту от гонки при параллельном изменении статуса.

1. Админ подтверждает заказ (`PAID → CONFIRMED`)
   - **Ожидается:** статус меняется, заказ появляется в очереди склада
2. Одновременно из двух вкладок попытаться перевести один и тот же заказ в разные статусы (например, админ отменяет, склад одновременно начинает сборку)
   - **Ожидается:** ровно одно из двух действий проходит; второе получает `OrderConcurrentModificationError`, а не тихо перезаписывает результат первого
3. Полный цикл: `CONFIRMED → ASSEMBLING (склад) → READY_FOR_DELIVERY (склад) → OUT_FOR_DELIVERY (курьер) → ARRIVED (курьер) → DELIVERED (курьер)`
   - **Ожидается:** каждый переход виден в списках соответствующей роли, недопустимые переходы (например, склад пытается доставить) отклоняются

## 3. Адреса и адрес по умолчанию

**Проверяет:** атомарность `set_default_address`, невозможность получить два адреса с `is_default=true`.

1. Создать 2-3 адреса, один пометить как «по умолчанию»
   - **Ожидается:** ровно один адрес с флагом «по умолчанию»
2. Быстро (двойной клик / два запроса подряд) переключить «по умолчанию» между двумя разными адресами
   - **Ожидается:** в итоге ровно один адрес остаётся «по умолчанию» — тот, что установлен последним; ни в коем случае не два одновременно
3. Оформить гостевой чекаут без сохранённого адреса, указав адрес текстом
   - **Ожидается:** заказ создаётся, `addressId` не привязан ни к одному сохранённому адресу

## 4. Товары продавца

**Проверяет:** rule engine публикации (`DRAFT → PUBLISHED → HIDDEN`), валидацию (Zod + доменный слой).

1. Продавец создаёт товар (черновик) → публикует → скрывает
   - **Ожидается:** товар появляется в буферном каталоге только в статусе `PUBLISHED`
2. Продавец пытается скрыть ещё не опубликованный товар (`DRAFT → HIDDEN` напрямую)
   - **Ожидается:** переход отклонён политикой публикации
3. Создать товар с названием длиннее 200 символов / ценой выше 10 000 000
   - **Ожидается:** отклонено на этапе Zod-валидации до обращения к БД

## 5. Роли и авторизация

**Проверяет:** `resolveRolesForUser()`, что роль берётся из БД, а не из тела запроса.

1. Пользователь без роли `admin` обращается к `/admin/orders`
   - **Ожидается:** `ForbiddenError`, доступ запрещён
2. Пользователь с ролью `seller` пытается вызвать admin-эндпоинт напрямую (минуя UI)
   - **Ожидается:** отклонено на уровне `requireAdminFromRequest()`, роль проверяется по `user_roles`, не по данным из запроса

## 6. Аудит-лог

**Проверяет:** переход с in-memory на персистентный `SupabaseAuditLog`, устойчивость к сбою одного из подписчиков события.

1. Оформить заказ → проверить появление записи в таблице `audit_log`
   - **Ожидается:** запись создана с корректным `entity_id` (id заказа) и `payload`
2. (Если возможно смоделировать сбой одного из подписчиков `order.created`) убедиться, что сбой подписчика уведомлений не мешает записи аудит-лога и не откатывает сам заказ
   - **Ожидается:** заказ создан, аудит записан, независимо от отказа других подписчиков (`Promise.allSettled`-изоляция)

## 7. Таймауты транспорта

**Проверяет:** таймаут на `supabaseAdmin`-транспорте (8с).

Сложно воспроизвести вручную без контроля над сетью до Supabase. Если возможно — временно заблокировать доступ к `SUPABASE_URL` на firewall/hosts-файле и убедиться, что запрос завершается ошибкой около 8 секунд, а не висит бессрочно.

## Список потоков, которые невозможно проверить без рабочего SUPABASE_SERVICE_ROLE_KEY

Все перечисленные ниже используют `supabaseAdmin` безусловно (см. `server/di/container.ts`) — без реального ключа они либо не работают вовсе, либо не проверены дальше уровня статического анализа/unit-тестов с фейковыми репозиториями:

1. **Чекаут и создание заказа** — `SupabaseOrderRepository`, `SupabaseProductRepository` (резерв стока), `SupabaseAddressRepository`, `SupabaseDeliveryZoneRepository`
2. **Управление заказами** (admin/warehouse/courier — списки, смена статусов) — `SupabaseOrderRepository`
3. **Адреса** (список/создание/обновление/удаление/адрес по умолчанию) — `SupabaseAddressRepository`
4. **Товары продавца** (список/создание/обновление/публикация) — `SupabaseSellerProductRepository`
5. **Аудит-лог** — `SupabaseAuditLog`
6. **Разрешение ролей и авторизация** (`resolveRolesForUser`) — используется всеми admin/warehouse/courier/seller-guard'ами
7. **Каталог платформы** — `SupabaseProductRepository`, только если `FEATURE_CATALOG_SOURCE=platform` (в текущей dev-среде `shopify`, поэтому каталог **проверяем** без ключа)
8. **Реальное применение и порядок миграций** на живой БД — включая CHECK-constraint и UNIQUE-index миграции, которые теоретически могли не примениться при наличии унаследованных данных, нарушающих ограничения (см. `20260725060000_non_negative_constraints.sql`, `20260725080000_atomic_default_address.sql`)

Что удалось проверить без ключа в этой сессии: статический анализ (TypeScript, ESLint, `npm audit`), полный набор unit/integration-тестов на фейковых репозиториях (183/183), production build, синтаксическая корректность всех 19 файлов миграций, конфигурация (`tsconfig.json`, `server/config/env.ts`, `.env.example`), Shopify-обслуживаемая часть витрины (каталог, поиск, пагинация) через реальный dev-сервер.
