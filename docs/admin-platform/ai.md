**Модуль:** ИИ-инструменты
**Статус в коде:** частично существует — `marketplace-ai` (`server/domain/marketplace-ai/`): `AIOrchestrator`, `AIWorkerRegistry`, `AIMediaWorker`, `AICatalogWorker`, `MediaQualityAnalyzerService`, `CatalogQualityAnalyzerService`, `CATEGORY_DICTIONARY` (rule-based, без LLM)
**Роли с доступом:** Admin (полный доступ), Seller (просмотр оценок по своим товарам, если подключено)

> Этот документ описывает исключительно существующий и будущий ИИ-функционал платформы. Правила автоподбора курьера, автопополнения склада и т.п. — это Rule Engine, не ИИ (важное разграничение, см. «Что не является ИИ» ниже) — они описаны в соответствующих документах.

## Назначение

Дать администратору доступ к автоматической оценке качества карточек товара (изображения, описания, категоризация) и — в будущем — другим ИИ-инструментам, помогающим модерировать и улучшать каталог без ручной проверки каждой карточки.

## Уже существующая архитектура (важная находка аудита)

Подсистема `marketplace-ai` **реально работает уже сегодня**, но не как отдельный модуль администратора, а как встроенный, автоматически срабатывающий побочный эффект оформления заказа: `checkout.service.ts` публикует событие `order.created`, на которое подписаны `AIMediaWorker`/`AICatalogWorker` (через `subscribeAIWorkers`, `server/di/container.ts`), которые синхронно (в рамках того же запроса) анализируют товары/фото из состава заказа и публикуют результат как события `catalog.analysis.completed`/`photo.analysis.completed`/`ai.job.completed`.

**Критический, уже задокументированный пробел** (зафиксирован в `docs/architecture/ARCHITECTURE_PRINCIPLES.md`): у этих событий **нет ни одного подписчика за пределами самого ИИ-модуля** — результат анализа нигде не сохраняется и нигде не отображается. Это означает, что сегодня ИИ-анализ **добавляет задержку к каждому оформлению заказа, не принося никакой пользы** — классический «расходует ресурсы, результат в никуда».

**Для этого модуля Административной платформы это означает первоочередную задачу**, отличную от «добавить новый ИИ-функционал»: либо (а) подключить существующий результат к чему-то полезному — например, витрине модерации в `catalog.md` («карточки с низкой оценкой качества»), либо (б) осознанно отключить автозапуск на каждый заказ (это не соответствует смыслу — анализ качества карточки логичнее запускать при создании/публикации товара, не при его продаже) и запускать анализ по событию `product.published` (см. пробел, зафиксированный в `catalog.md` — публикация товара тоже сегодня не публикует событие в общую шину).

## Отдельный, не связанный с витриной словарь категорий

`CATEGORY_DICTIONARY` (`server/domain/marketplace-ai/catalog/category-dictionary.ts`) — rule-based (без LLM) словарь для сопоставления текста товара с категорией по ключевым словам, используется `CatalogQualityAnalyzerService`. Аудит каталога категорий (проведённый до написания этой документации) обнаружил, что этот словарь определяет **свой собственный, не синхронизированный с `public.categories` набор из 9 категорий** (включая «Яйца», «Острокислое», которых нет в реальном списке категорий витрины, и не включая «Хлеб и выпечка», которая в нём есть). Это не ошибка ИИ-модуля — он не обязан использовать тот же список, что и витрина, поскольку решает другую задачу (сопоставление свободного текста, не отображение категорий), — но при проектировании раздела ИИ в Административной платформе важно не смешивать эти два списка визуально, чтобы не повторить путаницу, из-за которой ранее файл изображения одной категории ошибочно ассоциировался с другой.

## Что не является ИИ (важное разграничение)

Автоматический подбор курьера (`couriers.md`), автопополнение склада (`warehouse.md`), применимость купона (`marketing.md`) — это **Rule Engine** (детерминированные, явно написанные правила `order → applies → evaluate`), а не ИИ/ML. Не следует путать эти два механизма при проектировании: Rule Engine — для правил, которые бизнес должен понимать и контролировать явно; ИИ — для задач, где явное правило неэффективно (анализ изображения, свободный текст).

## Структура раздела

```
ИИ-инструменты
├── Анализ качества карточек (результаты AICatalogWorker/AIMediaWorker — при подключении к хранению)
├── Статус воркеров (включены/выключены, последний запуск, ошибки)
└── Настройка триггеров (когда запускать анализ — см. «Первоочередная задача» выше)
```

## Права доступа

| Действие | Admin | Seller |
|---|---|---|
| Просмотр результатов анализа (вся платформа) | ✅ | — |
| Просмотр результатов по своим товарам | 👁 | ✅ |
| Включение/выключение ИИ-воркеров | ✅ | — |
| Настройка триггеров запуска | ✅ | — |

## Будущие расширения

- Персистентное хранение результатов анализа (сегодня результат существует только как событие в момент публикации, нигде не сохраняется).
- Расширение `AIWorkerRegistry` новыми воркерами (например, генерация описания товара) — архитектурно уже поддержано (реестр воркеров, единый `AIOrchestrator`), не требует нового механизма, только нового `Worker`-класса.
