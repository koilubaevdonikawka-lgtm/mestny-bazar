> Этот документ описывает исключительно поставщиков и связанные с ними поставки/закупочные цены. Остатки товара на складе — `warehouse.md`; сами товары как каталожные единицы — `catalog.md`.

## Назначение

Дать администратору и складу инструмент для ведения списка поставщиков, оформления заявок на пополнение (вручную или по сигналу от Склада, см. `warehouse.md` — событие `stock.low`) и отслеживания закупочных цен отдельно от розничных.

## Модель данных (предлагается, не реализовано)

Полностью новый домен — не расширение существующей таблицы. Минимальный набор сущностей:

```
Поставщик (id, name, contactPhone, contactPerson, notes, isActive)
Поставка/Заявка (id, supplierId, status: DRAFT|SENT|CONFIRMED|RECEIVED|CANCELLED, createdAt, expectedAt)
Позиция поставки (id, supplyId, productId, quantity, purchasePrice)
```

Закупочная цена (`purchasePrice`) хранится отдельно от `products.price` (розничная цена, уже существует) — это два независимых числа, их разница не вычисляется автоматически этим модулем (маржинальность — задача `finance.md`, который **потребляет** оба значения, не владея ни одним).

## Структура раздела

```
Поставщики
├── Список поставщиков (активность, контакты)
├── Карточка поставщика (история поставок, товары, закупочные цены)

│   ├── Создание вручную
│   └── Созданные автоматически (по событию stock.low из warehouse.md) — помечены отдельно
└── Приёмка поставки (подтверждение фактически полученного количества → увеличение stock)
```

## Бизнес-логика

Жизненный цикл заявки на поставку (`DRAFT → SENT → CONFIRMED → RECEIVED`/`CANCELLED`) — кандидат на тот же Rule Engine стандарт, что уже используется для заказов и публикации товара (Принцип 12), если переходы должны быть ролезависимыми (например, «подтвердить получение может только Warehouse»). На первом этапе, при небольшом количестве правил, допустимо начать с простого явного стейт-машин без полноценного rule chain — но интерфейс (`ISupplyLifecyclePolicy` с `assertCanTransition`) должен быть спроектирован так, чтобы миграция на полноценный Rule Engine не требовала переписывания вызывающего кода (тот же паттерн, что уже применён для `IOrderLifecyclePolicy`).

**Приёмка поставки — единственная точка, где Поставщики пишут в данные Склада** (увеличение `stock`), и это должно происходить через тот же порт/сервис, которым уже управляет резервированием `InventoryService`, а не отдельным прямым запросом к БД — иначе Склад теряет единственный источник истины о собственных остатках.

## События

- `supply.requested` (новое) — публикуется при создании заявки (вручную или автоматически по `stock.low`).
- `supply.received` (новое) — потребляется Складом (увеличение остатка) и Финансами (учёт закупки).

## Будущие расширения

- Автоматический выбор поставщика по товару (если у товара несколько поставщиков — критерии выбора не определены, открытый вопрос).
- Интеграция с внешними системами поставщиков (EDI/API) — потребует нового порта/адаптера по уже существующему паттерну Ports & Adapters, не отдельного механизма.
