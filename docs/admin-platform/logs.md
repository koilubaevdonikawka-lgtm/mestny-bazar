> Этот документ описывает исключительно журнал событий (аудит-лог) — что произошло на платформе и кто это сделал. Каталог автоматизаций (что настроено срабатывать) — `automation.md`; безопасность как периметр — `security.md`. Эти три модуля тесно связаны, но не идентичны: Журналы — это факт «что случилось», Автоматизация — «что настроено произойти», Безопасность — «кто и как может действовать».

## Назначение

Дать администратору неизменяемый, достоверный журнал значимых действий на платформе — для разбора инцидентов, ответа на вопросы «кто отменил этот заказ и почему», подтверждения соответствия процессам.

## Уже существующая модель (аудит)

```sql
audit_log (id, action, occurred_at, entity_type, entity_id, actor_id, payload jsonb, created_at)
```

- Запись пишется через `IAuditLog.append()`, реализация — `SupabaseAuditLog`, вызывается **исключительно через `service_role`** (запись в обход RLS — таблица помечена «server-only», без клиентского пути чтения, см. комментарий в миграции `20260725030000_audit_log.sql`).
- Подписка на события уже реализована по тому же паттерну, что и остальная автоматизация (`server/domain/audit-log/marketplace-events.subscriber.ts`) — журналирование **не встроено вручную** в каждый сервис (`OrderService.cancelOrder()` не содержит вызова `auditLog.append()`), а происходит автоматически как реакция на публикацию события в `IMarketplaceEventBus`. Это архитектурно важно: любое **новое** событие, публикуемое любым модулем, может быть подключено к журналу добавлением одной подписки, без изменения кода, который это событие порождает.
- Сегодня журналируются только два действия: `order.created`, `order.cancelled`. Все остальные значимые действия (подтверждение заказа админом, публикация товара, изменение остатка, назначение курьера) **не журналируются**, поскольку соответствующие модули либо не публикуют события вовсе (см. пробел, отмеченный в `orders.md`, `catalog.md`), либо ещё не существуют.

## Структура раздела

```
Журналы событий
├── Лента событий (фильтр: тип действия, сущность, исполнитель, период)
├── Карточка события (payload целиком — для разбора инцидента)
├── Журнал по сущности (например, вся история конкретного заказа — уже возможно через entity_type+entity_id)
└── Журнал по исполнителю (все действия конкретного администратора/сотрудника)
```

Индексы под эти сценарии уже существуют (`idx_audit_log_entity`, `idx_audit_log_occurred_at`) — раздел проектируется как UI поверх уже готовой для этого схемы, не требует новой модели данных для базового функционала.

## Расширение покрытия

Полноценный модуль Журналов требует, чтобы **каждый** модуль Административной платформы публиковал событие на каждое значимое действие (список уже собран по документам: `order.confirmed`, `product.published`, `stock.adjusted`, `courier.assigned`, `coupon.created`, `payout.completed`, `settings.changed`, `permission.changed` и т.д.) — это не задача самого модуля Журналов, а требование к каждому модулю-источнику, зафиксированное здесь как сквозное ожидание.

## Бизнес-логика

У Журналов нет собственной логики допуска/запрета — это чистый read-only потребитель событий (аналогично Аналитике, см. схему владения в мастер-спецификации). Единственное «правило» — что журнал **не редактируется и не удаляется** через UI ни при каких обстоятельствах (неизменяемость — это то, что делает аудит-лог полезным как источник истины при разборе инцидента; возможность правки сделала бы его бесполезным для этой цели).

## Будущие расширения

- Расширение покрытия событиями до уровня «каждое значимое действие каждого модуля» (см. выше) — основная работа этого модуля на практике, не новая инфраструктура.
- Хранение журнала за пределами `public.audit_log` для очень больших объёмов (архивация) — вопрос масштабирования (мастер-спецификация, Stage 10), не первоочередной.
