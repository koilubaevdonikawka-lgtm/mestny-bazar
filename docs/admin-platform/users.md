**Модуль:** Покупатели
**Статус в коде:** частично существует — `ProfileDTO` (`shared/contracts/user.ts`), `AddressService`, Supabase Auth (Google OAuth)
**Роли с доступом:** Admin (полный доступ, только просмотр — не редактирование чужих данных без явной причины)

> Этот документ описывает исключительно покупателей — тех, кто оформляет заказы на витрине. Продавцы, курьеры, склад и админ — отдельные роли, описанные в `sellers.md`, `couriers.md`; управление правами этих ролей — `permissions.md`. Заказы покупателя — `orders.md`, не этот документ.

## Назначение

Дать администратору обзор покупателей платформы: кто они, сколько заказов сделали, какой у них статус (активен/заблокирован), без необходимости лезть в Supabase Auth напрямую.

## Уже существующая модель данных

```
ProfileDTO { id, fullName, phone, roles: UserRole[], createdAt }
```

Роль `customer` — одна из пяти в `UserRole`, назначается по умолчанию при регистрации. Адреса покупателя — отдельная, уже реализованная сущность (`AddressService`, `IAddressRepository`), с поддержкой гостевого чекаута (заказ может существовать без привязанного покупателя — `orders.user_id` допускает `NULL`, см. `ARCHITECTURE_PRINCIPLES.md`, CD-07 «Guests Are a First-Class Path»).

## Структура раздела

```
Покупатели
├── Список (поиск по имени/телефону, фильтр по активности)
├── Карточка покупателя
│   ├── Профиль (имя, телефон, дата регистрации)
│   ├── Адреса (уже существующая сущность, только просмотр)
│   ├── История заказов (ссылка в orders.md, отфильтрованная по покупателю)
│   └── Действия: заблокировать/разблокировать (новое)
└── Гостевые заказы (заказы без привязанного покупателя — отдельная категория, не «покупатель» в строгом смысле)
```

## Бизнес-логика

Блокировка покупателя — новая функциональность, которой в коде сегодня нет. Она не должна становиться отдельным полем `is_blocked` с ручной проверкой в каждом месте, где покупатель что-то делает (оформляет заказ, отменяет) — правильное место для этой проверки: `PaymentPolicyService`/`OrderLifecycleService` (Rule Engine уже поддерживает «глобальные guard-правила» — см. `docs/principles/12-rule-engine-standard.md`, зарезервированный диапазон `order: 0–70` под будущие guard-правила вроде `BlockedUserRule`, упомянутый прямо в комментарии `server/di/container.ts`). Это значит: блокировка покупателя технически уже предусмотрена архитектурой (зарезервированное место в rule chain существует), но правило не написано.

## События

- `customer.blocked` / `customer.unblocked` (новое) — потребляется Журналами (`logs.md`) и, потенциально, Automation (например, отмена всех активных заказов заблокированного покупателя — это решение уровня продукта, не инженерное).

## Права доступа

| Действие | Admin |
|---|---|
| Просмотр списка и карточки покупателя | ✅ |
| Редактирование профиля покупателя | Не предусмотрено — покупатель управляет своим профилем сам, Административная платформа не подменяет его действия без явного продуктового решения |
| Блокировка/разблокировка | ✅ |
| Просмотр адресов | 👁 |

## Будущие расширения

- Сегментация покупателей (для `marketing.md` — например, «покупатели без заказов 30+ дней»), сегодня не реализована.
- Программа лояльности — явно вне текущего ядра платформы, описана только как продуктовое видение в `docs/architecture/ARCHITECTURE_POLICY.md` (Loyalty BCM, версия 2), не проектируется в рамках Административной платформы версии 1.
