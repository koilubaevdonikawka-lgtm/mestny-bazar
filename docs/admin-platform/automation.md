**Модуль:** Автоматизация
**Статус в коде:** частично существует — `IMarketplaceEventBus`/`MarketplaceEventsService` (in-memory pub/sub), `NotificationCenter`, подписчики (`subscribeAuditLog`, `subscribeNotificationCenter`, `subscribeAIWorkers`)
**Роли с доступом:** Admin (полный доступ — просмотр и настройка); остальные роли не взаимодействуют с этим модулем напрямую, только пользуются его результатами (уведомления)

> Этот документ описывает исключительно механизм автоматических процессов: события, очереди, триггеры, фоновые задачи. Конкретные события конкретных модулей (например, `order.cancelled`) уже перечислены в документах этих модулей — здесь фиксируется общий механизм и то, как за ним наблюдать/управлять им.

## Назначение

Дать платформе единый, наблюдаемый механизм «когда происходит X, автоматически сделать Y» — без необходимости внедрять вызов в каждое место кода, которое может привести к X (уже реализованный принцип, не новый).

## Уже существующая архитектура (не переизобретается)

```
Domain Service (например, OrderService.cancelOrder)
    │  await this.events.publish({ type: "order.cancelled", order, reason })
    ▼
IMarketplaceEventBus (MarketplaceEventsService — in-memory, единственный процесс, без внешнего брокера)
    │
    ├──▶ subscribeAuditLog       → пишет в audit_log (см. logs.md)
    ├──▶ subscribeNotificationCenter → уведомляет admin/warehouse/courier каналы (заглушки, см. integrations.md)
    └──▶ subscribeAIWorkers      → запускает анализ качества карточки (см. ai.md)
```

Ключевое, уже принятое и явно задокументированное в коде архитектурное свойство: **один подписчик, упавший с ошибкой, не должен ронять публикацию события и не должен маскировать успех/неуспех остальных подписчиков** (`MarketplaceEventsService.publish()` использует `Promise.allSettled`, каждый неуспех логируется отдельно). Любая новая автоматизация обязана следовать этому же свойству — иначе, например, сбой в интеграции с внешней CRM мог бы тихо заблокировать запись в журнал аудита того же события.

## Ограничение архитектуры сегодня

Шина событий — **in-memory, в рамках одного процесса**, без персистентности и без внешнего брокера (не Kafka/SQS/аналог). Это означает:
- Событие, опубликованное во время обработки запроса, обрабатывается подписчиками **синхронно в рамках того же запроса** (до возврата ответа клиенту) — не откладывается в очередь.
- Если процесс завершится между публикацией и обработкой (маловероятно при текущем синхронном `await`, но важно для будущих фоновых задач) — события не переживают перезапуск.
- Это осознанное, задокументированное ограничение текущей архитектуры (`server/domain/marketplace-events/marketplace-events.service.ts`, «In-memory marketplace event bus — single process, no external broker»), не случайный недосмотр.

**Для модуля Автоматизация это значит:** длительные/ненадёжные фоновые задачи (интеграция с внешним провайдером, генерация отчёта, массовая рассылка) не должны реализовываться как ещё один синхронный подписчик на существующей шине — это либо новый, отдельный механизм очереди (требует архитектурного решения — Cloudflare Queues или аналог, поскольку runtime — Cloudflare Workers), либо явное разделение на «быстрый» подписчик (публикует задачу) и «медленный» обработчик очереди (не спроектировано, открытый вопрос).

## Предполагаемая структура раздела

```
Автоматизация
├── Каталог событий (какие события публикует каждый модуль — сводка ссылок на документы модулей)
├── Подписчики (что на каждое событие реагирует, включён/выключен)
├── Триггеры по расписанию (новое — cron-подобные задачи: например, ежедневный отчёт, проверка порогов склада)
└── Журнал выполнения автоматизаций (успех/ошибка по каждому срабатыванию) — пересекается с logs.md
```

## Бизнес-логика

Включение/выключение конкретной автоматизации (например, «не уведомлять склад о новых заказах ночью») — настройка (`settings.md`), не код. Условия срабатывания сложной автоматизации (не просто «событие X произошло», а «событие X произошло И выполнено условие Y») — потенциальный Rule Engine, если таких условных автоматизаций станет много; для простого маппинга «событие → подписчик» текущий механизм `bus.subscribe(eventType, handler)` уже достаточен и не требует переусложнения.

## События

Автоматизация — не источник бизнes-событий, а наблюдатель/оркестратор поверх событий других модулей. Единственное, что Автоматизация может публиковать сама, — служебные события о собственном исполнении (`automation.triggered`, `automation.failed`) для журналирования.

## Будущие расширения

- Полноценная очередь с персистентностью для длительных задач (см. «Ограничение архитектуры» выше) — требует отдельного ADR, поскольку меняет способ доставки данных между слоями.
- Визуальный конструктор автоматизаций («если X, то Y») для администратора без участия разработчика — прямое продолжение главной цели платформы (раздел 1 мастер-спецификации), но требует, чтобы условия были представимы декларативно, а не только предопределённым набором подписчиков.
