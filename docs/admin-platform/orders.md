**Модуль:** Заказы
**Статус в коде:** в значительной степени существует — `OrderService`, `AdminOrderService`, `WarehouseOrderService`, `CourierOrderService`, `OrderLifecycleService` (Rule Engine), `CheckoutService`
**Роли с доступом:** Admin (полный доступ), Warehouse (только очередь сборки), Courier (только очередь доставки), Seller (только заказы со своими товарами — не реализовано)

> Этот документ описывает исключительно систему заказов внутри Административной платформы: просмотр, управление статусами, отмену. Оформление заказа покупателем (`CheckoutService`) уже реализовано и не входит в объём Административной платформы — здесь описывается то, что происходит с заказом **после** его создания, с точки зрения персонала.

## Назначение

Дать Admin единый обзор всех заказов платформы с возможностью управлять их статусом (подтверждение, отмена), а Warehouse/Courier — рабочую очередь заказов, относящихся к их этапу выполнения. Заказ как сущность и его жизненный цикл уже полностью реализованы — Административная платформа не переизобретает эту логику, а даёт ей интерфейс.

## Жизненный цикл заказа (уже реализовано, не подлежит пересмотру в рамках этого модуля)

```
CREATED → PAID → CONFIRMED → ASSEMBLING → READY_FOR_DELIVERY → OUT_FOR_DELIVERY → ARRIVED → DELIVERED
                     │             │                                    
                     └─────────────┴──────── CANCELLED (с разных точек, разными правилами) 
```

Каждый переход управляется `OrderLifecycleService` — универсальным Rule Engine (`order → applies → evaluate → terminal`, Принцип 12), сегодня зарегистрировано 10 правил: `TerminalStateGuardRule`, `AdminConfirmOrderRule`, `AdminCancelOrderRule`, `CustomerCancelOrderRule`, `WarehouseStartAssemblyRule`, `WarehouseCompleteAssemblyRule`, `CourierAcceptOrderRule`, `CourierStartDeliveryRule`, `CourierArriveRule`, `CourierCompleteDeliveryRule`. Административная платформа **вызывает** эти правила через существующие домен-сервисы (`AdminOrderService.confirmOrder/cancelOrder`), она не содержит собственной копии логики переходов.

## Архитектурное решение: буфер отмены заказа покупателем — 2 минуты

Это **уже принятое и реализованное архитектурное решение**, зафиксированное здесь как обязательное к учёту при проектировании Административной платформы (а не как предложение для обсуждения):

- Покупатель может самостоятельно отменить свой заказ **только в течение 2 минут после его создания** и только пока заказ находится в статусе `CREATED` или `PAID` (то есть до подтверждения администратором — `CONFIRMED` и позже отменить самостоятельно уже нельзя).
- Окно отмены проверяется **исключительно на сервере**, от `order.created_at` (источник истины — база данных) и серверных часов (`Date.now()`) — клиентский таймер используется только для отображения обратного отсчёта в UI и никогда не участвует в решении о том, разрешена ли отмена.
- Реализация: `CustomerCancelOrderRule` (`server/domain/order-lifecycle/rules/customer-cancel-order.rule.ts`) — часть общего `OrderLifecycleService`, использует общую (frontend + backend) утилиту `isWithinCancellationWindow`/`CUSTOMER_CANCELLATION_WINDOW_MS` из `shared/lib/order-cancellation.ts`, чтобы порог в 2 минуты был определён **в одном месте** и не мог разойтись между клиентским отображением и серверной проверкой.
- При успешной отмене: статус → `CANCELLED`, зарезервированный сток восстанавливается (best-effort — сбой восстановления логируется, но не отменяет уже состоявшуюся отмену и не блокирует ответ покупателю), пишется запись в журнал аудита (`order.cancelled`), публикуется событие `order.cancelled` в `IMarketplaceEventBus`.

**Для Административной платформы это означает:** раздел «Заказы» должен явно показывать администратору и складу, что заказ **ещё может быть отменён покупателем самостоятельно** в оставшееся окно (это не блокирует административные действия, но полезно для понимания, почему заказ мог внезапно исчезнуть из очереди). Изменение длительности окна (2 минуты) или условий (допустимые статусы) — это изменение уже принятого архитектурного решения, а не настройка Административной платформы; выносить его в `settings.md` как редактируемый параметр можно только через отдельное ADR (см. открытый вопрос №2 в мастер-спецификации).

## Административные действия

| Действие | Роль | Существующий механизм |
|---|---|---|
| Просмотр всех заказов (с фильтрами, пагинацией) | Admin | `AdminOrderService.listOrders()` |
| Просмотр одного заказа | Admin, Warehouse, Courier (в рамках своей очереди) | `getOrder()` у соответствующего сервиса |
| Подтверждение заказа (`CONFIRMED`) | Admin | `AdminOrderService.confirmOrder()` |
| Административная отмена заказа (в отличие от отмены покупателем — доступна из более широкого набора статусов, до `DELIVERED`/повторной `CANCELLED`) | Admin | `AdminOrderService.cancelOrder()` / `AdminCancelOrderRule` |
| Начало/завершение сборки | Warehouse | `WarehouseOrderService.startAssembly()/completeAssembly()` |
| Принятие/доставка курьером | Courier | `CourierOrderService` (см. также `couriers.md` — обнаруженный пробел в привязке заказа к курьеру) |

## Структура раздела

```
Заказы
├── Список (фильтр: статус, дата, способ оплаты, покупатель)
├── Карточка заказа
│   ├── Состав заказа, сумма, адрес, способ оплаты
│   ├── Таймлайн статусов (уже есть паттерн — OrderTimeline на стороне покупателя)
│   ├── Индикатор «окно самостоятельной отмены: осталось Х сек» (если применимо)
│   └── Доступные административные действия (зависят от текущего статуса и роли)
└── Очереди по ролям (Warehouse — сборка, Courier — доставка) — уже частично реализовано как отдельные страницы
```

## События

Заказы уже публикуют `order.created` и `order.cancelled` в `IMarketplaceEventBus`. Административная платформа должна расширить это до публикации событий на **каждый** статус-переход (`order.confirmed`, `order.assembling_started`, `order.ready_for_delivery`, `order.out_for_delivery`, `order.arrived`, `order.delivered`) — сегодня эти переходы происходят молча (только пишутся в БД через `updateStatus`), что не даёт Dashboard/Automation/Analytics обновляться в реальном времени. Это прямое расширение уже существующего паттерна, не новый механизм.

**Важное уточнение по срокам:** событие `order.created` публикуется немедленно (как и сегодня) и остаётся сигналом самого факта создания заказа. Но **операционный каскад, который на него реагирует** (уведомление продавца, операционное резервирование для склада, фоновый подбор курьера) — в целевой архитектуре запускается не по этому событию напрямую, а по отдельному, отложенному на 2 минуты триггеру, синхронизированному с истечением буфера отмены (см. `platform-lifecycle.md`, §3). Это не отменяет немедленную публикацию `order.created` — она нужна, например, Журналам и Dashboard для мгновенного отображения нового заказа, — но означает, что подписчики, отвечающие за операционные действия персонала, не должны реагировать на `order.created` напрямую.

## Права доступа

См. сводную матрицу в мастер-спецификации (раздел 8) и полную — в `permissions.md`. Ключевое уточнение для этого модуля: Warehouse и Courier получают **только свою очередь** (`listByStatuses` с фиксированным набором статусов), не полный список заказов — это уже так реализовано на уровне domain-сервисов, Административная платформа не должна ослаблять это ограничение ради «удобства UI».

## Будущие расширения

- Продавцу — фильтр «заказы с моими товарами» (сегодня заказ не хранит `sellerId` на уровне позиции для мультипродавцовой аналитики).
- Публикация событий на каждый статус-переход (см. «События» выше).
- Настраиваемость окна отмены — только через ADR, не как обычная настройка (см. §«Архитектурное решение» выше).
