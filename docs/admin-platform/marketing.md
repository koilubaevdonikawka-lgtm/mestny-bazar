> Этот документ описывает исключительно акции, купоны и маркетинговые кампании. Визуальное оформление баннеров и главной страницы — `design.md` (Маркетинг решает **что** и **кому** показать, Оформление — **как** это выглядит). Сегментация покупателей как данные — `users.md`; здесь — только то, как Маркетинг эти сегменты использует.

## Назначение

Дать администратору/маркетологу возможность создавать скидки, промокоды и таргетированные акции без участия разработчика — прямое применение главной цели Административной платформы (мастер-спецификация, раздел 1).

## Принцип владения данными и встраивания в цену

Маркетинг **не имеет права напрямую менять `products.price`** — это нарушило бы единственный источник истины о цене товара, которым владеет Каталог, и обошло бы уже существующую серверную проверку цены при чекауте (`CheckoutService.resolveLineItems()`, которая всегда пересчитывает цену на сервере — принцип CD-01, «Never Trust Client-Supplied Business Data», уже зафиксирован в `ARCHITECTURE_PRINCIPLES.md`). Вместо этого Маркетинг создаёт **правила скидок**, которые `PricingService` (уже существующий домен-сервис, сегодня считает только `subtotal`/`deliveryFee`/`total`) применяет во время расчёта заказа — по той же логике, по которой уже применяется `PaymentPolicyService` при чекауте.

## Предполагаемая структура

```
Маркетинг
├── Купоны/промокоды (создание, срок действия, лимит использований)
├── Акции (скидка на категорию/товар, период действия)
├── Сегменты (используют данные users.md — например, "новые покупатели")
└── Баннеры/кампании (контент — через design.md, таргетинг — здесь)
```

## Бизнес-логика

Применимость купона/акции к конкретному заказу — Rule Engine (Принцип 12), новый `DiscountPolicyService` в дополнение к уже существующему `PaymentPolicyService`, встраиваемый в `CheckoutService` на этапе расчёта цены (`PricingService.calculateSubtotal`), тем же способом, каким уже встроен `paymentPolicy.assertCanUsePaymentMethod()`. Правила вида «нельзя применить два купона одновременно», «минимальная сумма заказа для купона» — это именно то, для чего Rule Engine уже используется в проекте, не новый класс задач.

**Важное ограничение:** расчёт цены с учётом скидки должен оставаться серверным и пересчитываемым при каждом запросе — купон, применённый на клиенте, ничего не значит, пока сервер не подтвердил его действительность и не применил скидку самостоятельно (прямое продолжение принципа «Server is Source of Truth»).

## События

- `coupon.created` / `coupon.redeemed` (новое) — потребляется Аналитикой (эффективность акции) и Журналами.
- `campaign.started` / `campaign.ended` (новое) — потребляется Dashboard, Оформлением (`design.md` может реагировать сменой баннера).
