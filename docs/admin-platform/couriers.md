**Модуль:** Курьеры
**Статус в коде:** частично существует — `CourierOrderService` (общая очередь доставки), роль `courier` в `UserRole`, проверка через `requireCourierFromRequest()`
**Роли с доступом:** Admin (управление и обзор со стороны Административной платформы), Courier (не через Административную платформу — через отдельную PWA, см. ниже)

> Этот документ описывает исключительно систему курьеров: как заказ попадает к курьеру, как устроено курьерское приложение и как оно связано с остальной платформой. Сама доставка как этап жизненного цикла заказа (`OUT_FOR_DELIVERY → ARRIVED → DELIVERED`) уже описана в `orders.md` — здесь фокус на курьере как исполнителе, а не на статусе заказа.

## Ранее принятые архитектурные решения (обязательны к учёту, не подлежат пересмотру в рамках этого документа)

1. **Курьеры не закрепляются за районами.** Любой активный курьер потенциально может выполнить доставку в любой район — система не хранит статичной привязки «курьер X всегда возит район Y».
2. **Система автоматически выбирает наиболее подходящего курьера** для каждого заказа, а не курьер вручную выбирает заказ из общего списка «кто успел».
3. **Курьерское приложение — отдельная PWA внутри проекта**, а не раздел Административной платформы (в отличие от Warehouse/Seller, которые являются разделами внутри Административной платформы — см. §3 мастер-спецификации).
4. **Общая база данных** — курьерская PWA не имеет собственного хранилища, работает с теми же таблицами Supabase, что и всё остальное.
5. **Общий Backend** — курьерская PWA обращается к тем же `server/functions/`, что и остальная платформа, через тот же Platform API (`src/api/`), не к отдельному сервису.
6. **Единая авторизация** — курьер входит через тот же Supabase Auth, ту же таблицу `user_roles`, тот же механизм `requireCourierFromRequest()`, что уже реализован.

## Обнаруженный пробел (критично для проектирования этого модуля)

Аудит кодовой базы, проведённый перед написанием этой документации, подтвердил: **решение №2 («автоматический подбор наиболее подходящего курьера») сегодня не реализовано.**

Конкретно:
- `shared/contracts/order.ts` (`OrderDTO`) **не содержит поля**, связывающего заказ с конкретным курьером (нет `courierId`/`assignedCourierId`).
- `CourierOrderService.acceptOrder()` вызывает `orderLifecycle.assertCanTransition(...)` (проверка, что переход в принципе разрешён), но **не вызывает `updateStatus` и не сохраняет никакого состояния** — метод по факту ничего не персистит.
- `CourierOrderService.listDeliveryOrders()` возвращает **все** заказы в статусах `READY_FOR_DELIVERY | ASSEMBLING | OUT_FOR_DELIVERY | ARRIVED` — единый список, который видят одновременно все курьеры с ролью `courier`, без фильтрации по тому, «назначен» ли этот заказ конкретному курьеру.

Другими словами: то, что сегодня реализовано, — это **общая доступная всем курьерам очередь** («кто первый принял — тот и повёз»), а не автоматическое назначение. Это прямо противоречит ранее принятому решению №2 и является тем самым техническим долгом, который должна закрыть Административная платформа. Это не ошибка предыдущей реализации — это ожидаемое состояние на данном этапе миграции (courier-flow был реализован как MVP-очередь до появления Административной платформы, где могла бы жить логика подбора).

Плюс новая сущность для отслеживания состояния курьера в моменте (доступен/занят/оффлайн, текущая геопозиция — если продуктово требуется):

## Бизнес-логика: подбор курьера

Подбор «наиболее подходящего курьера» — это классическая задача для Rule Engine (Принцип 12), не для одной хардкоженной функции сортировки. Предлагаемая структура: `CourierAssignmentPolicyService` с правилами вида `NearestAvailableCourierRule`, `LeastLoadedCourierRule`, `HighestRatingCourierRule`, применяемыми по порядку (`order`), где точные критерии (расстояние, текущая загрузка, рейтинг) — **открытый продуктовый вопрос**, зафиксированный в мастер-спецификации (§12, открытый вопрос №3), а не инженерное решение, принимаемое в одиночку при реализации.

Назначение курьера должно происходить через тот же `OrderLifecycleService` (новое правило вместо/в дополнение к нынешнему `CourierAcceptOrderRule`, которое сейчас не персистит назначение), чтобя логика допуска («может ли этот курьер взять этот заказ») и логика записи состояния не расходились, как это уже происходит в других частях системы (например, отмена заказа покупателем — одна операция, а не отдельно «проверить» и отдельно «записать»).

## Курьерская PWA — устройство

PWA — это **отдельная точка входа** (отдельный маршрут/сборка на фронтенде), но не отдельное приложение в архитектурном смысле:

```
Courier PWA (src/routes/courier/... — уже существующая точка входа для orders)
    │
    │  тот же src/api/ → server/functions/ → server/domain/
    │  та же Supabase Auth-сессия
    │  та же таблица user_roles (роль "courier")
    ▼
Общий Backend (server/) ── Общая БД (Supabase)
```

Требования к PWA как классу приложения (следствие принципов «Browser First» и «Независимость от ОС» из мастер-спецификации): устанавливается на экран телефона без App Store/Google Play, работает в браузере, минимальный вес, работоспособность при нестабильном интернете (курьер «в поле») — для последнего сегодня в проекте нет ни service worker, ни offline-кэширования (подтверждено аудитом: `manifest.json`/PWA-инфраструктуры в проекте не существует вовсе — см. `docs/architecture/ARCHITECTURE_PRINCIPLES.md`, ранее зафиксированный пробел). Это означает, что «курьерская PWA» сегодня существует только как обычные, не-PWA веб-страницы (`src/routes/courier/orders/*`) — сама PWA-обёртка (manifest, service worker, «Добавить на экран») ещё не реализована ни для одной части платформы.

## Структура раздела в Административной платформе (управление, не сама PWA)

```
Курьеры  (раздел внутри Административной платформы, для Admin)
├── Список курьеров (статус: доступен/занят/оффлайн, текущая нагрузка)
├── Карточка курьера (история доставок, рейтинг — если введён)
├── Активные назначения (какой заказ у какого курьера прямо сейчас)
└── Настройка правил подбора (параметры CourierAssignmentPolicyService)
```

## События

- `courier.assigned` (новое) — публикуется при назначении курьера на заказ, потребляется Dashboard и курьерской PWA (push/live-обновление списка заказов курьера).
- `courier.status_changed` (новое) — доступен/занят/оффлайн, потребляется логикой подбора.

## Права доступа

| Действие | Admin | Courier |
|---|---|---|
| Просмотр всех курьеров и назначений | ✅ | — |
| Настройка правил автоподбора | ✅ | — |
| Просмотр своей очереди доставки | — | ✅ (через PWA, не через Административную платформу) |
| Изменение своего статуса (доступен/занят) | — | ✅ (через PWA) |

## Будущие расширения

- Полноценная PWA-инфраструктура (manifest, service worker, offline-режим) — сегодня отсутствует полностью, требуется до того, как courier-flow можно будет считать «отдельным PWA» не только по маршрутизации, но и по факту.
- Геолокация и построение маршрута — не заложено ни в модели данных, ни в домене.
- Оплата/учёт заработка курьера — зависит от `finance.md`, не спроектировано.
