> Этот документ описывает исключительно периметр безопасности Административной платформы: аутентификацию, авторизацию, защиту данных. Права доступа как модель ролей/разрешений — `permissions.md` (этот документ описывает, **как обеспечивается**, что модель прав не обходится, а не саму модель).

## Назначение

Свести в одном месте то, что сегодня разбросано по коду и мигрциям как неявные соглашения, и дать администратору видимость в состояние периметра безопасности платформы (что защищено, что нет).

## Уже существующая модель безопасности (аудит)

| Уровень | Механизм | Где |
|---|---|---|
| Аутентификация | Supabase Auth (JWT), Google OAuth | `src/lib/auth.ts`, `server/auth/resolve-user.ts` |
| Проверка роли | `require<Role>FromRequest()` — JWT валидируется, роль читается из `user_roles`, **никогда не берётся из тела запроса** | `server/auth/resolve-user.ts` |
| Row Level Security | `auth.uid() = user_id` — политика владения на каждой таблице с персональными данными (`addresses`, `carts`, `cart_items`, и т.д.) | Миграции `supabase/migrations/*.sql` |
| Обход RLS | `service_role` ключ (`supabaseAdmin` клиент) — используется **только на сервере**, никогда в браузере | `server/adapters/supabase/client.ts` |
| Таймаут внешних вызовов auth | JWKS-запрос при проверке JWT ограничен 5 секундами (`AUTH_FETCH_TIMEOUT_MS`), чтобы недоступность auth-эндпоинта Supabase не подвешивала каждый запрос | `server/adapters/supabase/address.repository.ts` (`createSupabaseFetch`) |
| Границы импортов | ESLint `no-restricted-imports` — фронтенд не может импортировать `@supabase/supabase-js` (для данных) или `server/**` | `eslint.config.js`, Принцип 6 |

**Важное архитектурное свойство, уже реализованное и обязательное к сохранению:** `service_role` ключ обходит RLS полностью — это значит, что **вся защита данных сегодня фактически обеспечивается кодом сервера** (проверка `userId` в каждом запросе к репозиторию), а RLS — это defense-in-depth, вторая линия, а не первая. Административная платформа не должна ослаблять код серверной проверки в расчёте на то, что «RLS всё равно защитит» — RLS не применяется к запросам через `service_role`, которым выполнены все текущие server-side репозитории.

## Обнаруженные пробелы

| Пробел | Статус |

## Ограничения при реализации

1. **Административная платформа не вводит второй контур авторизации.** Всё управление доступом — расширение уже существующего `user_roles`/`require<Role>FromRequest()` (см. `permissions.md`), не параллельная система логинов.
2. **service_role ключ никогда не передаётся клиенту ни в каком виде**, включая частичное/маскированное отображение в UI Административной платформы (см. также ограничение в `integrations.md` про секреты).
3. Любая новая таблица с персональными или бизнес-чувствительными данными **обязана** получить RLS-политику по уже устоявшемуся паттерну (`auth.uid() = owner_column`), даже если в текущей архитектуре она фактически защищена только кодом сервера, — это не опциональный шаг, а уже принятая практика проекта (подтверждена ~10+ существующими миграциями).

## Будущие расширения

- Rate limiting — требует инфраструктурного решения (Cloudflare), вне объёма чисто-документационного проектирования.
- Двухфакторная аутентификация для ролей `admin`/`admin-finance` — не заложено, продуктовое решение.
- Автоматическое обнаружение аномального доступа (например, вход в Административную платформу с нового устройства) — зависит от появления журнала попыток доступа (см. «Обнаруженные пробелы»).
