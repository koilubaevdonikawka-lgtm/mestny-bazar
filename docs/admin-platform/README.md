## Назначение Административной платформы

Административная платформа — единая точка управления всеми операционными процессами «Местного Базара»: каталогом, заказами, складом, курьерами, продавцами, покупателями, маркетингом, финансами и настройками магазина. Главная и не подлежащая пересмотру цель: **все изменения в работе магазина должны быть возможны без участия разработчика** — через интерфейс платформы, а не через правку кода. Полная формулировка цели, философии и ограничений — [`ADMIN_PLATFORM_MASTER_SPEC.md`](./ADMIN_PLATFORM_MASTER_SPEC.md), раздел 1–2.

## Порядок чтения документов

Документация спроектирована так, чтобы читаться **сверху вниз**, не вразнобой:

1. **Этот README** — что где лежит и зачем.
2. [`ADMIN_PLATFORM_MASTER_SPEC.md`](./ADMIN_PLATFORM_MASTER_SPEC.md) — цель, философия, полный список модулей, роли, матрица доступа верхнего уровня, ограничения. **Не содержит** детального описания ни одного модуля — это намеренно.
3. [`platform-lifecycle.md`](./platform-lifecycle.md) — как роли (Покупатель, Администратор, Продавец, Курьер, Склад, AI) взаимодействуют друг с другом во времени, на примере полного пути заказа. Даёт контекст, без которого документы отдельных модулей читаются как разрозненные фрагменты.
4. [`dependency-map.md`](./dependency-map.md) — какие модули от каких зависят, что нельзя менять изолированно.
5. **Специализированные документы модулей** (`dashboard.md`, `catalog.md`, …) — читаются по мере необходимости, не обязательно все подряд; каждый самодостаточен для своего модуля благодаря шагам 2–4, уже давшим общий контекст.
6. [`IMPLEMENTATION_ORDER.md`](./IMPLEMENTATION_ORDER.md) — открывается непосредственно перед началом реализации, не раньше: это операционный план, а не архитектурный контекст.

## Связь с Architecture Principles

Административная платформа не вводит новую архитектуру — она встраивается в уже существующую и наследует её принципы без исключений. Каждый документ этой папки, начиная с этой ревизии, содержит в заголовке поле **«Связанные Architecture Principles»** со ссылками на конкретные ID (`PL-01`…`PL-14`, `CD-01`…`CD-11`) из [`docs/architecture/ARCHITECTURE_PRINCIPLES.md`](../architecture/ARCHITECTURE_PRINCIPLES.md). Если при реализации возникает необходимость нарушить принцип — это не решается внутри документации Административной платформы (см. [`docs/architecture/README.md`](../architecture/README.md), раздел «Когда нельзя менять Architecture Principles»).

## Связь с ADR

ADR фиксируют **конкретные, разовые решения**, принципы — **правила игры** (разница объяснена в [`docs/architecture/README.md`](../architecture/README.md)). Сегодня существует один ADR — [ADR-001](../adr/ADR-001-ports-and-adapters.md) (Ports & Adapters Platform Layer), и на него ссылается каждый документ этой папки, поскольку вся Административная платформа строится поверх решения, зафиксированного в этом ADR.

Ряд решений, задокументированных в этой папке, по критериям [Принципа 14](../principles/14-architecture-decision-record.md) **должны в будущем стать отдельными ADR**, а не оставаться только записью в спецификации модуля — они либо меняют поток данных, либо вводят новую границу между слоями:

| Кандидат на ADR | Где описан |
|---|---|
| Двухминутный буфер отмены как гейт перед всем операционным каскадом (уведомления, резерв, сборка, поиск курьера) | [`platform-lifecycle.md`](./platform-lifecycle.md) |
| Автоматический подбор курьера (новая модель данных, новый Rule Engine) | [`couriers.md`](./couriers.md) |
| Введение под-ролей внутри `admin` (`admin-finance`/`admin-marketing`) | [`permissions.md`](./permissions.md) |
| Модель бизнес-настроек в БД, разделение с переменными окружения | [`settings.md`](./settings.md) |

Эти решения **уже прошли архитектурное проектирование**, но не заменяют собой формальный ADR — они станут ADR по мере перехода от проектирования к реализации (см. [`IMPLEMENTATION_ORDER.md`](./IMPLEMENTATION_ORDER.md)).

## Связь с `docs/architecture/ARCHITECTURE_PRINCIPLES.md`

`ARCHITECTURE_PRINCIPLES.md` — это восстановленный свод принципов **всего проекта** (41 принцип, включая уже реализованные PL-01…PL-14 и обнаруженные в коде CD-01…CD-11). Документация Административной платформы **не дублирует** его содержание — она на него ссылается точечно, там, где конкретный модуль применяет конкретный принцип (пример: `orders.md` ссылается на CD-01 «Never Trust Client-Supplied Business Data» именно в контексте серверной проверки буфера отмены, не пересказывая сам принцип). Если возникает противоречие между документом Административной платформы и `ARCHITECTURE_PRINCIPLES.md` — правым считается `ARCHITECTURE_PRINCIPLES.md`, документ Административной платформы исправляется (см. `docs/architecture/README.md`, «Когда нельзя менять Architecture Principles»).

## Связь между MASTER SPEC и специализированными документами

`ADMIN_PLATFORM_MASTER_SPEC.md` — единственный документ, у которого есть право описывать платформу **целиком**: цель, философию, полный список модулей, их взаимосвязь верхнего уровня, роли, сводную матрицу доступа, бизнес-процессы верхнего уровня, ограничения. Он **намеренно** не детализирует ни один модуль — как только описание одного модуля начинает превышать пару предложений, оно принадлежит документу этого модуля, не MASTER SPEC.

Специализированные документы (`dashboard.md`, `catalog.md`, …), в свою очередь, **не переопределяют** ничего, уже зафиксированного в MASTER SPEC (роли, сквозные архитектурные ограничения) — они его детализируют. Если специализированный документ противоречит MASTER SPEC — это ошибка специализированного документа, исправляется он (в этой ревизии таких противоречий не найдено — см. отчёт по итогам аудита, раздел «Проверь документацию» в Промпте №002).

## Связь с `IMPLEMENTATION_ORDER.md`

`IMPLEMENTATION_ORDER.md` — единственный документ этой папки, который описывает **порядок** реализации (номер этапа, цель, критерии завершения, обязательные проверки, коммит). Все остальные документы отвечают на вопрос «как это должно быть устроено», `IMPLEMENTATION_ORDER.md` — на вопрос «в каком порядке это строить». Он не содержит архитектурных решений сам по себе — только ссылается на документы, где эти решения уже приняты.

> **Важно:** ранее (Промпт №001) был создан `implementation-roadmap.md` с той же целью. По итогам аудита (см. отчёт по Промпту №002) он помечен как **заменённый** `IMPLEMENTATION_ORDER.md` — подробности и обоснование в заголовке самого `implementation-roadmap.md`. Файл не удалён (история решений сохраняется, по аналогии с тем, как проект не удаляет superseded ADR), но **не используется** как актуальный источник порядка реализации.

## Правила сопровождения документации

1. **Единый заголовок обязателен для каждого документа этой папки** (см. шаблон ниже) — ни один новый документ не добавляется без него.
2. **Версионирование:** `0.x` — документ ещё в проектировании, содержание может существенно меняться; `1.0` — документ принят как основа для реализации соответствующего модуля (переход `0.x → 1.0` для конкретного модуля происходит не раньше, чем начинается этап `IMPLEMENTATION_ORDER.md`, затрагивающий этот модуль); дальнейшие версии (`1.1`, `2.0`) — по тем же правилам, что уже приняты для ADR (существенное изменение решения = обсуждение, не тихая правка).
3. **Статус** — один из пяти: `Действующий — центральный документ`, `Черновая архитектура — не реализовано`, `Черновая архитектура — частично реализовано`, `План реализации`, `Заменён` (с указанием, чем).
4. **Дата последнего обновления** меняется при каждой правке содержания документа (не при косметике вроде исправления опечатки в заголовке).
5. **Не менять содержание принципов задним числом под текущий код** — если реализация разошлась с документом, это фиксируется как найденное расхождение (как уже сделано, например, в `couriers.md` относительно автоподбора курьера), а не тихо переписывается в документе.
6. **Новый модуль = новый файл** с тем же заголовком, добавленный в этот README (структура выше), в `dependency-map.md` и, при необходимости, в матрицу доступа `ADMIN_PLATFORM_MASTER_SPEC.md` — не отдельная, никому не известная запись.
7. **Формат единого заголовка** (используется во всех документах этой папки без исключения):

```markdown
# <Название документа>

| Поле | Значение |
|---|---|
| **Версия** | 0.1 |
| **Статус** | <один из пяти статусов выше> |
| **Дата последнего обновления** | YYYY-MM-DD |
| **Связанные документы** | ссылки на 2–5 наиболее релевантных документов этой папки |
| **Связанные ADR** | ссылки, либо «нет» |
| **Связанные Architecture Principles** | ID вида PL-XX / CD-XX |

---
```
