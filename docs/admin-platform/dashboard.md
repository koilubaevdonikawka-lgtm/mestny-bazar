> Этот документ описывает исключительно Dashboard. Данные, которые Dashboard отображает, принадлежат другим модулям (Заказы, Склад, Каталог и т.д.) — их бизнес-логика описана в соответствующих документах, здесь — только то, как Dashboard эти данные показывает и на какие действия даёт короткий путь.

## Назначение

Dashboard — первый экран после входа в Административную платформу. Его задача — ответить на вопрос «что требует внимания прямо сейчас», не заставляя пользователя обходить все разделы платформы вручную. Dashboard не хранит и не изменяет данные — это агрегирующая витрина над другими модулями (см. §6 мастер-спецификации: «модуль-потребитель никогда не пишет напрямую в таблицы модуля-владельца»).

Dashboard **не является** аналитическим модулем (это `analytics.md`) — Dashboard показывает оперативную, «сейчас», картину, а Аналитика — исторические тренды и отчёты.

## Структура

Dashboard строится по ролям: `admin` видит сводку по всей платформе, `warehouse` — только свою очередь, `seller` — только свои товары/заказы. Это не UI-скрытие блоков, а следствие того, что данные для каждого виджета запрашиваются через server function, которая сама ограничивает выборку ролью вызывающего (как уже сделано, например, в `WarehouseOrderService.listAssemblyOrders()` — сервис не принимает фильтр «покажи мне только моё», он **всегда** возвращает только релевantную роли выборку).

Компоновка (для роли `admin`, полный набор):

```
┌─────────────────────────────────────────────────────────┐
│  Строка ключевых показателей (карточки)                   │
├───────────────┬───────────────┬───────────────┬──────────┤
│ Новые заказы  │ На сборке     │ В доставке    │ Выручка   │
│ сегодня       │               │               │ сегодня   │
└───────────────┴───────────────┴───────────────┴──────────┘
┌─────────────────────────────┬─────────────────────────────┐
│  Виджет: Требует внимания    │  Виджет: Заказы в реальном   │
│  (низкий остаток, зависшие   │  времени (лента статусов)    │
│  заказы, ошибки интеграций)  │                              │
├─────────────────────────────┼─────────────────────────────┤
│  Виджет: Очередь склада      │  Виджет: Активность          │
│  (кол-во на сборке/готово)   │  курьеров                    │
└─────────────────────────────┴─────────────────────────────┘
```

## Виджеты

| Виджет | Источник данных (модуль-владелец) | Обновление |
|---|---|---|
| Карточки ключевых показателей | Заказы, Финансы | При загрузке страницы + периодический опрос |
| «Требует внимания» | Склад (низкий остаток), Заказы (зависшие в статусе дольше нормы), Интеграции (ошибки платежей/уведомлений) | При загрузке + событие |
| Заказы в реальном времени | Заказы (через `IMarketplaceEventBus`, событие `order.created`/статус-переходы) | Событийно (live) |
| Очередь склада | Склад | При загрузке + событие |
| Активность курьеров | Курьеры | При загрузке + событие |

## Карточки

Карточка ключевого показателя — минимальная единица Dashboard: число + подпись + (опционально) короткий тренд («+12% к вчера») + клик ведёт в соответствующий модуль с уже применённым фильтром (например, карточка «На сборке» ведёт в Заказы, отфильтрованные по статусу `ASSEMBLING`). Dashboard не содержит собственной логики фильтрации — он лишь формирует ссылку с параметрами, которые понимает модуль-владелец.

## Действия

Dashboard **не выполняет бизнес-операций напрямую** (не подтверждает заказ, не меняет остаток) — только предоставляет переход в модуль, где это действие определено. Единственное исключение — быстрые, безопасные, идемпотентные действия уровня «подтвердить прочтение предупреждения», если такие понадобятся; ни одно мутирующее бизнес-действие Dashboard не реализует самостоятельно.

## Бизнес-логика

У Dashboard нет собственной бизнес-логики в смысле правил допуска/запрета — это read-only агрегатор. Единственная логика, которая ему принадлежит: приоритизация того, что показывать в «Требует внимания» (какие пороги считать критичными). Эта приоритизация — потенциальный кандидат на Rule Engine в будущем (если правил станет много и они должны настраиваться без деплоя), но на первом этапе может быть простым, явно прописанным набором условий, поскольку сам факт «показать/не показать предупреждение» не является правилом уровня бизнес-транзакции (в отличие от, например, «можно ли оплатить наличными»).

## События

Dashboard **подписывается** на события `IMarketplaceEventBus` для живого обновления виджетов (`order.created`, `order.cancelled`, будущие статус-переходы), но сам не публикует ни одного события — он не является источником истины ни для одной сущности.

## Права доступа

| Роль | Что видит |
|---|---|
| Admin | Все виджеты, вся платформа |
| Admin-Finance (если введена — см. открытый вопрос мастер-спецификации, §12) | Только карточки выручки/финансов |
| Admin-Marketing (если введена) | Только виджеты, связанные с каталогом/акциями |
| Warehouse | Только «Очередь склада» и связанные предупреждения о нехватке |
| Seller | Только показатели по своим товарам и своим заказам |
| Courier | Dashboard недоступен — курьер использует отдельную PWA (см. `couriers.md`), у которой свой, гораздо более узкий «домашний экран» |

## Будущие расширения

- Настраиваемая компоновка виджетов (drag-and-drop), сохраняемая per-пользователь — требует отдельного хранилища настроек UI, не бизнес-данных.
- Виджет ИИ-инсайтов (см. `ai.md`) — сегодня невозможен, поскольку результаты `marketplace-ai` никем не потребляются (см. известный пробел в `ARCHITECTURE_PRINCIPLES.md`).
- Виджет активных экспериментов/A-B тестов — зависит от `marketing.md`, не спроектирован.
