**Документ:** только дорожная карта. Описание модулей — в соответствующих `*.md` этой папки; здесь — исключительно порядок и границы этапов реализации.

## Принцип разбиения

Минимально возможное число крупных, максимально автономных этапов. «Автономный» означает: по завершении этапа платформа (и существующий маркетплейс) находится в полностью рабочем состоянии — ни один этап не оставляет систему в промежуточном, нерабочем виде до начала следующего (тот же принцип, что уже применялся при миграции на Ports & Adapters, см. `docs/stage-1-checklist.md`: «Fix architecture without changing runtime behavior»).

Этапы упорядочены по зависимости владения данными (см. `ADMIN_PLATFORM_MASTER_SPEC.md`, раздел 6): модуль-потребитель не может быть реализован раньше модуля-владельца, чьи данные он использует.

**Каждый этап обязан завершаться прогоном:** `typecheck`, `lint`, `tests`, `build` — без исключений, по уже действующей в проекте практике (см. историю коммитов этой кодовой базы, каждое предыдущее архитектурное изменение проверялось этим же набором).

## Этап 1 — Фундамент Административной платформы

**Модули:** каркас платформы (навигация, роутинг, общий layout), `permissions.md` (базовая версия — переиспользование существующих ролей, без под-ролей на этом этапе), `settings.md` (инфраструктура: `platform_settings`, `ISettingsRepository`, без миграции конкретных хардкодов из витрины)

**Почему первым:** всё остальное — разделы внутри этого каркаса, защищённые этим же механизмом прав. Реализация раздела без готовой навигации и без единого способа проверки прав означала бы либо блокировку, либо временный, потом переделываемый код.

**Что НЕ входит:** под-роли `admin-finance`/`admin-marketing` (остаётся открытым продуктовым вопросом — можно достроить в любой последующий этап без переделки фундамента, поскольку `permissions.md` уже спроектирован как расширяемый Rule Engine).

**Результат этапа:** пустая, но полностью рабочая Административная платформа с навигацией и защитой по ролям; ни один существующий customer-facing путь не изменён.

---

## Этап 2 — Ядро операционного управления

**Модули:** `dashboard.md`, `orders.md`, `catalog.md`, `warehouse.md`

**Почему вторым:** это модули, где уже существует значительная часть домена (`OrderService`, `AdminOrderService`, `CatalogService`, `InventoryService`, весь Order Lifecycle Rule Engine) — этап **достраивает UI и недостающие серверные операции** (управление категориями, пороги склада) поверх уже проверенной бизнес-логики, а не создаёт домен с нуля. Наименее рискованный крупный этап.

**Явно фиксируется:** буфер отмены заказа (2 минуты, `orders.md`) — уже готовая логика, этот этап только делает её видимой в интерфейсе персонала, не меняет её.

**Что НЕ входит:** прогноз окончания товара (`warehouse.md`) — зависит от истории расхода, которую разумно агрегировать после того, как через платформу пройдёт достаточно операционных данных; переносится в Этап 4 вместе с Аналитикой, с которой прогноз концептуально ближе.

**Результат этапа:** администратор, склад видят и управляют заказами/каталогом/остатками через Административную платформу, не через прямые правки в БД.

## Этап 3 — Участники платформы

**Модули:** `sellers.md`, `suppliers.md`, `users.md`, `couriers.md`

**Почему третьим:** зависит от Этапа 2 (заказы и каталог должны уже существовать в Административной платформе, чтобы карточка продавца/курьера могла на них ссылаться). Этот этап **закрывает главный технический долг, обнаруженный аудитом**: отсутствие привязки заказа к курьеру и механизма автоподбора (`couriers.md`) — на сегодня самый рискованный и содержательный пункт этапа, требует нового поля в модели заказа и нового Rule Engine (`CourierAssignmentPolicyService`).

**Что НЕ входит:** сама PWA-инфраструктура для курьера (manifest, service worker, offline-режим) — это отдельная, чисто техническая задача, не зависящая от бизнес-логики назначения курьера, может выполняться параллельно отдельной подкомандой, но по завершении Этапа 3 (нет смысла строить offline-приложение до того, как у него будет корректная бизнес-логика для работы).

**Результат этапа:** у платформы появляются полноценные сущности «продавец» и «поставщик»; заказ действительно назначается конкретному курьеру автоматически, а не разбирается из общей очереди.

## Этап 4 — Деньги, рост, аналитика

**Модули:** `analytics.md`, `finance.md`, `marketing.md`, `design.md` (плюс отложенный из Этапа 2 прогноз склада)

**Почему четвёртым:** каждый из этих модулей **потребляет** данные, накопленные в Этапах 2–3 (заказы, продавцы, курьеры) — их ценность и тестируемость напрямую зависят от того, что предыдущие этапы уже поставляют реальные операционные данные.

**Явное ограничение:** полная функциональность `finance.md` (автоматическая сверка платежей) заблокирована внешней зависимостью — реальной интеграцией Finik (Stage 7 основной миграции проекта, вне рамок Административной платформы). Этап 4 реализует всё, что не зависит от Finik (учёт по данным заказа, выплаты продавцам, комиссия), и явно помечает сверку как заблокированную, не пытаясь обойти отсутствующую интеграцию суррогатным решением.

**Результат этапа:** администратор может анализировать динамику, управлять акциями и оформлением витрины, видеть финансовую картину в той части, что не требует внешней платёжной интеграции.

## Этап 5 — Наблюдаемость и автоматизация

**Модули:** `automation.md`, `integrations.md`, `ai.md`, `security.md`, `logs.md`

**Почему последним:** это модули **наблюдения и настройки** поверх уже работающей системы (аналогично тому, как в основной архитектуре проекта Audit Log и Notification Center — «сквозные» подписчики, а не часть основного потока данных) — их ценность максимальна, когда есть за чем наблюдать, то есть после того как Этапы 1–4 уже дают платформе реальный объём событий и операций.

**Явно включено:** расширение покрытия событиями (`orders.md`, `catalog.md` и другие модули сегодня публикуют события не на каждый значимый переход) — эта работа физически распределена по всем предыдущим модулям, но её **сведение в единый обзор** (Автоматизация, Журналы) — задача этого этапа.

**Явно включено:** решение по обнаруженному в `ai.md` пробелу (результаты ИИ-анализа карточки никем не потребляются) — либо подключение к модерации в Каталоге, либо осознанное отключение автозапуска на каждый заказ.

**Результат этапа:** платформа полностью наблюдаема (журналы, статус интеграций, статус безопасности) и имеет единый обзор автоматических процессов.

## Обязательное условие завершения каждого этапа

```
typecheck  →  lint  →  tests  →  build
```

Этап не считается завершённым, если любая из четырёх проверок не проходит. Ни один этап не коммитится и не переходит в следующий при красном статусе хотя бы одной проверки — без исключений, по уже действующей в проекте практике.
