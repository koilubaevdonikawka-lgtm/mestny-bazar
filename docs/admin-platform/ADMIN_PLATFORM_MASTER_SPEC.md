## 1. Цель Административной платформы

Административная платформа — это единая точка управления всеми операционными процессами «Местного Базара»: каталогом, заказами, складом, курьерами, продавцами, покупателями, маркетингом, финансами и настройками магазина.

Главная цель сформулирована явно и является архитектурным требованием, а не пожеланием:

> **Все изменения в работе магазина должны быть возможны без участия разработчика** — через интерфейс Административной платформы, а не через правки кода.

Это прямое продолжение уже принятого в проекте Принципа 11 (Feature Flags) и общего курса на то, что бизнес-логика конфигурируется, а не хардкодится (см. `docs/principles/12-rule-engine-standard.md`, раздел «Forbidden»: `if (paymentMethod === "CASH")` в оркестраторах запрещён). Административная платформа — это интерфейс, через который сотрудники магазина взаимодействуют с этим уже существующим механизмом конфигурации и правил, не более и не менее.

Вторичные цели:
- Дать каждой роли (админ, склад, курьер, продавец) свой рабочий инструмент поверх **одного и того же** backend и домена, без дублирования бизнес-логики.
- Заложить точки расширения так, чтобы новые операционные модули (финансы, маркетинг, ИИ-инструменты) подключались аддитивно, не трогая уже работающие.
- Не нарушить ни один принцип, уже зафиксированный в `docs/architecture/ARCHITECTURE_PRINCIPLES.md`.

## 2. Архитектурная философия

Административная платформа не вводит новую архитектуру — она **встраивается** в уже существующую Ports & Adapters платформу («Местный Базар» уже прошёл Stage 1–6 миграции, см. `docs/architecture.md`) и наследует её ограничения без исключений.

Философия строится на принципах, уже принятых и задокументированных в проекте (полный текст и обоснование — `docs/architecture/ARCHITECTURE_PRINCIPLES.md`):

| Принцип | Как проявляется в Административной платформе |
|---|---|
| **Server is Source of Truth** | Ни один модуль Административной платформы не хранит бизнес-состояние в браузере дольше, чем требуется для рендеринга. Решения («можно/нельзя», остатки, статусы) всегда пересчитываются на сервере при каждом запросе — ровно так же, как уже сделано для окна отмены заказа (см. `orders.md`) и для цены товара в корзине (`CartService.validate()`, признано принципом CD-01). |
| **Ports & Adapters** | Каждый новый модуль Административной платформы (finance, marketing, ai и т.д.) — это новый домен-сервис в `server/domain/`, обращающийся к внешним системам только через порты. Административная платформа не создаёт исключений из этого правила ради скорости разработки. |
| **Rule Engine** | Любая логика вида «можно / нельзя» (права доступа, лимиты скидок, условия автопополнения склада, критерии выбора курьера) реализуется тем же стандартом `order → applies → evaluate → terminal` (Принцип 12), что уже используют `PaymentPolicyService`, `OrderLifecycleService`, `ProductPublicationService`. Новый Policy-модуль — это новый rule chain, а не `if`-цепочка в сервисе. |
| **Browser First** | Административная платформа — веб-приложение (включая PWA для курьеров), без нативных мобильных сборок. Работает в любом современном браузере, без установки, без App Store/Google Play зависимости. |
| **Независимость от операционной системы** | Прямое следствие «Browser First» — ни один функционал Административной платформы не должен требовать конкретной ОС ни на клиенте, ни на сервере (сервер уже работает на Cloudflare Workers — платформо-независимая среда выполнения). |
| **Минимальное участие разработчика** | См. раздел 1. Операционные изменения (цены, акции, тексты, категории, лимиты) — через UI и конфигурацию, не через деплой. |
| **Управление магазином без изменения кода** | То же самое, сформулировано как ограничение на реализацию: если для типового операционного действия требуется правка `.ts`-файла — модуль спроектирован неверно. |
| **Возможность масштабирования** | Административная платформа проектируется для объёма, заявленного в `docs/architecture.md` (Stage 10: 10k+ заказов/день) — то есть без синхронных полных пересчётов на каждый чих и без хранения оперативных данных вне БД. |
| **Возможность подключения новых модулей** | Новый раздел Административной платформы = новый пункт навигации + новый домен-сервис + (при необходимости) новые порты. Существующие модули не переписываются под новый (см. `ARCHITECTURE_POLICY.md`, принцип «Extend, Never Replace», уже зафиксированный в проекте под POL-14). |
| **Возможность создания новых PWA внутри проекта** | Курьерское приложение — первый пример: отдельная PWA-точка входа поверх общего backend и общей авторизации (детали — `couriers.md`). Административная платформа должна проектироваться так, чтобы этот паттерн повторялся (например, будущее PWA для продавцов) без дублирования домена. |
| **Единая база данных** | Один Supabase Postgres-проект на всё: customer storefront, Административная платформа, курьерская PWA. Никаких отдельных БД под новые модули. |
| **Единая авторизация** | Один Supabase Auth, одна таблица `user_roles`, один механизм проверки роли (`require<Role>FromRequest()` в `server/auth/resolve-user.ts`) — Административная платформа не вводит второй auth-контур. |
| **Единая бизнес-логика** | Домен-сервисы Административной платформы — это те же классы в `server/domain/`, что уже обслуживают customer-facing API, где это применимо (пример: `OrderLifecycleService` уже обслуживает и покупателя, и админа, и склад, и курьера — единой цепочкой правил, разными `reason`). Новый код не дублирует уже существующие правила. |

## 3. Общая схема платформы

```
                         ┌───────────────────────────────────┐
                         │         Supabase (единая БД)       │
                         │   Postgres · Auth · Storage · RLS  │
                         └──────────────────┬──────────────────┘
                                            │
                         ┌──────────────────┴──────────────────┐
                         │      server/  (Ports & Adapters)     │
                         │  Domain services · Rule Engines ·    │
                         │  Repositories · Composition Root     │
                         └──────────────────┬──────────────────┘
                                            │ src/api/ (единственный мост)
        ┌──────────────────┬───────────────┼───────────────┬──────────────────┐
        │                  │               │               │                  │
 ┌──────┴──────┐   ┌───────┴──────┐  ┌─────┴──────┐  ┌─────┴──────┐   ┌───────┴───────┐
 │  Customer    │   │   Admin      │  │ Warehouse  │  │  Seller    │   │  Courier PWA  │
 │  Storefront  │   │   Platform   │  │  Workspace │  │  Workspace │   │  (отдельная   │
 │  (существует)│   │  (этот      │  │  (внутри   │  │  (внутри   │   │  точка входа, │
 │              │   │   документ) │  │  Admin     │  │  Admin     │   │  см. couriers │
 │              │   │              │  │  Platform) │  │  Platform) │   │  .md)         │
 └──────────────┘   └──────────────┘  └────────────┘  └────────────┘   └───────────────┘
```

Ключевое архитектурное решение: **Warehouse Workspace и Seller Workspace — это разделы внутри Административной платформы** (общий UI-каркас, общая навигация, разграничение по ролям), а **Courier — отдельное PWA-приложение** поверх того же backend. Это не произвольный выбор, а уже принятое решение (см. `couriers.md`): курьер работает «в поле», ему нужен отдельный, максимально лёгкий, устанавливаемый на экран телефона интерфейс — тогда как склад и продавец работают за рабочим местом и укладываются в общий административный каркас без потери удобства.

Верхнеуровневая навигация Административной платформы (порядок — по частоте использования в операционной работе, не финальный, уточняется в `dashboard.md`):

```
Административная платформа
├── Dashboard            (см. dashboard.md)
├── Заказы               (см. orders.md)
├── Каталог              (см. catalog.md)
├── Склад                (см. warehouse.md)
├── Продавцы             (см. sellers.md)
├── Поставщики           (см. suppliers.md)
├── Покупатели           (см. users.md)
├── Курьеры              (см. couriers.md — управление, не сама PWA)
├── Доставка             (см. ../delivery/DELIVERY_MASTER_SPEC.md — отдельный модуль,
│                          Delivery Management & Pricing: зоны, тарифы, коэффициенты)
├── Аналитика            (см. analytics.md)
├── Финансы              (см. finance.md)
├── Маркетинг            (см. marketing.md)
├── ИИ-инструменты       (см. ai.md)
├── Интеграции           (см. integrations.md)
├── Автоматизация        (см. automation.md)
├── Оформление           (см. design.md)
├── Настройки            (см. settings.md)
├── Права доступа        (см. permissions.md)
├── Журналы событий      (см. logs.md)
└── Безопасность         (см. security.md)
```

Видимость каждого пункта навигации определяется матрицей доступа (раздел 8) — пользователь с ролью `seller` не увидит «Финансы» или «Права доступа», это не вопрос UI-скрытия, а вопрос того, что соответствующий server function изначально требует другую роль (см. `permissions.md`).

## 6. Взаимосвязь модулей

Модули не равноправны — часть из них **владеет** данными, часть **потребляет** чужие данные через события или прямые запросы. Полная схема зависимостей уточняется в документе каждого модуля; здесь фиксируется только направление владения, чтобы ни один специализированный документ не спроектировал модуль так, будто он владеет чужими данными.

```
Каталог ──owns──> Товары, Категории
Продавцы ──owns──> Товары продавца (через Каталог, Rule Engine публикации)
Поставщики ──owns──> Поставки, закупочные цены  (новый домен)
Склад ──owns──> Остатки, резервирование  (частично: резерв уже владеет Checkout)
Заказы ──owns──> Заказ, статус, позиции заказа
Курьеры ──owns──> Доставку конкретного заказа (после устранения пробела §9)
Доставка ──owns──> Зоны, тарифы, коэффициенты (docs/delivery/); ──produces──> стоимость/ETA, которые Заказы применяют через DeliveryPricingEngine (не напрямую)
Покупатели ──owns──> Профиль, адреса
Финансы ──consumes──> Заказы, Оплаты (read-only агрегация, не пишет в Заказы)
Аналитика ──consumes──> Заказы, Каталог, Покупатели, Курьеры (read-only)
Маркетинг ──consumes──> Каталог, Покупатели; ──produces──> купоны/акции, которые Заказы применяют через Rule Engine (не напрямую)
Автоматизация ──observes──> события всех модулей (через IMarketplaceEventBus), не владеет ничьими данными
ИИ ──observes──> события Каталога/Товаров, ──produces──> оценки качества (сегодня никем не потребляются — открытый вопрос, см. `ai.md`)
Права доступа ──governs──> доступ ко всем остальным модулям, сама не хранит бизнес-данные, кроме ролей
Настройки ──governs──> конфигурацию всех остальных модулей
Журналы ──observes──> события всех модулей, только для чтения
Безопасность ──governs──> весь периметр, не является отдельным «разделом с данными»
```

Правило, вытекающее из этой схемы: **модуль-потребитель никогда не пишет напрямую в таблицы модуля-владельца.** Финансы не меняют статус заказа; Маркетинг не меняет цену товара напрямую — он создаёт правило, которое Rule Engine применяет при расчёте цены. Это прямое расширение уже принятого в проекте запрета «hardcode бизнес-правил» на уровень межмодульного взаимодействия.

## 7. Роли пользователей

Административная платформа не вводит новых ролей аутентификации сверх уже существующих в `shared/contracts/user.ts` (`UserRole = "admin" | "customer" | "warehouse" | "courier" | "seller"`), но вводит **более тонкое разграничение прав внутри роли `admin`** — это необходимо, потому что сегодня роль `admin` в коде означает «может всё», а Административная платформа явно требует разделения (финансист не должен видеть управление правами, маркетолог не должен видеть финансовые отчёты).

| Роль | Уже существует в коде | Использует Административную платформу | Использует отдельную PWA |
|---|---|---|---|
| **Admin** (полный доступ) | Да | Да — весь охват | — |
| **Admin-Finance** (предлагается) | Нет | Да — только Финансы, Аналитика (read-only) | — |
| **Admin-Marketing** (предлагается) | Нет | Да — только Маркетинг, Оформление, Аналитика (read-only) | — |
| **Warehouse** | Да | Да — только Склад, очередь сборки заказов | — |
| **Seller** | Да | Да — только свои товары, свои заказы (частично) | — |
| **Courier** | Да | Нет (курьер не заходит в Административную платформу) | Да — отдельная PWA |
| **Customer** | Да | Нет | Нет |

Подробная матрица «роль × действие» — раздел 8 и полностью в `permissions.md`. Введение под-ролей admin (Finance/Marketing) — это архитектурное **предложение**, требующее продуктового решения (см. Открытые вопросы, раздел 12) прежде чем становиться ADR.

## 9. Основные бизнес-процессы

Ниже — процессы, критичные для понимания масштаба платформы, с явной фиксацией того, что уже решено архитектурно, а что — обнаруженный в ходе аудита пробел.

### 9.1 Жизненный цикл заказа (уже реализовано)
`CREATED → PAID → CONFIRMED → ASSEMBLING → READY_FOR_DELIVERY → OUT_FOR_DELIVERY → ARRIVED → DELIVERED`, с веткой в `CANCELLED` с разных точек. Полностью управляется `OrderLifecycleService` (Rule Engine, 10 правил). **Буфер отмены заказа покупателем — 2 минуты после создания, серверная проверка по `order.created_at`, уже реализовано и задокументировано отдельно в `orders.md` как принятое архитектурное решение** (не подлежит пересмотру в рамках Административной платформы).

### 9.2 Публикация товара продавцом (уже реализовано)
`DRAFT → PUBLISHED → HIDDEN` через `ProductPublicationService` (тот же стандарт Rule Engine).

### 9.3 Назначение курьера на доставку (**архитектурный пробел, требует проектирования**)
Ранее принятое решение гласит: курьеры не закреплены за районами, система автоматически подбирает наиболее подходящего курьера. Аудит подтвердил: в текущей модели данных **нет поля, связывающего заказ с конкретным курьером** (`OrderDTO` не содержит `courierId`), а `CourierOrderService.acceptOrder()` не сохраняет никакого состояния — по факту сегодня это общая очередь заказов в статусах `READY_FOR_DELIVERY`/`ASSEMBLING`/`OUT_FOR_DELIVERY`/`ARRIVED`, которую видят все курьеры одновременно. Это единственный пункт данного документа, где «основной бизнес-процесс» не является описанием реализованного, а является **техническим долгом, который должна закрыть Административная платформа** — см. `couriers.md`.

### 9.4 Резервирование и списание склада (частично реализовано)
Атомарное резервирование при оформлении заказа (`reserve_product_stock`) и его восстановление при отмене — уже реализовано (см. `warehouse.md` и `ARCHITECTURE_PRINCIPLES.md`, CD-02). Управление остатками, порогами нехватки, автопополнением — не реализовано, это предмет проектирования `warehouse.md`.

### 9.5 Уведомление операционных ролей о новом заказе (реализовано частично, требует изменения сроков)
`NotificationCenter.dispatch("order.created")` уже сегодня независимо уведомляет admin/warehouse/courier каналы (сейчас — заглушки, `StubNotificationAdapter`), при отказе одного канала остальные не блокируются — этот механизм независимости каналов остаётся без изменений. Изменяется **момент** его срабатывания: сегодня он привязан напрямую к `order.created` (немедленно), а по [`platform-lifecycle.md`](./platform-lifecycle.md), §3, операционное уведомление персонала должно запускаться только по истечении 2-минутного буфера отмены, отдельным, отложенным триггером — не по `order.created` напрямую. См. также `orders.md`, раздел «События».

## 10. Архитектурные ограничения

Ограничения ниже — не рекомендации, а условия, при нарушении которых реализация Административной платформы будет противоречить уже принятой архитектуре проекта (см. `docs/architecture/README.md`, раздел «Когда нельзя менять Architecture Principles»).

1. **Frontend Административной платформы не обращается к Supabase напрямую.** Только через `src/api/` → `server/functions/` (Принцип 1, 8).
2. **Ни один модуль не создаёт адаптер внутри домен-сервиса.** Выбор реализации — только в `server/di/container.ts` (Принцип 3, 5).
3. **Любая логика допуска/запрета — через Rule Engine**, не через условные операторы в оркестраторах (Принцип 12).
4. **Секреты новых интеграций (платёжные, аналитические, маркетинговые SaaS) — только на сервере**, никогда в client bundle (Принцип 7).
5. **Ни один новый модуль не может стать обязательной зависимостью уже работающего ядра** (заказы, каталог, склад, checkout) — если выключить Финансы или Маркетинг, магазин обязан продолжать полностью работать (прямое применение `ARCHITECTURE_POLICY.md`, принцип независимости модулей, POL-04).
6. **Единая база данных, единая авторизация, единый backend** — ни один модуль не заводит свой Supabase-проект, свою таблицу пользователей или свой сервер.
7. **Курьерская PWA — самостоятельная точка входа, но не самостоятельный backend.** Общий домен, общие правила, общая БД (см. §3).
8. **Изменение окна отмены заказа, правил публикации товара, правил жизненного цикла заказа — это ADR-уровня решение**, а не настройка Административной платформы, до тех пор пока в проекте нет отдельного, явного решения вынести эти пороги в конфигурацию (см. открытый вопрос §12 и `orders.md`).
9. **Ничего из перечисленного в этом документе не реализовано в коде.** Это спецификация, а не отчёт о готовой системе — см. запрет в промпте «не приступай к разработке».

## 11. Правила расширения платформы

1. Новый модуль = новый файл `docs/admin-platform/<module>.md`, добавленный в разделы 5 и 6 этого документа, плюс пункт навигации (раздел 4).
2. Новый модуль не имеет права **владеть** данными существующего модуля — только читать через порт/событие или создавать собственные данные, на которые существующие модули реагируют через `IMarketplaceEventBus`, не наоборот.
3. Новая роль или под-роль — решение уровня ADR (влияет на модель прав доступа платформы целиком), не решение уровня отдельного модуля.
4. Любое новое разрешаемое/запрещаемое действие добавляется как новое правило в соответствующий Rule Engine (Payment Policy, Order Lifecycle, Product Publication, будущий Permission Policy) — никогда как встроенная проверка в UI-компоненте.
5. Каждый этап реализации (см. `implementation-roadmap.md`) должен оставлять систему в полностью рабочем состоянии — Административная платформа строится инкрементально, поверх работающего маркетплейса, никогда не в отдельной ветке, блокирующей продакшн (тот же принцип, что уже применялся при миграции на Ports & Adapters, `docs/stage-1-checklist.md`).

1. Нужны ли под-роли `admin-finance`/`admin-marketing` (раздел 7), или на первом этапе достаточно единой роли `admin` без внутреннего разграничения?
