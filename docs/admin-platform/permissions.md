**Модуль:** Права доступа
**Статус в коде:** частично существует — роли (`UserRole`), проверка через `require<Role>FromRequest()` в `server/auth/resolve-user.ts`, разграничение по таблице `user_roles`. UI управления правами, под-роли внутри `admin`, гранулярные разрешения на уровне действия — не существуют.
**Роли с доступом:** Admin (единственная роль, имеющая доступ к этому модулю — управление правами не делегируется)

> Этот документ описывает исключительно модель ролей, прав и матрицу доступа. Конкретные права по каждому модулю уже частично зафиксированы в разделах «Права доступа» соответствующих документов (`orders.md`, `catalog.md` и т.д.) — здесь описывается **механизм**, которым эти права проверяются и настраиваются, единообразно для всей платформы.

## Назначение

Дать администратору единую точку управления тем, кто и что может делать на платформе, и дать инженерной части платформы единый, не дублируемый по модулям механизм проверки этих прав.

## Уже существующая модель (не переизобретается)

```
auth.users (Supabase Auth)
    │
    ▼
user_roles (user_id, role)  — role ∈ {admin, customer, warehouse, courier, seller}
    │
    ▼
requireAdminFromRequest() / requireWarehouseFromRequest() / requireCourierFromRequest() / requireSellerFromRequest()
    │  (server/auth/resolve-user.ts — единая точка проверки JWT + роли)
    ▼
Каждый executor (admin.executor.ts, warehouse.executor.ts, ...) вызывает нужную require-функцию
```

Это уже единообразный, не дублированный механизм: проверка роли происходит **до** вызова доменного сервиса, никогда не внутри UI-компонента, и всегда с сервера (JWT проверяется, роль читается из БД — Принцип «Server is Source of Truth» уже применён здесь без исключений).

## Обнаруженный пробел

Модель сегодня — **грубая** (одна роль = все права этой роли, без исключений). Роль `admin` в текущем коде означает «может абсолютно всё в разделе заказов» — нет механизма дать одному администратору доступ только к финансам, а другому — только к маркетингу, что явно требуется мастер-спецификацией (раздел 7, под-роли `admin-finance`/`admin-marketing`).

## Предлагаемая архитектура: Permission Policy как Rule Engine

Соответствие уже принятому в проекте стандарту (Принцип 12, `docs/principles/12-rule-engine-standard.md`) — модель прав реализуется **тем же способом**, что `PaymentPolicyService`/`OrderLifecycleService`/`ProductPublicationService`, не отдельным, специфичным для прав механизмом:

```
IPermissionPolicy { can(context): PermissionResult; assert(context): void }

PermissionContext { actor: { id, roles }, module: string, action: string }

PermissionPolicyService (rule chain):
  - AdminFullAccessRule        (order: 10, terminal: true — admin имеет доступ, если нет более специфичного запрета)
  - AdminFinanceScopeRule      (order: 20 — ограничивает under-роль admin-finance конкретными модулями)
  - AdminMarketingScopeRule    (order: 20)
  - WarehouseScopeRule         (order: 30 — доступ только к warehouse/orders(очередь сборки))
  - SellerOwnDataOnlyRule      (order: 30 — доступ только к своим товарам/заказам)
```

Это не заменяет уже существующие `require<Role>FromRequest()` — они остаются первой линией (есть ли вообще валидный пользователь с такой ролью), а `PermissionPolicyService` добавляет вторую линию (что именно этой роли/под-роли разрешено внутри Административной платформы), по аналогии с тем, как в `OrderLifecycleService` есть и `TerminalStateGuardRule` (общий guard), и специфичные ролевые правила.

## Под-роли: механизм, не решение

Под-роли `admin-finance`/`admin-marketing` (мастер-спецификация, раздел 7) — это **продуктовое** решение (нужны ли они вообще на первом этапе), но если оно принято, механически они реализуются **не** как новые значения в `UserRole` (это сломало бы все существующие проверки `roles.includes("admin")` по всей кодовой базе), а как дополнительный, более гранулярный признак поверх существующей роли `admin` — например, отдельная таблица `admin_scopes (user_id, scope)`, которую читает только `PermissionPolicyService`, не трогая существующий механизм `user_roles`/`UserRole`.

## Матрица разрешений

Полная матрица «роль × модуль × действие» строится из таблиц «Права доступа», уже зафиксированных в каждом специализированном документе (`orders.md`, `catalog.md`, `warehouse.md`, `couriers.md`, `sellers.md`, `analytics.md`, `finance.md`, `marketing.md`, `design.md`, `settings.md`, `automation.md`, `integrations.md`, `ai.md`, `security.md`, `logs.md`, `dashboard.md`) — сводная версия уже приведена в `ADMIN_PLATFORM_MASTER_SPEC.md`, раздел 8. Этот документ не дублирует таблицу, а фиксирует, что она должна оставаться единственной сводной точкой (изменения матрицы вносятся в мастер-спецификацию, детали реализации — здесь).

## Права доступа к самому модулю

Только Admin. Управление правами не делегируется ни одной под-роли — иначе под-роль потенциально может выдать себе более широкие права, что является классической уязвимостью privilege escalation (см. также `security.md`).

## Будущие расширения

- Гранулярные права на уровне отдельной сущности (не «продавцы», а конкретный продавец, для делегированного модератора) — не заложено, не требуется на первом этапе.
- Временные/истекающие права (доступ на ограниченный срок).
