> Этот документ описывает исключительно настройки платформы как таковые — где они хранятся, кто их меняет, как они попадают в работающую систему. Конкретное содержимое настроек, специфичное для модуля (правила скидок — `marketing.md`, пороги склада — `warehouse.md`, права — `permissions.md`), описывается в документе соответствующего модуля; здесь — только сам механизм.

## Назначение

**Главная и единственная цель этого модуля сформулирована явно:** все изменения в работе магазина должны быть возможны без участия разработчика. Настройки — это модуль, который технически это обеспечивает: он превращает то, что сегодня является правкой кода и деплоем, в правку данных через интерфейс.

## Текущее состояние (аудит)

Сегодня «настройки» платформы — это исключительно `server/config/env.ts`: Zod-схема, валидируемая один раз при старте процесса (`getServerEnv()`, с кэшированием на весь жизненный цикл процесса — значение не может измениться без перезапуска). Все текущие «настраиваемые» параметры на самом деле являются **флагами уровня разработчика**, а не настройками уровня бизнеса:

| Параметр | Что это сегодня |
|---|---|
| Пороги (окно отмены заказа — 2 минуты) | Константа в коде (`CUSTOMER_CANCELLATION_WINDOW_MS`, `shared/lib/order-cancellation.ts`) |
| Тексты/названия категорий на кыргызском | Хардкод (`KG_NAME_BY_SLUG` в `src/routes/index.tsx`) |
| Изображения категорий (fallback) | Хардкод (`FALLBACK_IMAGE_BY_SLUG`) |

Это ровно то состояние, которое модуль Настройки обязан устранить — не как абстрактная цель, а как список конкретных, уже найденных при аудите хардкодов.

## Архитектурная модель настроек

Настройки должны храниться в БД (новая таблица, например `platform_settings: key, value (jsonb), category, updatedBy, updatedAt`), читаться доменными сервисами через новый порт (`ISettingsRepository`), не через `process.env`. Это разделяет два разных класса конфигурации, которые сегодня ошибочно смешаны в одном `server/config/env.ts`:

| Класс конфигурации | Где хранится | Кто меняет | Пример |
|---|---|---|---|
| **Секреты и инфраструктура** (API-ключи, URL БД) | Переменные окружения (как сегодня) | Разработчик/DevOps | `SUPABASE_SERVICE_ROLE_KEY`, `FINIK_API_KEY` |
| **Бизнес-настройки** (новое) | БД, `platform_settings` | Admin через UI | Пороги, тексты, лимиты, включение/выключение фич продавцами |

Это разделение — не создание нового исключения из Принципа 7 (Server-Only Secrets), а его уточнение: секреты остаются server-only переменными окружения, бизнес-настройки — данными в БД, доступными только через сервер (не напрямую из браузера — тот же Ports & Adapters, что и везде).

## Предполагаемая структура

```
Настройки
├── Общие (название магазина, контакты, часовой пояс)
├── Каталог (правила публикации по умолчанию)
├── Заказы (пороги, лимиты — с явным предупреждением там, где параметр требует ADR, см. ниже)
├── Доставка (зоны, стоимость — уже частично в БД, delivery_zones, не требует нового механизма)
├── Уведомления (какие каналы включены)
└── Feature flags (то, что сегодня в .env, — с осторожным переносом, см. «Ограничения»)
```

## Ограничения

1. **Не каждый параметр кода имеет право стать настройкой.** Порог окна отмены заказа (2 минуты) — уже принятое архитектурное решение (`orders.md`), и модуль Настройки **не должен** автоматически делать его редактируемым полем без отдельного ADR, разрешающего именно это (см. `docs/principles/14-architecture-decision-record.md` — изменение бизнес-правила такого уровня требует ADR, а не просто UI-поля). Настройки — это механизм для конфигурации, которая **уже признана** конфигурируемой; он не отменяет необходимость архитектурного решения о том, что можно конфигурировать.
2. ~~Смена `FEATURE_CATALOG_SOURCE`/`FEATURE_CHECKOUT_SOURCE` через UI — высокий риск.~~ Снято: оба флага и Shopify-адаптер, который они переключали, удалены ([ADR-002](../architecture/adr/ADR-002-complete-shopify-catalog-migration.md)) — `SupabaseProductRepository` единственный источник каталога, переключать больше нечего.
3. Домен-сервисы **не читают настройки напрямую из репозитория настроек в произвольном месте** — по аналогии с уже действующим правилом «domain не читает `env` напрямую» (Принцип 11: «Domain service не читает env напрямую» — выбор передаётся через Composition Root). Тот же принцип распространяется на бизнес-настройки: они внедряются в сервис при сборке в `server/di/container.ts`, а не читаются сервисом самостоятельно в произвольной точке выполнения.

## Будущие расширения

- Версионирование настроек (история изменений, откат) — естественным образом пересекается с `logs.md`.
- Настройки per-продавец (например, свои условия доставки) — не спроектировано, зависит от продуктового решения о степени автономности продавца.
