**Модуль:** Продавцы
**Статус в коде:** частично существует — `SellerProductService`, `ProductPublicationService` (Rule Engine), роль `seller`, `requireSellerFromRequest()`
**Роли с доступом:** Admin (полный доступ ко всем продавцам), Seller (только собственный профиль и товары)

> Этот документ описывает исключительно продавцов как участников платформы (профиль, статус, доступ к их собственному разделу Административной платформы). Управление самими товарами продавца — уже описано в `catalog.md` (продавец пользуется тем же разделом Каталога, что и админ, но в ограниченной по правам версии). Выплаты продавцу — `finance.md`.

## Назначение

Дать администратору обзор продавцов платформы (кто они, сколько товаров, статус верификации) и дать продавцу собственное рабочее пространство внутри Административной платформы, ограниченное его же данными.

## Уже существующая бизнес-логика (не переизобретается)

- **Публикация товара продавцом** — уже полностью реализованный Rule Engine (`ProductPublicationService`): продавец создаёт товар (`DRAFT`), публикует (`PUBLISHED`), скрывает (`HIDDEN`). Прямой переход `DRAFT → HIDDEN` уже запрещён.
- **Изоляция данных продавца** — `SellerProductService.listProducts(userId)`/`getProduct(productId, userId)` уже скопированы по тому же паттерну, что и `AddressService`: продавец физически не может получить чужой товар, потому что запрос всегда включает его `userId`, а не потому что UI это скрывает.
- **Роль** — `seller` в `UserRole`, отдельная от `admin`.

## Обнаруженный пробел

Сегодня **нет сущности «профиль продавца»** отдельно от `ProfileDTO` (общий профиль пользователя) — продавец как бизнес-единица (название магазина, контакты, статус верификации, реквизиты для выплат) нигде не смоделирован. Роль `seller` в `user_roles` говорит только «этот пользователь может управлять товарами», но не хранит ничего о самом продавце как о поставщике товара на маркетплейс.

## Модель данных (предлагается, дополняет существующее)

```
SellerProfile (userId, storeName, contactPhone, verificationStatus: PENDING|VERIFIED|REJECTED, payoutDetails)
```

Не заменяет `ProfileDTO` — дополняет его для пользователей с ролью `seller`, по аналогии с тем, как `AddressDTO` дополняет профиль покупателя, не сливаясь с ним в одну сущность.

## Структура раздела

```
Продавцы
├── Список продавцов (Admin: статус верификации, кол-во товаров, дата регистрации)
├── Карточка продавца
│   ├── Профиль магазина
│   ├── Товары (ссылка в catalog.md, отфильтровано по продавцу)
│   ├── Статистика (заказы с товарами продавца — зависит от orders.md)
│   └── Верификация (Admin: подтвердить/отклонить)
└── Личный кабинет продавца (для роли Seller — тот же UI, ограниченный своими данными)
```

## Бизнес-логика

Верификация продавца (`PENDING → VERIFIED → REJECTED`) — ещё один кандидат на Rule Engine по уже устоявшемуся стандарту (Принцип 12), особенно если критерии верификации со временем усложнятся (документы, минимальный рейтинг и т.д.) — на старте может быть простым явным переходом, спроектированным так, чтобы не потребовалось переписывание при усложнении (тот же принцип совместимости интерфейса, что и в `suppliers.md`).

**Публикация товара непроверенным продавцом** — открытый вопрос: должна ли верификация быть предпосылкой для `SellerPublishRule`, или продавец может публиковать товары до верификации, а верификация влияет только на что-то другое (видимость в поиске, лимиты)? Это продуктовое решение, не инженерное — сегодня `SellerPublishRule` никак не учитывает статус верификации, потому что такого статуса не существует.
