**Место в архитектуре.** Platform Access — детализация элементов, уже перечисленных в `PLATFORM_CORE_ARCHITECTURE.md` §5 («Identity», «Authentication», «Access»), и потребитель домена Platform Ownership (§3 ниже) для вопросов «кто владелец». Это не новый, четвёртый независимый модуль верхнего уровня, а раскрытие механизма, которым Platform Core решает «кто вошёл и в какой Workspace его пустить».

---

## 1. Назначение Platform Access

Platform Access — механизм, который превращает факт «пользователь успешно прошёл вход» в факт «пользователь оказался в правильном Workspace, с правильным набором доступных действий». Это единственное место платформы, отвечающее на вопрос **«куда пользователь должен попасть после входа, и почему именно туда»** — вопрос, который сегодня в репозитории решается неявно и по частям (см. §4, честная оговорка).

---

## 2. Цели Platform Access

1. **Один проход аутентификации на весь визит.** Пользователь не должен повторно подтверждать личность при переходе между Workspace, если его сессия ещё действительна.
2. **Единая точка проверки прав.** Ни один Workspace не решает самостоятельно, пускать пользователя или нет — решение всегда приходит из Platform Core.
3. **Явное, предсказуемое определение Workspace.** После входа пользователь должен попасть туда, где ему действительно есть место, а не туда, откуда он случайно инициировал вход.
4. **Предметная нейтральность.** Platform Access ничего не знает о том, что происходит внутри Workspace после того, как впустил туда пользователя.

---

## 3. Связь Platform Access с Platform Initialization, Platform Core и Platform Ownership

- **С Platform Initialization** — конвейер Role Resolution → Workspace Selection не имеет связи в рантайме с Bootstrap и не имеет смысла до `Bootstrap Completed` (до этого момента нет ни одной роли, ни одного Workspace, доступного для входа, кроме самого экрана Bootstrap) — см. `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §13, §17 (то же правило «нет обратной рантайм-зависимости», применённое здесь). Это не относится к примитиву Identity (§5) — он используется уже во время самой claim-операции Bootstrap (см. `BOOTSTRAP_EXECUTION_FLOW_ARCHITECTURE.md` §14), поскольку принадлежит Platform Core и не переизобретается отдельно ни для Bootstrap, ни для Platform Access — оба используют один и тот же механизм.
- **С Platform Core** — Platform Access физически реализуется внутри Platform Core, используя его же Identity/Access/Authorization-сервисы (см. `PLATFORM_CORE_ARCHITECTURE.md` §5); отдельного, самостоятельного хранилища или механизма проверки прав у Platform Access нет.
- **С Platform Ownership** — Root Owner и Owner (см. `PLATFORM_OWNERSHIP_ARCHITECTURE.md`) — два из перечня ролей, которые Platform Access обязан распознавать при Role Resolution (§6, §9), наравне с Access-ролями Platform Core. Platform Access не подменяет и не дублирует логику Platform Ownership — он только считывает её результат (кто сейчас Root Owner/Owner) как одну из категорий роли пользователя.

---

## 4. Процесс входа пользователя

Вход состоит из двух чётко разделённых шагов, которые Platform Access не смешивает:

1. **Authentication** — подтверждение личности внешним провайдером (Supabase Auth / Google OAuth). Существующий аналог: `src/lib/auth.ts` (`signInWithGoogle`, `getAuthRedirectUrl`) инициирует вход; сам провайдер (Google, затем Supabase) подтверждает личность и выдаёт JWT.
2. **Identity + Role Resolution + Workspace Selection** (см. §5-7) — уже задача Platform Access, выполняется после того, как JWT получен, независимо от того, каким конкретно провайдером аутентификации он был выдан.

**Честная оговорка относительно текущего кода.** Сегодня шаг 2 в этом виде не существует как отдельный, явный этап: каждый Workspace-роут (`src/routes/admin/index.tsx`, `src/routes/seller/profile/index.tsx`, `src/routes/courier/orders/index.tsx` и т.д.) самостоятельно вызывает `useSupabaseSession()` и проверяет `isAuthenticated`, а `redirectTo` при входе вычисляется как «текущая страница» (`getAuthRedirectUrl()`, единая точка после исправления в рамках расследования Промптов №032-033) — то есть пользователь после входа возвращается туда, откуда начал вход, а не на маршрут, определённый его ролью. Единого, централизованного Role Resolution → Workspace Selection шага в коде не существует; настоящий документ описывает целевую архитектуру Platform Access, а не уже реализованный процесс.

---

## 5. Процесс определения личности пользователя (Identity)

Platform Access принимает уже выданный JWT и передаёт его в Identity-сервис Platform Core, который извлекает из него идентификатор пользователя — не проверяет пароль, не взаимодействует с провайдером напрямую, только читает уже подтверждённый токен. Существующий аналог: `resolveUserIdFromRequest()`/`requireUserIdFromRequest()` (`server/auth/resolve-user.ts`) — разбирают `Authorization: Bearer <JWT>` и возвращают `userId` или `null` для гостя.

Identity не определяет роль и не решает, куда пользователя пускать — это исключительно следующий шаг (§6).

---

## 6. Процесс определения активной роли пользователя (Role Resolution)

После того как Identity установила `userId`, Platform Access запрашивает у Platform Core полный список ролей этого пользователя (включая владельческий статус — Root Owner/Owner, из Platform Ownership) и формирует **набор**, а не единственное значение — пользователь может одновременно обладать несколькими ролями (существующий аналог: `resolveRolesForUser()` уже возвращает `UserRole[]`, а не одну роль; `ProfileDTO.roles`/`AdminUserDTO.roles` — массивы; это подтверждено аудитом Промпта №034 §12).

«Активная роль» в контексте одной сессии Workspace — это не переопределение набора ролей пользователя, а лишь то, какая из уже имеющихся ролей используется прямо сейчас для конкретного Workspace, в который пользователь вошёл (см. §7-8) — сам набор ролей при этом не меняется.

---

## 7. Правила выбора Workspace после входа

1. Если у пользователя ровно одна роль, определяющая Workspace (например, только `customer`) — Workspace выбирается однозначно.
2. Если у пользователя несколько ролей, соответствующих разным Workspace (например, `seller` и `courier`) — выбор Workspace явный, выполняется самим пользователем (а не платформой за него), поскольку Platform Access не имеет права угадывать намерение.
3. Root Owner/Owner не имеют собственного отдельного Workspace (см. `PLATFORM_OWNERSHIP_ARCHITECTURE.md` §3-4) — их владельческие полномочия проявляются внутри Administration Workspace, куда они попадают наравне с Administrator, если такая роль у них также назначена, либо через отдельный, специально предусмотренный раздел управления владением внутри той же Administration Workspace.
4. Если ни одна роль пользователя не соответствует ни одному Workspace — доступ в любой Workspace отклоняется (см. Обязательный инвариант «пользователь не может попасть в Workspace, если соответствующая роль отсутствует»); единственный доступный пользователю Workspace в этом случае — Customer (роль, автоматически выдаваемая при регистрации, см. `PLATFORM_INITIALIZATION_ARCHITECTURE.md` — существующий аналог: триггер `handle_new_user()`, зафиксированный в аудите Промпта №034 §2).

---

## 8. Правила переключения между Workspace

- Переключение между Workspace не требует повторной Authentication — уже установленная Identity и уже вычисленный набор ролей переиспользуются (см. цель №1, §2).
- Переключение — это повторный проход через Role Resolution → Workspace Selection с уже известным набором ролей, не через вход заново.
- Переключение в Workspace, роль для которого отсутствует, запрещено на общих основаниях (§7, п.4) — переключение не является отдельным, более мягким путём обхода проверки роли.

---

## 9. Архитектура ролей

| Роль | Домен | Workspace | Связь с Access |
|---|---|---|---|
| **Root Owner** | Platform Ownership | Не имеет собственного; действует внутри Administration Workspace | Распознаётся Role Resolution как владельческий статус, не как обычная Access-роль (см. `PLATFORM_OWNERSHIP_ARCHITECTURE.md` §3) |
| **Owner** | Platform Ownership | Не имеет собственного; действует внутри Administration Workspace | Аналогично Root Owner (см. `PLATFORM_OWNERSHIP_ARCHITECTURE.md` §4) |
| **Administrator** | Platform Core (Access) | Administration Workspace | Существующий аналог — роль `admin`, guard `requireAdminFromRequest()` |
| **Seller** | Platform Core (Access) | Seller Workspace | Существующий аналог — роль `seller`, guard `requireSellerFromRequest()`, один-к-одному с `seller_profiles` (аудит Промпта №034 §11) |
| **Courier** | Platform Core (Access) | Courier Workspace | Существующий аналог — роль `courier`, guard `requireCourierFromRequest()` |
| **Warehouse** | Platform Core (Access) | Warehouse Workspace | Существующий аналог — роль `warehouse`, guard `requireWarehouseFromRequest()` |
| **Customer** | Platform Core (Access) | Customer Workspace | Существующий аналог — роль `customer`, назначается автоматически при регистрации |

Важное структурное отличие: Root Owner/Owner — роли домена Platform Ownership, не хранящиеся в той же таблице/механизме, что Access-роли (см. `PLATFORM_OWNERSHIP_ARCHITECTURE.md`, а также `PLATFORM_CORE_ARCHITECTURE.md` §5 — Ownership отделён от Access как отдельная строка перечня). Все остальные пять ролей — Access-роли Platform Core в существующем сегодня смысле (`user_roles`, аудит Промпта №034 §2).

---

## 10. Правила доступа пользователей

1. Доступ в Workspace определяется исключительно набором ролей, полученным от Platform Core — ни один Workspace не хранит и не проверяет собственную копию этого набора.
2. Проверка доступа выполняется дважды, на двух независимых рубежах (существующий, уже подтверждённый аудитом паттерн — Промпт №034 §6-8): грубый рубеж (Access — «есть ли вообще роль для входа в этот Workspace», аналог `require<Role>FromRequest()`) и тонкий рубеж (Authorization — «разрешено ли это конкретное действие внутри Workspace», аналог `PermissionPolicyService`/Rule Engine).
3. Гостевой доступ (без аутентификации) допускается там, где это отдельно предусмотрено конкретным Workspace (существующий аналог — гостевой чекаут, `resolveUserIdFromRequest()` возвращает `null`, не ошибку, см. `ARCHITECTURE_PRINCIPLES.md` CD-07) — Platform Access не запрещает этот случай, а передаёт `userId = null` дальше, оставляя решение о том, разрешён ли гостевой сценарий, самому Workspace.

---

## 11. Ограничения доступа

- Platform Access не выдаёт прав «по умолчанию» ни для одного Workspace, кроме Customer (единственная автоматически назначаемая роль).
- Platform Access не может расширить набор ролей пользователя самостоятельно — расширение ролей происходит только через Platform Core (назначение роли Root Owner/Owner/Administrator и т.д.) или Platform Ownership, никогда как побочный эффект самого входа или переключения Workspace.
- Истёкшая/отозванная сессия — немедленное отсутствие доступа во все Workspace одновременно, без частичного «доступ остался в одном Workspace, но не в другом» — поскольку Identity общая для всех Workspace (§3).

---

## 12. Принципы авторизации

1. **Access прежде Authorization.** Сначала грубая проверка «есть ли роль вообще», затем — если требуется — тонкая проверка конкретного действия (см. §10, п.2).
2. **Отказ по умолчанию.** Если ни одно правило Access/Authorization явно не разрешило действие — доступ запрещён (существующий аналог: `PermissionPolicyService` при отсутствии совпавшего правила отклоняет с `NO_MATCHING_RULE`, аудит Промпта №034 §6).
3. **Проверка на сервере, не на клиенте.** Клиентское состояние (`isAuthenticated` в UI) — удобство интерфейса, не источник истины; фактическая проверка всегда происходит на стороне Platform Core при каждом запросе, независимо от того, что показывает интерфейс.
4. **Роль не подразумевает Workspace автоматически там, где выбор неоднозначен.** См. §7, п.2 — платформа не решает за пользователя, если у него несколько применимых ролей.

---

## 13. Диаграмма

```
                              User
                               │
                               ▼
                        Authentication
              (Supabase Auth / Google OAuth —
               внешний провайдер подтверждает личность)
                               │
                               ▼
                            Identity
                (Platform Core: userId извлечён из JWT)
                               │
                               ▼
                        Platform Access
             (принимает Identity, запрашивает роли
              и владельческий статус у Platform Core
              и Platform Ownership)
                               │
                               ▼
                        Role Resolution
              (полный набор ролей пользователя —
               Access-роли + Root Owner/Owner статус)
                               │
                               ▼
                      Workspace Selection
             (однозначно, если роль одна;
              явный выбор пользователя, если ролей
              несколько; отказ, если ролей нет)
                               │
                               ▼
                           Workspace
        (Customer / Seller / Courier / Warehouse /
         Administration — точка, где Platform Access
         заканчивает свою ответственность)
```

## 14. Architecture Invariants Platform Access

- ❌ Пользователь не проходит Authentication более одного раза за время действия одной сессии — переключение Workspace не запускает вход заново (см. §8).
- ❌ Ни один Workspace самостоятельно не определяет права пользователя — единственный источник решения «что разрешено» — Platform Core.
- ❌ Все проверки доступа выполняются через Platform Core — не существует локальной, независимой проверки прав внутри кода конкретного Workspace.
- ❌ Platform Access не содержит бизнес-логики Workspace — ничего в нём не зависит от того, что такое заказ, товар, доставка или склад.
- ❌ Пользователь не может попасть в Workspace, если соответствующая роль отсутствует — ни через прямой переход по ссылке, ни через переключение, ни через любой иной путь в обход Role Resolution.
- ❌ Platform Access не может присваивать роли самостоятельно — присвоение ролей принадлежит исключительно Platform Core/Platform Ownership (см. §11).
- ❌ Root Owner/Owner не могут быть перепутаны с Access-ролями внутри Role Resolution — их источник данных и механизм проверки остаются отдельными (см. §3, §9), даже если конечная точка входа для них — тот же Administration Workspace.

---

## 15. Принципы безопасности Platform Access

1. **Единственный источник истины о ролях — сервер.** Клиентский `isAuthenticated`/локально закэшированный список ролей — не более чем отражение серверного состояния для UI, никогда не используется как основание для фактической проверки доступа.
2. **Свежесть проверки при каждом чувствительном действии.** Роль пользователя проверяется заново на каждый запрос, требующий Access/Authorization — не кэшируется на весь визит без возможности отозвать доступ немедленно.
3. **Явный отказ вместо неявного пропуска.** Отсутствие совпавшего правила или роли всегда трактуется как запрет, никогда как разрешение (см. §12, п.2).
4. **Единая точка отзыва.** Поскольку Identity и набор ролей общие для всех Workspace, отзыв роли или блокировка пользователя на уровне Platform Core немедленно и одновременно закрывает доступ во все Workspace — не требует отдельного действия для каждого Workspace по отдельности.
5. **Разделение грубой и тонкой проверки снижает поверхность ошибки.** Ошибка в тонком, предметно-специфичном Authorization-правиле одного Workspace не может по своей природе выдать доступ в другой Workspace — вход в сам Workspace уже прошёл независимый, более грубый Access-барьер раньше.
