Этот документ не вводит новых состояний или сущностей сверх уже утверждённых. Состояния Bootstrap (`ELIGIBLE`/`CLAIMING`/`COMPLETED`) взяты дословно из `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §3-4; сущности — из `BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md`. Ниже — то, как именно система проходит эти состояния на практике: что происходит в момент запроса, что происходит при сбое, и почему завершение необратимо технически, а не только по соглашению.

---

## 1. Назначение Bootstrap Execution Flow

`PLATFORM_INITIALIZATION_ARCHITECTURE.md` определил, **какие** состояния существуют. `BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md` определил, **какие данные** эти состояния отражают. Этот документ определяет **как именно** система проходит от первого открытия платформы (`Not Initialized`) до необратимого `COMPLETED` — включая то, что происходит, когда что-то идёт не так, и почему повторный запрос после успеха не может тайно создать второго «первого» Root Owner.

---

## 2. Полный жизненный цикл Bootstrap

```
1. Платформа развёрнута впервые.
   Записей владения — ноль. Bootstrap State = ELIGIBLE.

2. Пользователь открывает платформу.
   Platform Access (см. PLATFORM_ACCESS_ARCHITECTURE.md) видит: Root Owner
   не существует → показывается экран Bootstrap, а не обычный вход
   в Workspace.

3. Пользователь проходит Authentication (Google OAuth/Supabase Auth —
   уже существующий, не Bootstrap-специфичный механизм).

4. Пользователь инициирует claim — единственное действие, доступное
   на экране Bootstrap.

5. Система атомарно проверяет "Root Owner всё ещё 0?" и, если да,
   создаёт первую запись владения (ROOT_OWNER) для этого пользователя.

6. Успех → Bootstrap State становится COMPLETED (необратимо).
   Публикуется событие system.bootstrap.completed.

7. Неудача (см. §6-7) → состояние остаётся ELIGIBLE, ничего не создано,
   пользователь может повторить попытку.

8. С момента COMPLETED экран Bootstrap для всех последующих запросов
   недоступен навсегда — Platform Access отправляет всех в обычный
   процесс входа в Workspace.
```

---

## 3. Все состояния Bootstrap

Совпадают дословно с `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §3 — не переопределяются здесь заново, только используются:

| Состояние | Наблюдаемо между запросами? |
|---|---|
| `ELIGIBLE` | Да — постоянное состояние, пока не выполнен успешный claim |
| `CLAIMING` | Нет — существует только внутри одной атомарной операции (см. `BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md` §7, §11); ни один читающий запрос не может «застать» систему в этом состоянии |
| `COMPLETED` | Да — постоянное, необратимое состояние после первого успеха |

---

## 4. Условия перехода между состояниями

- **`ELIGIBLE → CLAIMING`**: получен запрос claim от аутентифицированного пользователя. Условие входа: Identity уже установлена (Platform Access, `PLATFORM_ACCESS_ARCHITECTURE.md` §5) — Bootstrap не выполняет собственную Authentication, использует уже пройденную.
- **`CLAIMING → COMPLETED`**: атомарная проверка «записей `ROOT_OWNER` = 0» подтверждена **и** запись создана **в той же неделимой операции** — не как два раздельных шага.
- **`CLAIMING → ELIGIBLE`** (фактически — просто откат, не новое персистентное состояние, см. §3): атомарная операция не завершилась успехом по любой причине (§6) — транзакция откатывается целиком, наблюдаемое состояние снаружи остаётся `ELIGIBLE`, как будто попытки не было.
- **Из `COMPLETED` переходов нет** — ни в `ELIGIBLE`, ни в `CLAIMING`, ни при каких условиях (см. §9).

---

## 5. События, инициирующие переходы

- **Единственное внешнее событие, способное сдвинуть Bootstrap State** — запрос claim, инициированный человеком через экран Bootstrap. Никакой фоновой задачи, таймера или автоматического перехода не существует и не предусмотрено — переход `ELIGIBLE → CLAIMING → COMPLETED` целиком управляется действием пользователя.
- Успешное завершение claim само публикует ровно одно **внутреннее** событие платформы — `system.bootstrap.completed` (Marketplace Events, уже существующий механизм — `server/ports/marketplace-events.port.ts`) — это событие является следствием перехода, не его причиной.
- Неудачная попытка **не публикует никакого события** — событие в этой архитектуре обозначает состоявшийся факт, а не попытку (согласуется с уже принятым в проекте паттерном: `role.assigned`/`role.revoked` и подобные события публикуются только доменным сервисом после успешного применения операции, не при отклонении).

---

## 6. Возможные точки отказа

1. **Гонка двух одновременных claim-запросов.** Два пользователя (или два клика одного пользователя) одновременно инициируют claim, пока состояние ещё `ELIGIBLE`.
2. **Сбой инфраструктуры в середине операции.** Обрыв соединения с базой данных между проверкой и записью.
3. **Сессия/Identity недействительна к моменту claim.** Пользователь начал заполнение экрана Bootstrap, но его сессия истекла до отправки запроса.
4. **Попытка claim после `COMPLETED`.** Кто-то (устаревшая вкладка, прямой вызов API, повторный визит) обращается к claim, когда Root Owner уже существует.
5. **Нарушение целостности данных на уровне БД.** Любое ограничение (уникальность, ссылочная целостность — см. `BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md` §8-9) отклоняет запись по причине, не связанной напрямую с состоянием Bootstrap (например, сама User Identity оказалась некорректной).

---

## 7. Поведение системы после каждой ошибки

1. **Гонка двух claim** — ровно один запрос выигрывает атомарную проверку и создаёт запись; второй запрос, выполняющий ту же атомарную проверку чуть позже (или параллельно, в рамках гарантий транзакционного слоя БД), видит уже ненулевое число `ROOT_OWNER`-записей и отклоняется — не создаёт вторую запись и не бросает платформу в противоречивое состояние с двумя «первыми» Root Owner. Это прямое следствие атомарности (см. §11), не отдельная защитная проверка сверху.
2. **Сбой инфраструктуры** — транзакция не подтверждена (no commit) → полный откат → состояние остаётся `ELIGIBLE`, ни частично созданной записи, ни частично изменённого состояния не остаётся. Пользователю возвращается ошибка, повторная попытка доступна немедленно (см. §8).
3. **Недействительная сессия** — запрос отклоняется на уровне Platform Access ещё до того, как достигает claim-логики Bootstrap (тот же общий механизм, что и для любого другого защищённого действия платформы, — не Bootstrap-специфичная обработка).
4. **Попытка claim после `COMPLETED`** — отклоняется той же самой атомарной проверкой «записей `ROOT_OWNER` = 0», которая используется для перехода — это не отдельная ветка кода «если уже завершено», а естественный, постоянный результат одной и той же проверки, однажды ставшей ложной навсегда (согласуется с принятым решением `BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md` §7 — Bootstrap State как вычисляемое, а не отдельно хранимое значение).
5. **Нарушение целостности данных** — операция отклоняется целиком, откат, `ELIGIBLE` сохраняется; конкретная причина возвращается вызывающей стороне как отдельная, отличимая от «Bootstrap уже завершён» ошибка (не должны восприниматься пользователем как один и тот же случай).

---

## 8. Правила повторного запуска

- Любая неудачная попытка claim **не оставляет платформу в промежуточном или испорченном состоянии** — она эквивалентна тому, что попытки не было (см. §7).
- Повторная попытка из `ELIGIBLE` **разрешена немедленно**, без задержки, требуемой архитектурой самой по себе — вопрос ограничения частоты попыток (rate limiting/защита от злоупотреблений) — это отдельная, не входящая в объём этого документа тема реализации/безопасности, не часть модели состояний.
- Повторная попытка **после `COMPLETED` не является «повторным запуском Bootstrap»** в смысле, предусмотренном архитектурой — это просто отклонённый вызов уже закрытой навсегда операции (см. §9).

---

## 9. Правила необратимого завершения Bootstrap

`COMPLETED` необратимо не потому, что где-то стоит флаг «не позволять», а потому что: единственное условие, разрешающее claim, — «записей `ROOT_OWNER` = 0» (`BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md` §7, §11) — и после первого успеха это условие **перестаёт быть истинным навсегда** при нормальной работе домена Platform Ownership (число `ROOT_OWNER`-записей может только расти или оставаться ≥1, но не возвращаться к нулю — инвариант минимума, `PLATFORM_OWNERSHIP_ARCHITECTURE.md` §11, §14). Необратимость Bootstrap — прямое следствие необратимости самого инварианта минимума Root Owner, а не отдельное, независимо поддерживаемое правило.

Не существует административной операции, флага конфигурации или ручного вмешательства, предусмотренного этой архитектурой, которые «переоткрывали» бы Bootstrap. Единственный предусмотренный путь появления дополнительных или замещающих Root Owner после `COMPLETED` — Transfer Root Ownership (`PLATFORM_OWNERSHIP_ARCHITECTURE.md` §7, §12) или Emergency Recovery (`PLATFORM_INITIALIZATION_ARCHITECTURE.md` §13) — оба явно и намеренно отделены от кода/состояния самого Bootstrap.

---

## 10. Архитектура событий Bootstrap

- Используется исключительно уже существующий механизм Marketplace Events (`IMarketplaceEventBus`, `server/ports/marketplace-events.port.ts`) — новой шины или отдельного канала для Bootstrap не создаётся.
- Ровно один новый тип события: `system.bootstrap.completed` — добавляется в уже существующий дискриминированный union типов события (тот же паттерн, что использовался при добавлении событий `delivery.*` — прецедент уже есть в проекте).
- Публикуется ровно один раз за всю жизнь платформы — сразу после (или как часть, в зависимости от решения реализации, см. §11) успешной атомарной операции создания первой записи владения.
- Потребитель — Audit Log, тем же способом, что и все остальные события платформы (существующий подписчик, не новый механизм подписки).
- Неудачные попытки claim не порождают событий (см. §5) — только сам факт успешного, состоявшегося перехода.

---

## 11. Архитектура транзакционности

Claim-операция — единая, неделимая единица работы, состоящая из двух логически связанных шагов, которые обязаны выполняться в одной атомарной операции на уровне базы данных (по образцу уже существующего в проекте паттерна для TOCTOU-чувствительных операций — `ARCHITECTURE_PRINCIPLES.md` CD-02, применённого ранее к резервированию остатков и умолчальному адресу):

1. Проверка: число записей владения со статусом `ROOT_OWNER` равно нулю.
2. Запись: создание новой записи владения со статусом `ROOT_OWNER` для вызывающего пользователя.

Оба шага — одна атомарная операция, а не «сначала SELECT в коде домена, потом отдельный INSERT» — иначе две параллельные попытки claim обе прошли бы шаг 1 до того, как любая из них выполнит шаг 2 (см. §6, точка отказа №1).

Публикация события `system.bootstrap.completed` (§10) происходит **после** подтверждённого (committed) успеха атомарной операции — в этой платформе события уже сегодня публикуются синхронно, в памяти, самим доменным сервисом по факту успешного применения операции (существующий паттерн `UserAdminService`, зафиксированный в аудите Промпта №034 §5) — Bootstrap не отступает от этого паттерна и не вводит альтернативный.

---

## 12. Архитектурные инварианты процесса

- Между `ELIGIBLE` и `COMPLETED` не может существовать наблюдаемого извне промежуточного состояния с частично созданной записью владения.
- Ни один читающий запрос (проверка «доступен ли ещё экран Bootstrap») не может увидеть состояние `CLAIMING` — оно не персистентно (см. §3).
- Успешный переход в `COMPLETED` происходит не более одного раза за всю жизнь платформы.
- Отклонённая попытка claim не изменяет ни одной существующей записи и не создаёт ни одной новой.
- Публикация события `system.bootstrap.completed` происходит тогда и только тогда, когда атомарная операция подтверждённо создала первую запись владения — не раньше, не при отказе, не более одного раза.

- **Требуется реализовать полностью заново** (ни одного из перечисленного в коде сегодня нет): экран Bootstrap, executor/API-функция claim, доменный сервис Bootstrap, атомарная операция проверки-и-записи, событие `system.bootstrap.completed` как новый тип union, подписка Audit Log на это конкретное событие.

## 15. Критерии успешного завершения Bootstrap

1. Ровно один claim-запрос завершился успехом за всю жизнь платформы.
2. Итоговое число записей владения со статусом `ROOT_OWNER` — ровно 1 (было 0).
3. Событие `system.bootstrap.completed` опубликовано ровно один раз и присутствует в Audit Log.
4. Любая последующая попытка claim, в любой момент после этого, стабильно и предсказуемо отклоняется — без исключений и без временного «окна», в котором она могла бы снова пройти.
5. Platform State (`PLATFORM_INITIALIZATION_ARCHITECTURE.md` §14), вычисляемое из этого же факта, читается как `Operational` — экран Bootstrap для всех пользователей заменяется обычным процессом входа в Workspace (`PLATFORM_ACCESS_ARCHITECTURE.md`).
