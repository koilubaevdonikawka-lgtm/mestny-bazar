---

## 1. Границы Этапа 1

Этап 1 создаёт **только** хранилище и доменный сервис Platform Ownership. Он не создаёт claim-операцию, не публикует событий, не касается Role Resolution, не создаёт UI и не реализует Transfer Root Ownership. Признак завершения границы: после Этапа 1 в проекте существует новый, полностью изолированный код, который **ни один существующий файл не вызывает**.

---

## 2. Цель Этапа 1

Дать Этапу 2 (`BOOTSTRAP_REALIZATION_PLAN.md` §4 — claim-операция Bootstrap) готовое, протестированное основание для чтения/записи записи владения — без чего claim-операция не может быть написана.

---

## 3. Что разрешено реализовывать

- Новую миграцию: тип перечисления статуса владения, таблица записи владения, тип перечисления состояний Ownership Transfer, таблица Ownership Transfer, ограничение уникальности «не более одной `PENDING`-записи на целевую сторону» (`BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md` §14, пп. 1-5) — **только структуры**, без атомарной claim-операции (п.6-7 того же перечня — предмет Этапа 2).
- Новый порт (интерфейс репозитория Platform Ownership) с базовыми операциями чтения/записи (создать запись владения, получить запись по пользователю, получить число записей по статусу, создать/обновить запись Ownership Transfer, получить записи Transfer по статусу) — без атомарной «проверка+запись» claim-логики.
- Новый адаптер репозитория (Supabase) — реализация порта.
- Новый доменный сервис Platform Ownership — тонкая обёртка над репозиторием, без бизнес-правил claim/Transfer (те принадлежат Этапам 2 и 4).
- Тесты к порту (паттерн `fake<Port>()`), тесты к сервису.
- Регистрация нового сервиса/репозитория в `server/di/container.ts` — только добавление.

---

## 4. Что запрещено реализовывать

- ❌ Атомарная claim-операция (проверка «Root Owner = 0» + запись в одной транзакции) — Этап 2.
- ❌ Новый вариант события в `MarketplaceEvent` (`system.bootstrap.completed` и любые `ownership.transfer.*`) — Этап 2 и Этап 4 соответственно.
- ❌ Расширение `resolveRolesForUser`/любого `require<Role>FromRequest()` владельческим статусом — Этап 3.
- ❌ Экран Bootstrap, раздел владения в `/admin` — Этап 3.
- ❌ State machine Ownership Transfer (переходы `PENDING→ACCEPTED→COMPLETED/CANCELLED`) — Этап 4; в Этапе 1 таблица для этих записей создаётся, но логика переходов не пишется.
- ❌ Любое изменение существующего `user_roles`/`admin_scopes`/`seller_profiles` или кода, который их читает.

## 8. Полная последовательность реализации Этапа 1

1. **Предпосылки** (не код) — согласовать письменно имя таблицы записи владения; зафиксировать решение по судьбе ранее не задеплоенных миграций `admin_scopes`/`customer_blocking` (обнаружено предреализационным аудитом, Промпт №046 — независимо от Bootstrap, но должно быть решено до применения новой миграции в ту же базу).
2. Написать миграцию (тип перечисления + таблица записи владения + тип перечисления + таблица Ownership Transfer + ограничение уникальности).
3. Применить миграцию — **только с явного разрешения пользователя** (постоянное правило проекта).
4. Подтвердить применение — прямой read-only запрос к таблицам (по образцу уже использованного в этой сессии метода, Промпт №046 п.2), убедиться, что обе новые таблицы существуют и пусты.
5. Написать порт `IPlatformOwnershipRepository`.
6. Написать адаптер `SupabasePlatformOwnershipRepository`, реализующий порт.
7. Написать тесты адаптера/порта (паттерн `fake<Port>()`).
8. Написать доменный сервис `PlatformOwnershipService`.
9. Написать тесты сервиса.
10. Зарегистрировать репозиторий и сервис в `server/di/container.ts` (только добавление).
11. Прогнать полный набор проверок (см. §12).
12. Подтвердить, что ни один уже существующий файл, кроме `container.ts`, не изменился (`git status`/`git diff --stat`).

## 10. Критерии успешного завершения Этапа 1

- Миграция применена, обе новые таблицы существуют, пустые.
- Порт, адаптер и доменный сервис реализованы и покрыты тестами.
- Сервис и репозиторий зарегистрированы в `server/di/container.ts`.
- Ни один существующий файл, кроме `container.ts`, не изменён.
- Ни один существующий вызов/сервис/executor/UI не обращается к новому коду (проверяется отсутствием ссылок на новые символы за пределами их собственных файлов и `container.ts`).
- Полный набор проверок (§12) — зелёный.

---

## 11. Критерии отката

Поскольку ни один существующий вызов не обращается к новому коду и таблицы гарантированно пусты (ни одна claim-операция ещё не реализована — она появляется только в Этапе 2), откат Этапа 1 не теряет никаких данных: удаление новых файлов, удаление добавленных строк в `container.ts`, `DROP TABLE`/`DROP TYPE` для новых объектов схемы. Это самый дешёвый по стоимости отката этап из всей дорожной карты (совпадает с оценкой `BOOTSTRAP_REALIZATION_PLAN.md` §3).

---

## 12. Проверки после завершения Этапа 1

- **typecheck** (`npm run typecheck`) — ноль ошибок.
- **lint** (`npm run lint`) — ноль новых ошибок (существующие некритичные предупреждения в `components/ui/*` не в счёт).
- **test** (`npm run test`) — все существующие тесты продолжают проходить; новые тесты (порт/адаптер/сервис) проходят.
- **build** (`npm run build`) — успешная сборка, без новых предупреждений о недостижимом/неиспользуемом коде.
- **Architecture Guard** (`npm run guard`) — PASS, без новых предупреждений.

Все пять проверок обязательны и неснижаемы — Этап 1 не считается завершённым при отсутствии хотя бы одной.

---

## 13. Что должно стать результатом Этапа 1

Работающий, полностью протестированный, но **пока не используемый** ни одним существующим потоком системы домен Platform Ownership: две новые таблицы в боевой БД, порт, адаптер и доменный сервис, зарегистрированные в Composition Root. Ни один пользователь платформы не видит и не может вызвать ничего нового — единственное наблюдаемое изменение системы снаружи отсутствует полностью. Это ожидаемый, спроектированный результат (см. `BOOTSTRAP_IMPLEMENTATION_ARCHITECTURE.md` §9, п.2 — «Новый код добавляется, но не подключается к существующим пользовательским сценариям автоматически»), а не недоработка.

---

Это исключительно техническая спецификация Этапа 1. Код, SQL, миграции не создавались; архитектура, модель данных, роли, жизненный цикл Bootstrap и дорожная карта не изменялись; Этап 2 не проектировался; коммит и деплой не выполнялись.
