# Architecture Policy — Политика архитектуры платформы «Местный Базар»

> **Статус:** официальный архитектурный документ  
> **Область действия:** все текущие и будущие этапы развития платформы  
> **Изменения кода:** данный документ не требует и не предполагает изменений в BCM, API, Domain, Infrastructure или базе данных

---

## 1. Миссия платформы

«Местный Базар» создаётся **не как обычный маркетплейс**.

Цель проекта — построить **масштабируемую цифровую экосистему** для жителей Кыргызстана: единую платформу, через которую люди получают доступ к локальным товарам, услугам, партнёрским программам и цифровым сервисам повседневной жизни.

**Маркетплейс является первым этапом** развития платформы. Он формирует фундамент доверия, транзакций, логистики и пользовательской базы. Все последующие возможности — лояльность, партнёрства, дополнительные сервисы — надстраиваются поверх уже работающего ядра, а не заменяют его.

---

## 2. Этапы развития

Развитие платформы происходит **поэтапно**. Архитектура закладывается заранее; функциональность внедряется постепенно.

| Версия | Фокус | Описание |
|--------|-------|----------|
| **Версия 1** | Marketplace Core | Надёжный маркетплейс: каталог, продавцы, заказы, оплата, доставка, администрирование |
| **Версия 2** | Loyalty BCM | Программа лояльности: уровни, бонусы, награды, кэшбэк, купоны |
| **Версия 3** | Partner Ecosystem | Партнёрская экосистема: банки, операторы, коммунальные и государственные сервисы |
| **Версия 4+** | Extended Services | Дополнительные сервисы по мере зрелости платформы и потребностей пользователей |

**Принцип:** архитектурные точки расширения проектируются заранее, но реализация каждой версии не блокирует работу предыдущих.

---

## 3. Принцип стабильного ядра

**Marketplace Core (Ядро маркетплейса)** должно оставаться максимально стабильным.

Основные процессы ядра:

- регистрация
- каталог
- продавцы
- поиск
- корзина
- заказ
- оплата
- доставка
- склад
- администрирование

Эти процессы **не должны переписываться** при появлении новых возможностей. Все развитие происходит **вокруг ядра**, а не вместо него.

Новые BCM подключаются как опциональные расширения через чётко определённые контракты (порты, события, Application Layer), не затрагивая внутреннюю логику ядра.

---

## 4. Принцип независимости модулей

Любой новый **Business Capability Module (BCM)** должен быть **полностью опциональным**.

Если отключить:

- Loyalty BCM (Модуль программы лояльности)
- Experience Engine (Движок пользовательского опыта)
- Rule Engine (Движок правил)
- Recommendation Engine (Движок рекомендаций)
- Partner Integrations (Партнёрские интеграции)
- Gamification (Геймификация)
- Live Commerce (Живая коммерция)

— **маркетплейс продолжает полностью работать**.

> **Жёсткое правило:** ни один дополнительный модуль не имеет права становиться обязательной зависимостью Marketplace Core.

Интеграция дополнительных модулей осуществляется через:

- события домена (Domain Events)
- Application Layer (оркестрация сценариев)
- опциональную регистрацию в Composition Root (DI)

---

## 5. Loyalty Architecture

Будущая программа лояльности реализуется отдельным **Loyalty BCM (Модулем программы лояльности)**.

Loyalty BCM отвечает **исключительно** за:

| Область | Примеры |
|---------|---------|
| Уровни | Bronze, Silver, Gold, Platinum |
| Бонусы | Начисление, списание, срок действия |
| Награды | Достижения, подарки, призы |
| Месячный оборот | Расчёт и отслеживание turnover |
| Партнёрские преимущества | Скидки от банков, операторов |
| Кэшбэк | Процент возврата по категориям |
| Купоны | Персональные и массовые промокоды |
| Персональные предложения | Targeted offers на основе профиля |

**Все правила лояльности** работают через **Rule Engine (Движок правил)**.  
**Запрещены hardcode-условия** вида `if (turnover > 10000)` непосредственно в коде BCM.

Loyalty BCM **не владеет** заказами, оплатой или каталогом — он **реагирует** на события ядра и **предоставляет** данные о балансе и наградах по запросу.

---

## 6. Rule Engine

**Rule Engine (Движок правил)** — центральный механизм конфигурируемой бизнес-логики.

Все бизнес-правила должны быть **конфигурируемыми** и управляться без деплоя нового кода.

### Примеры правил

```
оборот > 10 000 KGS
    ↓
получить награду «Активный покупатель»
```

```
день рождения пользователя
    ↓
подарок / персональный купон
```

```
Нооруз (21 марта)
    ↓
специальная сезонная акция
```

```
уровень клиента = Gold
    ↓
бесплатная доставка от 500 KGS
```

### Требования к Rule Engine

- правила создаются и изменяются **без изменения программного кода**
- правила версионируются и имеют срок действия
- правила тестируются в изолированной среде до публикации
- правила не создают прямых зависимостей между BCM — только через события и контракты

---

## 7. Experience Engine

**Experience Engine (Движок пользовательского опыта)** отвечает **исключительно** за визуальный и эмоциональный опыт пользователя.

Через Experience Engine управляются:

| Категория | Элементы |
|-----------|----------|
| Визуальная идентичность | темы, цвета, шрифты, иконки, иллюстрации |
| Контент главной | баннеры, рекламные блоки, акции, главная страница |
| Анимации | переходы, микро-взаимодействия, загрузочные экраны |
| Onboarding | приветственные экраны, туры по приложению |
| Сезонность | праздничные оформления, сезонные темы |
| Персонализация UI | блоки на основе уровня клиента, достижений, города |

Experience Engine **не содержит** бизнес-логики заказов, оплаты или лояльности. Он **получает** данные от других BCM (уровень клиента, активные акции) и **отображает** соответствующий интерфейс.

---

## 8. Динамический интерфейс

Интерфейс платформы должен иметь возможность **автоматически изменяться** в зависимости от контекста — **без выпуска новой версии приложения**.

### Триггеры изменений

| Триггер | Пример |
|---------|--------|
| Время года | Зимнее / летнее оформление |
| Погода | Баннер «Горячий чай» при −15 °C |
| Государственные праздники | Нооруз, День независимости |
| Городские события | Фестивали, ярмарки в конкретном городе |
| Маркетинговые кампании | «Чёрная пятница», «Новогодняя распродажа» |
| Достижения пользователя | Персональный баннер после первого заказа |
| Уровень клиента | Премиальное оформление для Gold |
| Партнёрские программы | Блок «Скидка от Optima Bank» |

Все изменения конфигурируются через **административную панель** и доставляются клиенту через **Experience Engine** в режиме реального времени или с минимальной задержкой (CDN / push-конфигурация).

---

## 9. Регистрация пользователя

Регистрация является частью **Onboarding Experience (Пути знакомства пользователя с приложением)**.

### Принципы

1. **Форма регистрации не должна быть первым экраном.** Пользователь сначала видит ценность платформы: товары, акции, преимущества, локальный контекст.
2. **Регистрация должна мотивировать**, а не препятствовать: минимум полей, понятная выгода («получите 500 бонусов за регистрацию»).
3. **Onboarding — это сценарий**, а не одна форма: welcome-экраны → демонстрация возможностей → мягкий призыв к регистрации → подтверждение телефона → персонализация.
4. Контент onboarding управляется через **Experience Engine**, а не захардкожен в коде.

---

## 10. Премиальный дизайн

Интерфейс должен создавать ощущение **продукта мирового уровня**.

### Основные принципы

| Принцип | Описание |
|---------|----------|
| **Минимализм** | Только необходимое на экране; никакого визуального шума |
| **Скорость** | Мгновенная отзывчивость; skeleton-загрузки вместо спиннеров |
| **Дорогая типографика** | Продуманная иерархия шрифтов, читаемость на всех устройствах |
| **Плавные анимации** | 60 fps; анимации с целью, а не ради декора |
| **Идеальные отступы** | Единая сетка; визуальный ритм |
| **Визуальная чистота** | Консистентные цвета, тени, скругления |
| **Единая дизайн-система** | Компоненты, токены, паттерны — один источник правды |
| **Эмоциональное восприятие** | Продукт должен вызывать доверие и желание возвращаться |

Дизайн-система является **общим активом** платформы и не дублируется в каждом BCM.

---

## 11. Конфигурируемость

Из **административной панели** должны изменяться без деплоя:

- баннеры
- темы
- цвета
- иконки
- иллюстрации
- главные экраны
- приветственные сообщения
- акции
- маркетинговые кампании
- сезонные оформления
- праздничные оформления

> **Запрещены жёстко прописанные значения** (hardcode) для любого пользовательского контента, который может меняться операционной командой.

Конфигурация хранится централизованно, версионируется и доставляется клиентам через Experience Engine.

---

## 12. Будущая экосистема

Архитектура должна позволять подключать **внешних партнёров** без изменения Marketplace Core:

| Категория партнёров | Примеры интеграций |
|---------------------|-------------------|
| Банки | Кэшбэк, рассрочка, оплата |
| Страховые компании | Страхование доставки, товаров |
| Коммунальные службы | Оплата счетов через приложение |
| Мобильные операторы | Пополнение, пакеты, бонусы |
| Интернет-провайдеры | Оплата тарифов, акции |
| Курьерские службы | Альтернативная доставка |
| Сервисы доставки | Еда, продукты, express |
| Государственные сервисы | Tunduk, налоги, справки |
| Другие организации | Любые партнёры через стандартный Partner Integration API |

### Принципы интеграции

- каждый партнёр подключается через **Partner Integration BCM** (будущий модуль)
- Marketplace Core **не знает** о конкретном партнёре — только о контракте
- отключение партнёра **не ломает** маркетплейс
- данные партнёра изолированы; обмен только через события и API-контракты

---

## 13. Архитектурные ограничения

### Запрещается

| # | Ограничение |
|---|-------------|
| 1 | **Ломать существующие BCM** — изменения только additive; breaking changes требуют ADR и миграционного плана |
| 2 | **Создавать сильную связанность** — прямые импорты между BCM запрещены; только через порты и события |
| 3 | **Добавлять новые зависимости в Marketplace Core** — ядро не должно зависеть от Loyalty, Experience, Rule Engine и т.д. |
| 4 | **Переписывать работающие бизнес-процессы** без документированной технической необходимости |
| 5 | **Hardcode бизнес-правил** — все правила через Rule Engine |
| 6 | **Hardcode UI-контента** — весь контент через Experience Engine / админ-панель |
| 7 | **Создавать новые Platform-модули** для вертикальных сценариев — сценарии живут в Application Layer поверх BCM |

### Разрешается

- добавление новых **опциональных** BCM
- расширение Application Layer (вертикальные сценарии)
- добавление REST-маршрутов **без изменения** существующих
- минимальные additive-изменения в BCM (новые методы, новые поля с defaults)
- создание ADR (Architecture Decision Record) для фиксации решений

---

## 14. Главный принцип

> **Каждая новая возможность должна расширять существующую архитектуру, а не заменять её.**

Система должна развиваться **десятилетиями** без необходимости полного переписывания.

```
Marketplace Core          ← стабильное, неизменное ядро
    ↑ events / ports
Application Layer         ← вертикальные сценарии (покупка, lifecycle, seller, customer)
    ↑ optional
Loyalty BCM               ← опционально
Experience Engine         ← опционально
Rule Engine               ← опционально
Partner Integrations      ← опционально
Recommendation Engine     ← опционально
Gamification              ← опционально
Live Commerce             ← опционально
```

Новая функциональность **надстраивается**. Старая **продолжает работать**. Ядро **остаётся стабильным**.
