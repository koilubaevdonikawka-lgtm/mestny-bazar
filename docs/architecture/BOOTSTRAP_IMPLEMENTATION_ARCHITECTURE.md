Этот документ не вводит ни одного нового архитектурного модуля. Он использует исключительно понятия, уже утверждённые в четырёх документах выше: **Platform Initialization**, **Platform Core**, **Platform Ownership**, **Platform Access**. Задача документа — превратить их в последовательность этапов, каждый из которых оставляет проект в рабочем состоянии.

---

## 1. Назначение Bootstrap Implementation

Bootstrap Implementation описывает **порядок**, в котором утверждённая архитектура (Platform Initialization → Platform Core → Platform Ownership → Platform Access) должна быть перенесена из документов в код, не нарушая при этом ни одного дня работы уже действующей платформы. Это не пятый архитектурный модуль — это план, показывающий, в каком порядке уже утверждённые модули появляются в репозитории.

---

## 2. Цели реализации Bootstrap

1. Довести Architecture v2.0 до рабочего кода без остановки платформы.
2. Каждый этап — самостоятельный, проверяемый шаг, а не часть одного большого неделимого изменения.
3. На любом этапе, в любой момент, проект должен проходить typecheck/lint/test/build/Architecture Guard.
4. Ни один этап не должен требовать одновременного изменения всех слоёв (БД + сервер + UI) одной неделимой поставкой.
5. Существующая система ролей (`user_roles`, `admin_scopes`, `PermissionPolicyService`) не заменяется и не переписывается — Platform Ownership/Access добавляются рядом (соответствует уже зафиксированному в `PLATFORM_CORE_ARCHITECTURE.md` §10 принципу расширения только добавлением).

## 4. Этапы реализации

### Этап 0 — Готовность
Проверка предпосылок без изменения кода: подтверждение фактического состояния существующих миграций (`user_roles`, `admin_scopes` — их задеплоенность в боевую БД остаётся открытым вопросом с момента аудита Промпта №034 §3 и должна быть закрыта до Этапа 1, иначе Этап 1 рискует наслаиваться на неизвестное состояние).

### Этап 1 — Схема данных Platform Ownership
Новые, исключительно аддитивные таблицы для домена Platform Ownership (`PLATFORM_OWNERSHIP_ARCHITECTURE.md`): хранение Root Owner/Owner и состояния Transfer Root Ownership. Ни одна существующая таблица (`user_roles`, `admin_scopes`, `profiles`) не изменяется.

### Этап 2 — Platform Core: домен Platform Ownership
Доменный сервис, порт и репозиторий для чтения/записи владения (по образцу уже существующего `UserAdminService`/`SupabaseUserAdminRepository`, зафиксированному в аудите Промпта №034 §4-5) + регистрация в Composition Root (`server/di/container.ts`). Ничего ещё не вызывает этот сервис — существующее поведение платформы не меняется.

### Этап 3 — Platform Initialization: Bootstrap
Состояния `ELIGIBLE → CLAIMING → COMPLETED` (`PLATFORM_INITIALIZATION_ARCHITECTURE.md` §3-4), инвариант «минимум один Root Owner», событие `system.bootstrap.completed`. Использует сервис из Этапа 2. До этого этапа claim-операции не существует физически — значит, до его завершения платформа объективно ещё не имеет механизма стать `Operational` в терминах `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §14, и это нормальное, ожидаемое промежуточное состояние всего плана внедрения, а не ошибка.

### Этап 4 — Platform Access: Role Resolution
Расширение существующего разрешения ролей (`resolveRolesForUser`, `server/auth/resolve-user.ts`) дополнительным чтением владельческого статуса (Root Owner/Owner) из сервиса Этапа 2, без изменения поведения существующих `require<Role>FromRequest()` guard'ов (`PLATFORM_ACCESS_ARCHITECTURE.md` §5-6, §9).

### Этап 5 — UI: экран Bootstrap и раздел владения
Экран, показываемый только при состоянии `ELIGIBLE` (см. `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §9 — единственный UI Platform Initialization), и раздел управления владением внутри Administration Workspace (просмотр/назначение Owner, инициация Transfer) — потребители Этапов 3-4.

### Этап 6 — Transfer Root Ownership
Состояние-машина `PENDING → ACCEPTED → COMPLETED/CANCELLED`, двустороннее согласие, события `ownership.transfer.*` (`PLATFORM_OWNERSHIP_ARCHITECTURE.md` §7, §12). Использует ту же схему Этапа 1 и сервис Этапа 2.

### Этап 7 — Полный CTO-аудит
Проверка соответствия всех четырёх утверждённых документов фактическому коду, актуализация документации, зелёный Architecture Guard — по уже проверенному в проекте образцу (Delivery Management, Этап 3).

## 5. Зависимости между этапами

| Этап | Зависит от | Причина |
|---|---|---|
| 0 | — | Не зависит ни от чего, чисто проверочный |
| 1 | 0 | Нужна уверенность в текущем состоянии БД перед добавлением новой схемы |
| 2 | 1 | Домен-сервису нужны таблицы, которые он читает/пишет |
| 3 | 2 | Bootstrap записывает/читает через сервис Этапа 2 |
| 4 | 2 | Role Resolution читает тот же сервис Этапа 2 (не обязательно дожидаться Этапа 3 — см. §7) |
| 5 | 3, 4 | UI показывает состояние Bootstrap (Этап 3) и роль-с-учётом-владения (Этап 4) |
| 6 | 1, 2 | Transfer использует ту же схему и сервис, что Bootstrap, но не сам Bootstrap как код (см. §7) |
| 7 | 1-6 | Аудит проверяет уже реализованное |

## 6. Изменения по слоям

**База данных** — только Этап 1: новые таблицы домена Platform Ownership (владение, состояние Transfer). Ни одного `ALTER`/`DROP` над существующими таблицами `user_roles`, `admin_scopes`, `profiles`.

**Серверная логика** — Этапы 2, 3, 4, 6: новый доменный сервис/порт/репозиторий Platform Ownership (Этап 2), claim-логика Bootstrap с инвариантом минимума (Этап 3), расширение Role Resolution (Этап 4), state machine Transfer (Этап 6). Существующие `server/domain/user-admin.service.ts`, `server/domain/permission-policy/`, все `require<Role>FromRequest()` — не изменяются, только дополняются рядом стоящим новым кодом.

**Platform Core** — принимает домен Platform Ownership как новый элемент своего перечня сервисов (уже предусмотрено в `PLATFORM_CORE_ARCHITECTURE.md` §5, строка «Ownership» помечена там как «спроектировано, в коде отсутствует» — Этапы 1-2 закрывают именно этот, уже заранее обозначенный пробел).

**Platform Ownership** — реализуется целиком в Этапах 1-2 (данные и сервис) и 6 (Transfer) — весь домен, описанный в `PLATFORM_OWNERSHIP_ARCHITECTURE.md`.

**Platform Access** — Этап 4: единственное изменение — Role Resolution начинает видеть владельческий статус наравне с Access-ролями, не меняя ни одного из существующих guard'ов.

**Пользовательский интерфейс** — только Этап 5: экран Bootstrap (новый, ранее не существовавший маршрут, показываемый один раз) и раздел владения внутри уже существующей Administration Workspace (`/admin`). Ни один существующий экран не переписывается.

---

## 7. Какие изменения можно выполнять независимо

- Этап 1 (схема Platform Ownership) — полностью независим от любого другого этапа; чисто аддитивная миграция, ни на что не влияющая, пока к таблицам никто не обращается.
- Этап 2 (сервис Platform Ownership) — может быть реализован и задеплоен без Этапа 3: сервис существует, но пока не вызывается ни Bootstrap, ни UI — нулевой риск для действующей системы.
- Этап 4 (Role Resolution) — технически не обязан ждать завершения Этапа 3: расширение чтения владельческого статуса можно закончить и задеплоить, пока Bootstrap ещё не реализован — просто до Этапа 3 этот статус всегда будет пуст (Root Owner ещё не существует), что не является ошибкой.
- Этап 6 (Transfer, как код) — можно писать параллельно с Этапом 3, поскольку использует ту же схему Этапа 1 и тот же сервис Этапа 2, а не сам код Bootstrap — но **практически бессмысленен до появления первого Root Owner** (Этап 3), то есть независим по коду, но не по ценности (см. разграничение в §8).

## 8. Какие изменения должны выполняться строго последовательно

- Этап 1 → Этап 2 — сервису физически не с чем работать без таблиц.
- Этап 2 → Этап 3 — Bootstrap не может писать факт владения, если некуда его писать.
- Этап 3 и Этап 4 → Этап 5 — UI показывает состояние, которого до этих этапов не существует; строить экран раньше данных, которые он отображает, бессмысленно.
- Этап 1, 2 → Этап 6 — Transfer нуждается в той же схеме/сервисе, что и Bootstrap (см. §7 — независим от Bootstrap-кода, но не от схемы/сервиса).
- Все этапы → Этап 7 — аудит по определению идёт последним.

---

## 9. Порядок миграции без остановки работающей системы

1. Все изменения БД (Этап 1) — только `CREATE TABLE`, без затрагивания существующих таблиц; такая миграция не блокирует текущие запросы и не требует окна обслуживания (тот же паттерн, что уже применялся во всех существующих миграциях `supabase/migrations/`).
2. Новый код (Этапы 2-4, 6) добавляется, но не подключается к существующим пользовательским сценариям автоматически — до Этапа 5 ни один пользователь не видит и не может вызвать ни одну из новых возможностей, значит, ошибка в новом коде не может проявиться в уже работающих потоках (Customer/Seller/Courier/Warehouse Workspace продолжают работать в точности как раньше).
3. Экран Bootstrap (Этап 5) — новый маршрут, не заменяющий ни одного существующего; появление раздела владения в `/admin` — аддитивное расширение уже существующей страницы, не переработка её текущего содержимого.
4. Каждый этап — отдельный деплой (в проекте нет автоматического CD, деплой выполняется вручную — установлено в ходе расследования Промптов №033-034), значит, каждый этап проверяется на проде изолированно, прежде чем начинается следующий.
5. Ни на одном этапе не требуется одновременная поставка изменений во всех слоях (БД + сервер + UI) одним неделимым релизом — что прямо удовлетворяет обязательному требованию «все этапы выполнимы независимо» (см. Обязательные требования промпта).

## 10. Архитектурные риски каждого этапа

- **Этап 0** — риск: неизвестное фактическое состояние `admin_scopes` в проде (задеплоено или нет) может исказить предположения последующих этапов о том, что уже существует в БД.
- **Этап 1** — риск: конфликт имён новых таблиц с чем-либо существующим; риск минимален, но не равен нулю без явной сверки.
- **Этап 2** — риск: сервис спроектирован без реального потребителя — тестовое покрытие может оказаться неполным до появления Этапа 3, если тесты пишутся исключительно «под интерфейс», а не под реальный сценарий использования.
- **Этап 3** — риск: некорректная реализация инварианта «минимум один Root Owner» способна либо заблокировать легитимный Bootstrap, либо (хуже) пропустить состояние с нулём Root Owner.
- **Этап 4** — риск: расширение Role Resolution способно случайно изменить поведение уже существующих `require<Role>FromRequest()` guard'ов, если реализовано не строго аддитивно.
- **Этап 5** — риск: экран Bootstrap, доступный дольше, чем предполагалось (например, из-за ошибки в проверке состояния `ELIGIBLE`), может остаться видимым/доступным уже после того, как Root Owner создан.
- **Этап 6** — риск: некорректная state-machine Transfer способна создать «зависший» PENDING-переход или, в худшем случае, позволить завершить передачу без согласия целевой стороны.
- **Этап 7** — риск: аудит проводится формально, не вскрывая реальных расхождений между документами и кодом.

---

## 11. Способы снижения рисков

- Этап 0: явно зафиксировать в отчёте фактическое состояние каждой существующей миграции перед началом Этапа 1, а не полагаться на предположение.
- Этап 1: сверка имён новых таблиц/типов с полным списком существующих объектов схемы перед написанием миграции.
- Этап 2: сервис Этапа 2 сопровождается тестами на уровне контракта порта (по уже принятому в проекте паттерну `fake<Port>()`, зафиксированному в `ARCHITECTURE_PRINCIPLES.md` CD-09) независимо от наличия реального потребителя.
- Этап 3: инвариант «минимум один Root Owner» проверяется отдельным, явным тестовым набором сценариев (0→1, 1→0 отклонён, 1→2, 2→1 разрешён) до подключения к реальному API.
- Этап 4: расширение Role Resolution проверяется регрессионным набором тестов на существующих `require<Role>FromRequest()`, подтверждающим, что их поведение не изменилось ни для одного существующего сценария.
- Этап 5: состояние `ELIGIBLE`/`COMPLETED` проверяется на сервере при каждом обращении к экрану Bootstrap (не кэшируется на клиенте) — устраняет саму возможность «дольше видимого экрана» как класс ошибки.
- Этап 6: Transfer тестируется на полный набор переходов состояний, включая явно отклонённые (`CANCELLED`, попытка `COMPLETED` без `ACCEPTED`, попытка увести число Root Owner в ноль).
- Этап 7: аудит выполняется по той же методологии, что уже применялась в проекте (Промпт №034 — построчная сверка кода с документом, а не пересказ документа).

## 12. Критерии завершения каждого этапа

| Этап | Критерий завершения |
|---|---|
| 0 | Фактическое состояние существующих миграций зафиксировано в отчёте; открытых вопросов о текущей схеме не осталось |
| 1 | Миграция применена (только с явного разрешения — постоянное правило проекта), typecheck/lint/test/build/guard зелёные, ни одна существующая таблица не изменена |
| 2 | Сервис/порт/репозиторий реализованы и покрыты тестами, зарегистрированы в Composition Root, ни один существующий вызов в проекте не использует их (проверяется отсутствием изменений в уже существующих сервисах) |
| 3 | Claim-операция работает через все 3 слоя API, инвариант минимума подтверждён тестами, событие `system.bootstrap.completed` публикуется и потребляется Audit Log |
| 4 | Role Resolution возвращает владельческий статус, все существующие guard'ы проходят регрессионные тесты без изменений в ожидаемых результатах |
| 5 | Экран Bootstrap показывается только при `ELIGIBLE` и не показывается после `COMPLETED`; раздел владения в `/admin` отображает реальные данные из Этапов 1-4 |
| 6 | Transfer проходит полный жизненный цикл (`PENDING → ACCEPTED → COMPLETED` и `PENDING → CANCELLED`) под тестами, инвариант минимума соблюдается и здесь |
| 7 | Все 4 утверждённых документа сверены с фактическим кодом построчно; расхождения (если найдены) зафиксированы, а не скрыты; Architecture Guard — PASS |

Во всех случаях: typecheck/lint/test/build/Architecture Guard — обязательный, неснижаемый минимум для завершения любого этапа, независимо от таблицы выше.

## 13. Финальная дорожная карта реализации Bootstrap

```
Этап 0 — Готовность                      (аудит, без изменений)
   ↓
Этап 1 — Схема Platform Ownership         (БД, аддитивно)
   ↓
Этап 2 — Platform Core: Ownership-домен   (сервер, без потребителей)
   ↓
Этап 3 — Platform Initialization: Bootstrap (сервер, claim-операция)
   │
   ├──→ Этап 4 — Platform Access: Role Resolution   (сервер, параллельно возможен раньше Этапа 3 — см. §7)
   │
   └──→ Этап 6 — Transfer Root Ownership             (сервер, код параллельно возможен — см. §7)
   ↓
Этап 5 — UI: экран Bootstrap + раздел владения       (требует 3 и 4)
   ↓
Этап 7 — Полный CTO-аудит                            (финальная проверка)
```

Каждая стрелка — отдельный, самостоятельно проверяемый деплой; ни одна стрелка не требует одновременного изменения всех слоёв платформы.

---

Это исключительно архитектурный документ. Код, SQL, миграции, существующие архитектурные документы не изменялись, коммит и деплой не выполнялись.
