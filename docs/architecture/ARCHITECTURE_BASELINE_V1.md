## 1. Назначение документа

Этот документ фиксирует итоговое, проверенное состояние архитектуры платформы «Местный Базар» как **Architecture Baseline Version 1.0** — официальную точку отсчёта, с которой сверяется любое последующее изменение системы.

Baseline решает три задачи:

1. **Единый эталон.** Вместо того чтобы каждый новый аудит или новая подсистема заново реконструировали архитектуру из кода и разрозненных документов, они сверяются с одним зафиксированным описанием.
2. **Граница «расширение vs изменение».** Baseline отделяет то, что уже проверено и стабильно (ядро), от того, что ещё будет построено (новые подсистемы). Новый код обязан расширять Baseline, а не переопределять его.
3. **Критерий проверки.** Architecture Guard и любой CTO Audit используют этот документ как основной источник критериев «что считается нарушением», наравне с `ARCHITECTURE_PRINCIPLES.md` и действующими ADR.

Baseline не заменяет `ARCHITECTURE_PRINCIPLES.md`, `ARCHITECTURE_POLICY.md`, ADR или `docs/admin-platform/`. Он их не пересказывает и не дублирует — он фиксирует **итог их применения** в виде одного проверяемого состояния.

## 2. Общая схема платформы

```
Местный Базар
│
├── Покупательское PWA          (src/routes/*, src/components/*)
├── Административная платформа  (src/routes/admin/*, включает Warehouse и Seller Workspace)
│
├── API                          (src/api/*.ts → src/api/*.functions.ts, createServerFn)
├── Domain                       (server/domain/*.service.ts)
├── Rule Engine                  (server/domain/**/*.rule.ts — order/applies/evaluate/terminal)
├── Repository                   (server/adapters/supabase/*.repository.ts, порты в server/ports/)
├── Supabase                     (единственная база данных: Postgres + Auth + Storage)
└── Marketplace Events           (server/ports/marketplace-events.port.ts — синхронная in-process шина)
```

**Курьерское PWA** — следующая подсистема платформы. Она строится как отдельная точка входа (отдельный набор маршрутов и лёгкий UI, устанавливаемый на экран телефона) поверх **того же** `server/`, той же авторизации, того же домена и той же базы данных — без создания второго backend, второй схемы БД или параллельной бизнес-логики. Курьерское PWA **расширяет** Baseline; оно не вносит в него изменений.

## 3. Архитектурные принципы

Итоговый, зафиксированный список принципов, обязательных для всего кода платформы:

| Принцип | Суть |
|---|---|
| **Single Source of Truth** | Server + Database — единственный источник данных и решений. Клиент не хранит и не вычисляет бизнес-состояние самостоятельно. |
| **Ports & Adapters** | Domain зависит только от интерфейсов (`server/ports/`). Конкретные реализации (Supabase, Finik, Telegram) — заменяемые адаптеры (`server/adapters/`). |
| **Rule Engine** | Любая логика «можно/нельзя» — `order` (порядок), `applies()` (применимость), `evaluate()` (результат), `terminal` (останов цепочки). Не `if`-цепочки в оркестраторах. |
| **Dependency Injection** | Каждый сервис получает зависимости через конструктор. Ничего не создаёт свои зависимости самостоятельно. |
| **Composition Root** | Единственное место сборки зависимостей — `server/di/container.ts`, функция `createServices()`. |
| **Repository Pattern** | Domain обращается к данным только через порт репозитория, никогда напрямую к клиенту БД. |
| **DTO First** | Frontend знает только контракты из `shared/contracts/` — никаких типов БД, никаких структур внешних провайдеров в UI. |
| **Event Driven** | Значимые действия платформы публикуются как `MarketplaceEvent` через `IMarketplaceEventBus`; подписчики (Audit Log, Notification Center, AI) реагируют независимо от источника события. |
| **Browser First** | Вся платформа — веб-приложение (включая PWA), без нативных мобильных сборок, без зависимости от конкретной ОС. |
| **PWA First** | Каждая новая точка входа для новой роли (после Customer/Admin) — отдельное PWA поверх общего backend, а не встроенный в один UI режим. |
| **Open for Extension, Never Replace** | Новая функциональность подключается аддитивно (новый домен-сервис, новый порт, новая подписка на события). Существующие модули не переписываются под нужды нового. |
| **Admin Platform как центр управления системой** | Все операционные изменения (каталог, цены, остатки, роли, контент, настройки) выполняются через Административную платформу и немедленно отражаются для Покупательского PWA — без отдельного деплоя. |

## 4. Инварианты архитектуры

Ниже — то, что запрещено нарушать при любом изменении системы, начиная с Baseline v1.0:

- ❌ Второй источник каталога (второй `IProductRepository`, второй путь получения товаров/цен/остатков/фото в обход Supabase).
- ❌ Обход Domain — вызов Repository/адаптера напрямую из транспортного слоя (`src/api/`, `server/functions/`) в обход `server/domain/*.service.ts`.
- ❌ Обход Repository — обращение к `supabaseAdmin` напрямую из Domain-сервиса в обход порта репозитория.
- ❌ Обход Rule Engine — бизнес-правило вида «можно/нельзя», реализованное как `if`-цепочка в оркестраторе, а не как правило Rule Engine.
- ❌ Обход API — прямой импорт `server/**` из `src/**` (кроме `src/api/`), в обход `createServerFn`-границы.
- ❌ Прямой доступ UI к БД — любой вызов Supabase SDK из клиентского кода (кроме сессии авторизации через `src/integrations/supabase/`).
- ❌ Второй `ProductRepository` — более одной реализации `IProductRepository`, одновременно активной в `server/di/container.ts`.
- ❌ Дублирование бизнес-логики — одно и то же правило/расчёт, реализованное в двух местах вместо переиспользования существующего домен-сервиса.
- ❌ Нарушение Dependency Injection — создание адаптера или Rule Engine-сервиса оператором `new` вне `server/di/container.ts`.
- ❌ Параллельная архитектура — вторая композиционная точка, вторая схема слоёв или второй backend для новой подсистемы вместо расширения существующего `server/`.

## 5. Границы ответственности

| Слой | Отвечает за |
|---|---|
| **Покупательское PWA** | Отображение данных, полученных через `src/api/*`; локальное состояние UI и гостевой корзины (`localStorage`) — не бизнес-решения, только снимок для рендера. Никогда не хранит цену/остаток/статус как источник истины. |
| **Административная платформа** | Единая точка операционного управления: создание и изменение каталога, заказов, ролей, контента, настроек. Включает Warehouse Workspace и Seller Workspace как встроенные разделы (не отдельные приложения). |
| **Server** | Единственная точка выполнения бизнес-логики. Транспортная граница (`src/api/*.functions.ts` → `server/functions/*`) — валидация запроса и делегирование в Domain, без собственной бизнес-логики. |
| **Domain** | Бизнес-правила и оркестрация сценариев (`server/domain/*.service.ts`). Зависит только от портов (`server/ports/`), никогда — от конкретных адаптеров. |
| **Repository** | Перевод между доменной моделью (DTO) и хранилищем (`server/adapters/supabase/*.repository.ts`). Единственное место, где строятся запросы к Supabase. |
| **Database (Supabase)** | Персистентное хранение всех данных платформы: каталог, заказы, пользователи, роли, контент. Единственная база данных на весь проект — покупательский PWA, Административную платформу и будущее Курьерское PWA. |
| **Marketplace Events** | Уведомление независимых подписчиков (Audit Log, Notification Center, AI-воркеры) о значимых доменных событиях, без прямой связи между Domain-сервисами. |
| **Rule Engine** | Конфигурируемые, тестируемые в изоляции цепочки правил для каждого класса «можно/нельзя»-решений (публикация товара, оплата, назначение курьера, права доступа и т.д.). |
| **DI (Composition Root)** | Единственное место, где адаптеры связываются с портами и передаются в конструкторы сервисов — `server/di/container.ts`. |

## 6. Source of Truth

**Server + Database являются единственным Source of Truth платформы «Местный Базар».**

Это означает:

- Покупательское PWA и Административная платформа читают и изменяют **одни и те же** данные через **один и тот же** путь: `Platform API → Server Function → Domain → Repository → Supabase`.
- Ни один альтернативный источник данных (внешний каталог, локальная копия бизнес-состояния, параллельная база) не допускается.
- Любое изменение, сделанное через Административную платформу, немедленно доступно Покупательскому PWA при следующем запросе — без отдельного деплоя, без ручной синхронизации.
- Единственное исключение — гостевая корзина в `localStorage` до авторизации: это снимок ввода пользователя для UX, не источник истины о цене/остатке (при оформлении заказа цена и остаток пересчитываются заново на сервере).

## 7. Расширение платформы

Любая новая подсистема — Курьерское PWA, AI, Программа лояльности, Интеграции с партнёрами и любые последующие — обязана:

- использовать существующий `server/` как единственный backend (та же авторизация, та же композиция зависимостей, та же база данных);
- подключаться аддитивно: новый домен-сервис, новые порты при необходимости, новые подписки на `MarketplaceEvent` — без изменения уже работающих сервисов сверх необходимого;
- не создавать вторую версию уже существующего механизма (второй каталог, вторая система прав, вторая шина событий).

**Создание параллельной архитектуры запрещено.** Если новая подсистема требует возможности, которой сегодня нет (новый порт, новое событие, новое правило) — она добавляется расширением существующего слоя, а решение уровня архитектуры (не реализации) фиксируется отдельным ADR.

## 8. Architecture Guard

Каждый новый этап, любая новая подсистема и любое изменение кода обязаны без исключений проходить:

```
☑ typecheck
☑ lint
☑ tests
☑ build
☑ Architecture Guard (npm run guard + ручной чек-лист ARCHITECTURE_GUARD.md §3)
```

Architecture Guard равноправен остальным четырём проверкам, не является опциональным дополнением. `FAIL` в любой из шести проверок безусловно запрещает commit, независимо от статуса остальных.

---

## 9. CTO Verification

Любое утверждение о готовности системы, о завершении миграции или об устранении нарушения подтверждается **только** доказательствами: конкретной командой, её реальным выводом, файлом и строкой.

Формулировки «проверено», «подтверждено», «исправлено», «работает» без прилагаемого доказательства не являются основанием для присвоения статуса.

Статус **VERIFIED** присваивается системе или её части только тогда, когда независимая проверка — не доверяющая предыдущим отчётам, повторяющая доказательства заново — не находит ни одного расхождения между заявленным и фактическим состоянием кода.
