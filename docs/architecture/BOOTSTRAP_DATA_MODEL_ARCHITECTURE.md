## 1. Назначение модели данных Bootstrap

Дать единое, проверяемое описание того, какие данные должны существовать, чтобы Platform Initialization (Bootstrap) и Platform Ownership могли функционировать, — прежде чем будет написана хотя бы одна строка миграции. Модель данных отвечает на вопросы «что хранится», «как сущности связаны» и «какие переходы состояний допустимы» — не «как это записать в SQL».

---

## 2. Какие сущности участвуют в Bootstrap

- **User Identity** — учётная запись, прошедшая Authentication (`PLATFORM_ACCESS_ARCHITECTURE.md` §5).
- **User Role** — Access-роль пользователя (Administrator/Seller/Courier/Warehouse/Customer).
- **Root Owner** — держатель конечной ответственности за платформу (`PLATFORM_OWNERSHIP_ARCHITECTURE.md` §3).
- **Owner** — делегированный совладелец (`PLATFORM_OWNERSHIP_ARCHITECTURE.md` §4).
- **Platform** — платформа как единица владения в целом.
- **Platform State** — текущее состояние платформы (Not Initialized / Initializing / Operational, `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §14).
- **Bootstrap State** — текущее состояние процесса Bootstrap (ELIGIBLE / CLAIMING / COMPLETED, `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §3).
- **Ownership Transfer** — процесс передачи Root Owner (`PLATFORM_OWNERSHIP_ARCHITECTURE.md` §7, §12) — участвует в модели данных Bootstrap постольку, поскольку использует ту же схему хранения владения (см. `BOOTSTRAP_IMPLEMENTATION_ARCHITECTURE.md` §5, Этап 6 зависит от Этапа 1).

## 4. Какие сущности потребуется добавить

- **Root Owner / Owner** — новая, единая сущность владения (см. §7 — почему единая, а не две отдельные таблицы).
- **Bootstrap State** — новая сущность, представляющая состояние процесса Bootstrap.
- **Platform State** — новое понятие, но, как показано в §7, не требующее отдельного хранения.
- **Ownership Transfer** — новая сущность, представляющая процесс передачи Root Owner.

## 5. Связи между сущностями

```
User Identity  1 ──── 0..N  User Role
User Identity  1 ──── 0..1  Root Owner / Owner   (пользователь либо не владелец, либо ровно одна запись владения)
Root Owner     1 ──── 0..N  Ownership Transfer    (как инициатор)
User Identity  1 ──── 0..N  Ownership Transfer    (как целевая сторона)
Platform       1 ──── 1     Bootstrap State       (ровно одно состояние Bootstrap на всю платформу)
Bootstrap State 1 ──── 1     Platform State        (Platform State полностью определяется Bootstrap State — см. §7)
```

Ключевая связь: **User Identity ↔ Root Owner/Owner — не многие-ко-многим, а ноль-или-один**, в отличие от User Identity ↔ User Role, которая уже сегодня многие-ко-многим (аудит Промпта №034 §2, §12). Это осознанное структурное отличие, а не упрощение: владение — либо есть, либо нет, но одна учётная запись не может быть «Root Owner дважды» или «одновременно Root Owner и Owner» — это два взаимоисключающих статуса одного и того же владельческого измерения (см. §8).

## 6. Жизненный цикл каждой сущности

- **User Identity** — создаётся Supabase Auth при первом входе, живёт всё время существования аккаунта; вне управления Bootstrap.
- **User Role** — создаётся автоматически (`customer` при регистрации) или назначением; независим от Bootstrap, живёт своим циклом, уже описанным в существующей системе.
- **Root Owner/Owner (запись владения)** — создаётся либо через Bootstrap (ровно один раз, для самой первой записи), либо через Ownership Transfer (`ACCEPTED → COMPLETED`); удаляется/меняет статус только через добровольный Transfer или (Owner) прямой отзыв Root Owner-ом (`PLATFORM_OWNERSHIP_ARCHITECTURE.md` §7-8).
- **Bootstrap State** — создаётся один раз, при первом развёртывании платформы, в состоянии `ELIGIBLE`; проходит `ELIGIBLE → CLAIMING → COMPLETED`; после `COMPLETED` не имеет дальнейших переходов (`PLATFORM_INITIALIZATION_ARCHITECTURE.md` §3-4).
- **Platform State** — не имеет собственного независимого жизненного цикла (см. §7) — синхронно отражает Bootstrap State.
- **Ownership Transfer** — создаётся при инициации Root Owner-ом; проходит `PENDING → ACCEPTED → COMPLETED` либо `PENDING → CANCELLED`; после терминального состояния (`COMPLETED`/`CANCELLED`) не изменяется — новая передача владения создаёт новую запись Ownership Transfer, а не переоткрывает старую.

## 7. Архитектура хранения

### Root Owner и Owner
Хранятся **в одной сущности владения** («запись владения»), а не в двух отдельных таблицах: у записи есть ровно одно из двух значений статуса — `ROOT_OWNER` или `OWNER`. Причина единой сущности: обе роли принадлежат одному домену (Platform Ownership), одному и тому же отношению к User Identity (ноль-или-один, см. §5), и различаются только уровнем полномочий (`PLATFORM_OWNERSHIP_ARCHITECTURE.md` §5-6), а не структурой данных. Разделение на две таблицы не даёт архитектурной пользы и дублирует одинаковую по форме информацию.

**Явно не объединяется** со схемой `user_roles`/`app_role` — отдельная сущность, отдельное хранилище (обоснование — `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §7, «ключевое архитектурное решение»: смешение владения и Access-роли в одном enum лишает `AdminFullAccessRule` однозначности).

### Platform
Платформа как единица владения существует в единственном экземпляре (проект — не multi-tenant система, обслуживающая несколько независимых платформ из одной базы данных). Явная сущность «Platform» с собственным идентификатором **не требуется**: всё, что можно было бы у неё спросить («сколько сейчас Root Owner», «в каком она состоянии») — это агрегатные вопросы к записям владения и к Bootstrap State, а не отдельно хранимый факт.

### Platform State
Не хранится как отдельная сущность. Значение (`Not Initialized`/`Initializing`/`Operational`) полностью и однозначно вычисляется из Bootstrap State — сами документы (`PLATFORM_INITIALIZATION_ARCHITECTURE.md` §14) уже приводят их как таблицу с отношением 1:1. Хранение обоих создало бы риск рассинхронизации двух источников истины об одном и том же факте.

### Bootstrap State
**Решено** (`BOOTSTRAP_ARCHITECTURE_REVIEW.md`, замечание №3 — ранее фиксировалось здесь как открытый вопрос с рекомендацией; рекомендация принята как окончательная формулировка, применяемая во всех документах серии, включая `BOOTSTRAP_EXECUTION_FLOW_ARCHITECTURE.md`): **Bootstrap State — вычисляемое значение, не отдельная таблица.** Оно выводится из наличия/отсутствия записей владения со статусом `ROOT_OWNER` (ноль записей → `ELIGIBLE`; хотя бы одна → `COMPLETED`; `CLAIMING` — не отдельно хранимое состояние, а мгновенный переход внутри одной транзакции claim-операции, не наблюдаемый как персистентное состояние между запросами). Причина: не требует отдельной таблицы, невозможна рассинхронизация с фактическим числом Root Owner; момент завершения Bootstrap не нуждается в отдельном столбце, так как тождественен `created_at` самой первой записи владения — это один и тот же факт, а не два независимых.

Рассматривался и отклонён альтернативный вариант — отдельная сущность состояния (единственная строка на всю платформу с явным статусом и меткой времени): даёт немного более явный аудиторский артефакт ценой второго источника истины, который пришлось бы держать синхронным с реальным числом записей владения — то, чего принятое решение избегает по конструкции.

### User Identity
Не хранится в модели данных Bootstrap отдельно — переиспользуется полностью существующий `auth.users` (Supabase Auth), как и сегодня.

### User Role
Не хранится в модели данных Bootstrap отдельно — переиспользуется полностью существующая таблица `user_roles`/enum `app_role`, без изменений её структуры (см. §3).

## 8. Инварианты модели данных

- Ровно 0 или 1 запись владения на одну User Identity (не может быть двух записей владения с одинаковым владельцем).
- Не может существовать запись владения без соответствующей существующей User Identity (владение всегда привязано к реальному аккаунту).
- Число записей владения со статусом `ROOT_OWNER` не может быть равно нулю ни в одном согласованном состоянии данных, кроме как до первого успешного Bootstrap (`Bootstrap State = ELIGIBLE`, где записей владения ещё нет вообще — это единственное легитимное состояние с нулём Root Owner, и оно же тождественно `Platform State = Not Initialized`).
- Запись Ownership Transfer в терминальном состоянии (`COMPLETED`/`CANCELLED`) не может быть изменена.
- Не может существовать более одной записи Ownership Transfer в состоянии `PENDING` для одной и той же целевой стороны одновременно (исключает гонку двух одновременных предложений владения одному и тому же аккаунту).

---

## 9. Требования к целостности данных

- Ссылочная целостность: запись владения и запись Ownership Transfer обязаны ссылаться на существующую User Identity — удаление аккаунта (если оно вообще возможно в системе) обязано быть согласовано с этими ссылками, а не оставлять их «висящими».
- Атомарность перехода Bootstrap: проверка «Root Owner ещё не существует» и создание первой записи владения должны происходить в одной неделимой операции — иначе два одновременных claim-запроса могли бы оба «увидеть» `ELIGIBLE` и оба создать первую запись (классическая TOCTOU-гонка, уже решаемая в проекте атомарными операциями для других сущностей — `ARCHITECTURE_PRINCIPLES.md` CD-02).
- Атомарность завершения Ownership Transfer: переход `ACCEPTED → COMPLETED`, создание новой записи владения для целевой стороны и (при «полной передаче») удаление/понижение записи инициатора — одна неделимая операция, не последовательность независимых записей.
- Согласованность с инвариантом минимума (§8): любая операция, потенциально уменьшающая число `ROOT_OWNER`-записей, обязана проверять итоговое количество в той же атомарной операции, а не полагаться на проверку «до» с отдельной записью «после».

---

## 10. Ограничения модели данных

- Модель не хранит историю смены статуса владения как отдельную сущность «версий записи» — история восстанавливается через Marketplace Events (Audit Log), а не через versioning самой таблицы владения (соответствует уже существующему в проекте разделению: таблицы хранят текущее состояние, `audit-log` — историю событий).
- Модель не предусматривает временного/частичного владения («Root Owner на неделю») — уже зафиксировано как ограничение в `PLATFORM_OWNERSHIP_ARCHITECTURE.md` §10.
- Модель не поддерживает владение, не привязанное к конкретной User Identity (анонимное/групповое владение) — каждая запись владения — это ровно один аккаунт.

## 11. Возможные состояния Bootstrap

Совпадают с уже утверждёнными в `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §3-4, здесь — в терминах данных:

| Состояние | Данные, которые его определяют |
|---|---|
| `ELIGIBLE` | Ноль записей владения со статусом `ROOT_OWNER` |
| `CLAIMING` | Переходное; наблюдаемо только внутри одной атомарной операции claim, не как персистентная строка между запросами |
| `COMPLETED` | Хотя бы одна запись владения со статусом `ROOT_OWNER` существует |

---

## 12. Сценарии изменения состояния данных

- **Первый Bootstrap**: 0 записей владения → claim выполнен атомарно → 1 запись владения (`ROOT_OWNER`) → `Bootstrap State` переходит в `COMPLETED` (вычисляется автоматически, см. §7).
- **Добавление второго Root Owner**: Ownership Transfer создаётся (`PENDING`, «со-владение») → целевая сторона подтверждает (`ACCEPTED`) → атомарно создаётся вторая запись владения (`ROOT_OWNER`), Transfer переходит в `COMPLETED`.
- **Полная передача**: то же самое, но атомарная операция завершения дополнительно изменяет/удаляет запись владения инициатора — с обязательной проверкой инварианта минимума (§8) до применения.
- **Назначение Owner**: одна атомарная операция создаёт запись владения со статусом `OWNER` для целевой User Identity — без Ownership Transfer (одностороннее действие, `PLATFORM_OWNERSHIP_ARCHITECTURE.md` §8).
- **Отзыв Owner**: одна атомарная операция удаляет/деактивирует запись владения со статусом `OWNER` — не затрагивает инвариант минимума (он относится только к `ROOT_OWNER`).
- **Отклонённая попытка уменьшить число Root Owner до нуля**: операция отклоняется целиком, ни одна запись не изменяется (см. §9, «согласованность с инвариантом минимума»).

## 14. Перечень объектов, которые позже потребуют SQL-миграций

Без самих миграций — только список объектов, каждый как отдельная будущая единица работы (Этап 1, `BOOTSTRAP_IMPLEMENTATION_ARCHITECTURE.md` §4):

1. Новый тип перечисления для статуса владения (`ROOT_OWNER` / `OWNER`) — отдельный от существующего `app_role`.
2. Новая таблица записей владения — ссылка на `auth.users`, статус владения, уникальность «одна запись владения на одну User Identity» (см. Инвариант §8).
3. Новый тип перечисления для состояний Ownership Transfer (`PENDING` / `ACCEPTED` / `COMPLETED` / `CANCELLED`).
4. Новая таблица Ownership Transfer — ссылка на инициатора и целевую сторону (обе — `auth.users`), состояние, выбор «со-владение»/«полная передача», временные метки создания/подтверждения/завершения.
5. Ограничение уникальности «не более одной записи Ownership Transfer в состоянии `PENDING` на одну целевую сторону» (см. §8).
6. Атомарная операция (по образцу уже существующих в проекте атомарных функций — `ARCHITECTURE_PRINCIPLES.md` CD-02) для claim-перехода Bootstrap.
7. Атомарная операция для завершения Ownership Transfer (создание/изменение записей владения + переход состояния Transfer одной неделимой операцией).
8. Явное подтверждение фактического состояния уже существующей миграции `admin_scopes` в боевой БД — не новый объект, но обязательный пункт, закрываемый до начала работы над пп. 1-7 (Этап 0 плана внедрения).

Ни «Bootstrap State», ни «Platform State», ни «Platform» как таковые — **не входят** в этот список: согласно §7, они не требуют собственных таблиц.

---

Это исключительно архитектурный документ. Код, SQL, миграции, существующие архитектурные документы не изменялись, коммит и деплой не выполнялись.
