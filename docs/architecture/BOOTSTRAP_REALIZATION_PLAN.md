# Bootstrap Realization Plan

| Поле | Значение |
|---|---|
| **Тип документа** | Окончательный технический план реализации, не архитектура |
| **Дата** | 2026-08-03 |
| **Проект** | «Местный Базар» (Everyday Eats Hub) |
| **Основание** | Все 8 утверждённых документов Bootstrap Architecture v2.0, согласованных в `BOOTSTRAP_ARCHITECTURE_REVIEW.md` и `BOOTSTRAP_ARCHITECTURE_REVIEW.md`-рефакторинге (Промпт №043) |
| **Роль документа** | Технический, исполняемый план — что именно будет создаваться, в каком порядке, с какими критериями готовности и отката. Сам не содержит реализации. |
| **Реализация** | Запрещена. Ни кода, ни SQL, ни миграций документ не содержит. |

Этот документ не вводит новых модулей, не меняет архитектурные решения, модель данных, роли или диаграммы, зафиксированные в восьми утверждённых документах серии. Он переизлагает уже утверждённую дорожную карту `BOOTSTRAP_IMPLEMENTATION_ARCHITECTURE.md` §4 (8 этапов: 0-7) в виде 5 укрупнённых, готовых к исполнению фаз (Этап 0-4) — соответствие показано в §0 ниже. Ни один этап исходной дорожной карты не пропущен и не переставлен местами.

## 0. Соответствие этапов

| Этап этого плана | Соответствует этапам `BOOTSTRAP_IMPLEMENTATION_ARCHITECTURE.md` §4 |
|---|---|
| Этап 0 — Готовность | Этап 0 |
| Этап 1 — Фундамент данных и Platform Core | Этапы 1 (схема Platform Ownership) + 2 (домен Ownership в Platform Core) |
| Этап 2 — Bootstrap (Platform Initialization) | Этап 3 |

Причина укрупнения: каждая из пяти фаз этого плана — минимальный набор изменений, дающий цельный, самостоятельно проверяемый прирост функциональности (что и требуется этим промптом), тогда как исходная восьмиэтапная разбивка описывала архитектурные зависимости на более мелком зерне (что требовалось `BOOTSTRAP_IMPLEMENTATION_ARCHITECTURE.md`). Зависимости между этапами не изменены — только сгруппированы.

## 1. Общая стратегия реализации

1. **Аддитивность на каждом шаге.** Ни один этап не изменяет существующую таблицу, существующий сервис или существующий guard — только добавляет новые, рядом стоящие (принцип уже зафиксирован в `PLATFORM_CORE_ARCHITECTURE.md` §10).
2. **Каждый этап — самостоятельный деплой.** Ни один этап не требует, чтобы следующий этап уже существовал в проде для того, чтобы текущий этап был признан завершённым.
3. **Проверяемость прежде продвижения.** Ни один этап не начинается, пока предыдущий не прошёл полный набор проверок (typecheck/lint/test/build/Architecture Guard) и не подтверждён в проде (там, где это применимо).
4. **Пользователь не видит новых возможностей до готовности.** До Этапа 3 ни один реальный пользователь платформы не взаимодействует с новым кодом — весь новый бэкенд Этапов 1-2 не имеет ни одной точки вызова из существующих пользовательских сценариев.
5. **Откат — не исключение, а спроектированное свойство каждого этапа** (см. критерии отката в каждом этапе ниже) — потому что аддитивная природа изменений делает откат дешёвым по конструкции, а не по счастливой случайности.

## 2. Этап 0 — Готовность

**Цель.** Убедиться, что фактическое состояние репозитория и боевой БД соответствует предположениям всех восьми архитектурных документов, прежде чем создавать первую миграцию.

**Входные условия.** Все 8 документов Bootstrap Architecture v2.0 утверждены (см. `BOOTSTRAP_ARCHITECTURE_REVIEW.md`, итоговое заключение — готовность подтверждена).

**Выходные условия.** Зафиксирован письменно (в отчёте по этапу, не в архитектурном документе) фактический статус миграции `admin_scopes` в боевой БД — задеплоена она или нет. Открытых вопросов о текущем состоянии схемы не остаётся.

**Изменяемые компоненты.** Ни один — это проверочный этап, ноль изменений кода/схемы.

**Архитектурные зависимости.** Нет — этот этап не зависит ни от чего внутри Bootstrap-архитектуры, только от текущего состояния боевой инфраструктуры.

**Критерии готовности.** Отчёт о фактическом состоянии `admin_scopes` предоставлен; иных предположений о текущей схеме, не проверенных напрямую, не осталось.

**Критерии отката.** Неприменимо — этап не производит изменяемых артефактов, откатывать нечего.

## 3. Этап 1 — Фундамент данных и Platform Core (Ownership-домен)

**Цель.** Создать хранилище и доменный сервис для Platform Ownership, не подключая их ни к одному существующему пользовательскому сценарию.

**Входные условия.** Этап 0 завершён; решение по хранению Bootstrap State зафиксировано как окончательное (`BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md` §7 — вычисляемое значение).

**Выходные условия.** Существует новая, изолированная таблица(-ы) записи владения и Ownership Transfer (`BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md` §14, пп. 1-5); существует доменный сервис Platform Ownership, порт и репозиторий, зарегистрированные в Composition Root; ни один существующий сервис/executor их не вызывает.

**Изменяемые компоненты.**
- Новая миграция (аддитивная, только `CREATE TYPE`/`CREATE TABLE` — см. `BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md` §14, пп. 1-5).
- Новый доменный сервис Platform Ownership (`server/domain/`), новый порт (`server/ports/`), новый адаптер репозитория (`server/adapters/supabase/`).
- Регистрация в `server/di/container.ts` (добавление, не изменение существующих строк).

**Архитектурные зависимости.** Зависит от Этапа 0 (уверенность в текущей схеме). Ничто последующее (Этапы 2-4) не может начаться раньше этого этапа — Bootstrap, Access и UI все читают/пишут через этот сервис.

**Критерии готовности.** Миграция применена (только с явного разрешения — постоянное правило проекта) и подтверждена; сервис/порт/репозиторий покрыты тестами на уровне контракта порта (паттерн `fake<Port>()`, `ARCHITECTURE_PRINCIPLES.md` CD-09); typecheck/lint/test/build/guard — зелёные; ни один существующий вызов в проекте не использует новый сервис (проверяется отсутствием изменений в уже существующих файлах, не считая `container.ts`).

**Критерии отката.** Поскольку ничто не вызывает новый сервис, откат — удаление новых файлов и `DROP` новых, ничем не заполненных таблиц (данных для потери нет, так как ни один пользователь ещё не мог создать запись владения). Самый дешёвый откат из всех пяти этапов.

## 4. Этап 2 — Bootstrap (Platform Initialization)

**Цель.** Реализовать claim-операцию и события Bootstrap, доступные только через прямой вызов API (без UI), поверх сервиса Этапа 1.

**Входные условия.** Этап 1 завершён и подтверждён в проде.

**Выходные условия.** Claim-операция работает через полный трёхслойный API (`server/functions/*.executor.ts → src/api/*.functions.ts → src/api/*.ts`); инвариант «минимум один Root Owner» и атомарность (`BOOTSTRAP_EXECUTION_FLOW_ARCHITECTURE.md` §11) реализованы и покрыты тестами; событие `system.bootstrap.completed` публикуется и потребляется Audit Log.

**Изменяемые компоненты.**
- Атомарная операция БД (проверка + запись, по образцу `ARCHITECTURE_PRINCIPLES.md` CD-02) — новая, не модифицирует существующие RPC-функции.
- Новый executor/API-функция claim.
- Новый тип события в дискриминированном union `MarketplaceEvent` (`server/ports/marketplace-events.port.ts`) — добавление варианта, не изменение существующих.
- Подписка Audit Log на новое событие (добавление подписчика, существующие подписки не трогаются).

**Архитектурные зависимости.** Зависит от Этапа 1 (сервис/таблицы владения). Не зависит от Этапа 3 (Access может быть реализован до или после этого этапа — см. `BOOTSTRAP_IMPLEMENTATION_ARCHITECTURE.md` §7).

**Критерии готовности.** Полный набор тестов на все переходы состояний (`ELIGIBLE→CLAIMING→COMPLETED`, гонка двух claim, попытка после `COMPLETED` — `BOOTSTRAP_EXECUTION_FLOW_ARCHITECTURE.md` §6-7) зелёный; typecheck/lint/test/build/guard — зелёные; claim по-прежнему недоступен ни из одного пользовательского интерфейса (UI ещё не существует до Этапа 3).

**Критерии отката.** Так как UI ещё не существует, единственный вызывающий — прямой API-вызов/тест. Откат — отключение executor'а и удаление нового варианта события из union (при условии, что ни одна реальная claim-операция ещё не была совершена в проде; если совершена — откат этого этапа уже недопустим, так как это означало бы потерю уже созданного Root Owner, что запрещено инвариантом минимума, — в этом случае откат этапа технически невозможен и не должен предприниматься).

## 5. Этап 3 — Access и интерфейс

**Цель.** Сделать владельческий статус видимым для Platform Access и дать людям реальный, работающий через UI способ пройти Bootstrap и управлять владением.

**Входные условия.** Этапы 1-2 завершены и подтверждены в проде.

**Выходные условия.** `Role Resolution` возвращает владельческий статус наравне с Access-ролями, не меняя поведения ни одного существующего `require<Role>FromRequest()`; экран Bootstrap показывается только при `ELIGIBLE`; раздел управления владением в `/admin` отображает реальные данные.

**Изменяемые компоненты.**
- Расширение существующей функции разрешения ролей (`server/auth/resolve-user.ts`) — добавление чтения владельческого статуса, без изменения сигнатур существующих `require<Role>FromRequest()`.
- Новый маршрут UI — экран Bootstrap (показывается только при `ELIGIBLE`, серверная проверка при каждом обращении — `BOOTSTRAP_EXECUTION_FLOW_ARCHITECTURE.md` §11 способ снижения риска).
- Новый раздел внутри уже существующей административной панели (`/admin`) — аддитивное расширение, ни один существующий экран не переписывается.

**Архитектурные зависимости.** Зависит от Этапов 1-2 (нечего показывать и не с чем работать без них). Не имеет обратной зависимости — существующие Workspace продолжают работать без знания об этом этапе.

**Критерии готовности.** Регрессионный набор тестов на существующие `require<Role>FromRequest()` подтверждает нулевое изменение их поведения; экран Bootstrap не показывается после `COMPLETED` ни при каких условиях (проверено тестами, не только вручную); typecheck/lint/test/build/guard — зелёные; ручная проверка обеих точек входа (см. ниже, «интеграционные и E2E тесты»).

**Критерии отката.** Откат UI — удаление нового маршрута и раздела `/admin`, без следов в остальном интерфейсе (аддитивность). Откат расширения Role Resolution — безопасен только если ни одно из уже существующих решений о доступе не начало полагаться на владельческий статус (что в этом плане и не предполагается — Access-роли и Ownership проверяются независимо, `PLATFORM_ACCESS_ARCHITECTURE.md` §11).

## 6. Этап 4 — Transfer Root Ownership и финальный аудит

**Цель.** Реализовать постоянно доступную операцию передачи владения и провести финальную сверку кода с документацией.

**Входные условия.** Этапы 1-3 завершены; в проде существует как минимум один реальный Root Owner (Bootstrap уже пройден хотя бы одним разом).

**Выходные условия.** Transfer Root Ownership проходит полный жизненный цикл (`PENDING → ACCEPTED → COMPLETED` и `PENDING → CANCELLED`); все 8 архитектурных документов сверены с фактическим кодом построчно; Architecture Guard — PASS.

**Изменяемые компоненты.**
- State machine Ownership Transfer (использует таблицу Этапа 1, новый доменный код).
- События `ownership.transfer.initiated/accepted/completed/cancelled` — новые варианты union, добавление подписки Audit Log и Notification Center (уведомление всех Root Owner, `PLATFORM_OWNERSHIP_ARCHITECTURE.md` §15, п.5).
- UI инициации/подтверждения Transfer внутри раздела владения (Этап 3).
- Финальный аудиторский отчёт (не код).

**Архитектурные зависимости.** Зависит от всех предыдущих этапов — использует ту же схему и сервис владения (Этап 1), тот же принцип атомарности (Этап 2), тот же UI-раздел (Этап 3).

**Критерии готовности.** Полное тестовое покрытие state machine, включая инвариант минимума при попытке «полной передачи» последнего Root Owner; уведомление всех Root Owner подтверждено тестом; итоговый CTO-аудит не выявил расхождений между документами и кодом (или расхождения зафиксированы явно, не скрыты); Architecture Guard — PASS.

**Критерии отката.** Откат Transfer-функциональности возможен только для записей в состоянии `PENDING`/`CANCELLED` (терминальных `COMPLETED`-передач откат недопустим — они уже изменили состав Root Owner, откатывать их означало бы принудительно отзывать чей-то владельческий статус, что запрещено инвариантом `PLATFORM_OWNERSHIP_ARCHITECTURE.md` §14). Финальный аудит отката не требует — он не производит изменяемых артефактов кода.

## 7. Порядок создания по типам артефактов (применяется внутри каждого этапа, где эти артефакты присутствуют)

```
1. SQL-миграция            (аддитивная, только там, где этап её вводит — Этапы 1, 4)
        ↓
2. Backend (домен/порт/репозиторий)
        ↓
3. API (executor → server function → клиентская обёртка, 3-слойный паттерн)
        ↓
4. Permission Policy         (только если этап затрагивает Rule Engine — Этап 3, расширение Role
                              Resolution; Bootstrap-claim сам не проходит через PermissionPolicyService,
                              см. PLATFORM_OWNERSHIP_ARCHITECTURE.md §3)
        ↓
5. Интеграционные тесты     (пишутся параллельно с Backend/API, не после UI)
        ↓
6. UI                        (только Этапы 3-4)
        ↓
7. E2E тесты                 (только там, где существует UI — Этапы 3-4; для Этапов 1-2, не
                              имеющих UI, вместо E2E — сценарные тесты на уровне API)
```

Обоснование порядка: миграция должна существовать прежде, чем на неё сможет опереться домен; домен — прежде API; API — прежде Permission Policy (которая ссылается на модуль/контекст, уже определённый API-слоем); интеграционные тесты пишутся сразу за Backend/API, не дожидаясь UI, чтобы логика была проверена до того, как на неё будет надстроен интерфейс; UI — последним слоем, поскольку он лишь отображает то, что уже работает и проверено; E2E — после UI, так как без него нечего проходить сквозным сценарием.

## 8. Архитектурные риски по этапам и способы контроля

| Этап | Риск | Способ контроля |
|---|---|---|
| 0 | Неверное предположение о текущем состоянии схемы (`admin_scopes`) искажает планирование Этапа 1 | Прямая проверка боевой БД перед началом Этапа 1, зафиксированная письменно, не принимаемая на веру |
| 1 | Конфликт имён новых объектов схемы с существующими | Сверка имён с полным перечнем существующих объектов перед написанием миграции |
| 1 | Сервис спроектирован без реального потребителя — тесты могут проверять только форму интерфейса, не реальное поведение | Тесты пишутся против сценариев, уже описанных в `BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md` §12 («Сценарии изменения состояния данных»), а не только против сигнатур методов |
| 2 | Гонка двух одновременных claim-запросов создаёт двух «первых» Root Owner | Атомарная операция БД (проверка + запись в одной транзакции), тест на конкурентный вызов обязателен до перехода к Этапу 3 |
| 2 | Некорректная реализация инварианта минимума пропускает состояние с нулём Root Owner | Явный тестовый набор на все граничные переходы (0→1, попытка 1→0 отклонена) прежде подключения к реальному API |
| 3 | Расширение Role Resolution случайно меняет поведение существующих `require<Role>FromRequest()` | Обязательный регрессионный прогон существующих guard-тестов перед завершением этапа, а не только новых тестов |
| 3 | Экран Bootstrap остаётся доступным дольше, чем должен (после `COMPLETED`) | Проверка состояния на сервере при каждом обращении к экрану, без клиентского кэширования — не полагаться на однократную проверку при загрузке |
| 4 | Некорректная state machine Transfer допускает передачу без согласия целевой стороны или обнуляет Root Owner | Тесты на полный набор переходов, включая явно отклонённые попытки; инвариант минимума проверяется в той же атомарной операции завершения Transfer |
| 4 | Финальный аудит проводится формально, не вскрывая реальных расхождений | Построчная сверка кода с документами по методологии, уже применённой в Промпте №034, а не пересказ документов |

## 9. Финальная дорожная карта реализации

```
Этап 0 ─── Готовность
   │        (проверка admin_scopes, без изменений)
   ▼
Этап 1 ─── Фундамент данных и Platform Core
   │        (миграция + домен Ownership, без потребителей)
   ▼
Этап 2 ─── Bootstrap
   │        (claim-операция, инвариант минимума, событие completion)
   ▼
Этап 3 ─── Access и интерфейс
   │        (Role Resolution + экран Bootstrap + раздел владения в /admin)
   ▼
Этап 4 ─── Transfer Root Ownership + финальный CTO-аудит
            (state machine передачи владения + построчная сверка с документами)
```

Каждая стрелка — отдельный, самостоятельно проверяемый деплой с полным набором проверок (typecheck/lint/test/build/Architecture Guard) и, где применимо, отдельным решением о применении миграции.
