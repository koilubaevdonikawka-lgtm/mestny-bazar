## 1. Назначение

Architecture Guard — обязательная система защиты архитектуры проекта «Местный Базар». Её задача — не дать ни одному изменению попасть в commit, если оно нарушает уже принятые архитектурные решения, независимо от того, насколько срочна или мала задача.

Architecture Guard решает конкретную, ранее не закрытую проблему проекта: до этого документа единственным механизмом защиты архитектуры был ручной, неформализованный аудит, проводимый от случая к случаю (см. `ARCHITECTURE_AUDIT.md` — обнаруженный постфактум орфанный composition root на ~4600 файлов, накопившийся именно потому, что не существовало обязательной, повторяемой проверки на каждом шаге). Architecture Guard превращает этот аудит в обязательный, повторяемый шаг, встроенный в последовательность закрытия каждого этапа (см. §3 и `IMPLEMENTATION_ORDER.md`, «Итоговое условие»), а не в разовое действие, которое можно забыть выполнить.

Architecture Guard не заменяет `typecheck`/`lint`/`tests`/`build` — эти проверки ловят синтаксические, типовые и поведенческие ошибки. Architecture Guard ловит то, что типизация и тесты в принципе не могут поймать: правильно типизированный, проходящий все тесты код, который тем не менее нарушает границы слоёв, дублирует Composition Root или принимает архитектурное решение без ADR там, где ADR обязателен.

Architecture Guard не вводит собственных критериев — он **проверяет соответствие** уже существующим источникам, перечисленным ниже в порядке убывания авторитетности. При противоречии между источниками ниже правым считается более авторитетный.

| 2 | [`ARCHITECTURE_POLICY.md`](./ARCHITECTURE_POLICY.md) | Продуктовая архитектурная политика: стабильное ядро, независимость модулей, принцип «расширяй, не заменяй» (`POL-14`) |

## 3. Обязательные проверки

Ниже — 13 обязательных категорий проверки. Для каждой указано, что проверяется, и что считается критическим нарушением (== немедленный `FAIL`, не предупреждение). Пометка **[скрипт]** означает, что проверка (полностью или частично) выполняется автоматически `scripts/architecture-guard.mjs` (`npm run guard`); пометка **[ручная]** — проверка требует смыслового решения (архитектурного суждения), которое не сводится к поиску по тексту, и выполняется тем, кто закрывает этап (сегодня — AI-агентом, ведущим Prompt-последовательность, по этому чек-листу).

### 3.1 Architecture Principles — **[ручная + частично скрипт]**

**Что проверяется:** каждое новое или изменённое архитектурное решение сверяется построчно с `ARCHITECTURE_PRINCIPLES.md`. В частности: PL-01 (frontend — только через Platform API), PL-03 (Dependency Rule — domain не зависит от adapters), PL-04 (DTO Contracts — никаких DB/provider-типов на фронтенде), PL-07 (секреты не покидают сервер), CD-01 (клиентским бизнес-данным не доверяют).

**Критическое нарушение:** любое изменение, которое `git diff` показывает как противоречащее конкретному `PL-*`/`CD-*` пункту без зафиксированного решения пересмотреть сам принцип.

### 3.2 ADR — **[ручная]**

**Что проверяется:** любое решение, подпадающее под таблицу «когда ADR обязателен» (`docs/principles/14-architecture-decision-record.md`, PL-14) — новый внешний провайдер, изменение правила импорта между слоями, прямой доступ фронтенда к БД/API — сопровождается новым ADR (`docs/architecture/adr/ADR-NNN-*.md`) **до**, не после, commit.

**Критическое нарушение:** решение, меняющее границу между слоями или добавляющее нового внешнего провайдера, реализовано без ADR. (Существующий пробел — отсутствие ADR на удаление орфанного composition root и на усиление ESLint-границ внутри `server/**`, см. `ADR_INDEX.md` — уже зафиксирован как известный, не новый; Architecture Guard не требует его задним числом закрывать, но требует не создавать новых пробелов того же рода).

### 3.3 Domain Boundaries — **[скрипт: Check 1]**

**Что проверяется:** `server/domain/**` не импортирует `server/adapters/**` напрямую (PL-03, Dependency Rule) — единственный путь к внешней системе для domain-сервиса — через порт (`server/ports/*`), реализация подставляется в `server/di/container.ts`.

**Критическое нарушение:** `import` из `@server/adapters/*` (или относительным путём `../adapters/*`) внутри любого файла `server/domain/**`, кроме `*.test.ts` (тестам разрешён прямой импорт мапперов адаптеров для их точечного юнит-тестирования, см. `CD-06`).

### 3.4 Ports & Adapters — **[ручная + частично скрипт]**

**Что проверяется:** каждая новая внешняя зависимость domain-сервиса выражена как интерфейс в `server/ports/` **до** написания реализующего его адаптера (PL-02). Adapter владеет деталями конкретного провайдера (Supabase-специфичные имена колонок, HTTP-детали Finik) — ни одна из этих деталей не протекает в domain или во frontend (PL-04, PL-08).

**Критическое нарушение:** domain-сервис, принимающий конкретный класс адаптера в конструкторе вместо интерфейса порта; DTO в `shared/contracts/` с полем, названным в честь провайдера (пример хардкода недопустим: `finik_payment_url` вместо `paymentUrl`).

### 3.5 Dependency Injection (Composition Root) — **[скрипт: Check 2, Check 7]**

**Что проверяется:** вся композиция зависимостей происходит только в `server/di/container.ts` (PL-05). Ни один domain-файл не создаёт адаптер через `new`; ни один файл вне `server/di/` не собирает цепочку из нескольких `new *Rule()` — это был бы кандидат на второй, параллельный composition root (тот самый класс ошибки, который привёл к орфанному дереву на ~4600 файлов, см. `ARCHITECTURE_AUDIT.md`).

**Критическое нарушение:** `new Supabase*Repository(...)`, `new FinikPaymentAdapter(...)` или аналогичный конструктор адаптера внутри `server/domain/**`; отдельный `factory.ts`, собирающий Policy-сервисы вне `container.ts`.

### 3.6 Rule Engine — **[скрипт: Check 5, частично; ручная — порядок и корректность правил]**

**Что проверяется:** каждый `*.rule.ts` реализует стандартную форму (Принцип 12): `order: number`, `applies(context): boolean`, `evaluate(context): Result`, опционально `terminal?: boolean` (по умолчанию `true`). Порядок правил в `container.ts` не противоречит именованным константам `*PolicyOrder`. Семантика движка: `!allowed` → немедленный отказ независимо от `terminal`; `allowed && terminal !== false` → немедленное разрешение; иначе — следующее правило; если ни одно правило не сработало — отказ с `NO_MATCHING_RULE`.

**Критическое нарушение:** захардкоженное условие вида `if (paymentMethod === "CASH")` внутри orchestrator-сервиса (`CheckoutService`, `OrderService`) вместо делегирования в соответствующий `*PolicyService`; правило без одного из обязательных методов; ручная (не через движок) проверка бизнес-условия, которая должна была пройти через Rule Engine.

### 3.7 Marketplace Events — **[ручная]**

**Что проверяется:** новое событие добавлено в `MarketplaceEvent` union (`server/ports/marketplace-events.port.ts`) с точным набором полей, подписчики зарегистрированы явно в `server/di/container.ts` (`subscribeX(marketplaceEvents, ...)`), Audit Log расширен на новое событие, если оно значимо для журнала.

**Критическое нарушение:** модуль публикует данные напрямую в другой модуль (прямой вызов сервиса вместо события) там, где `dependency-map.md` требует событийной связи; новое событие объявлено, но ни один подписчик не зарегистрирован (событие «в пустоту»).

### 3.8 Database — **[ручная]**

**Что проверяется:** каждая новая таблица/колонка сопровождается миграцией в `supabase/migrations/` **и** соответствующим обновлением `src/integrations/supabase/types.ts` (ручной синхронизации типов с реальной схемой, поскольку миграции этой сессией не применяются к реальной БД — см. правило ниже); RLS включён на каждой новой таблице с политикой, соответствующей ролевой модели; TOCTOU-чувствительные операции (одновременное чтение-затем-запись) реализованы как атомарная Postgres-функция (`CD-02`), а не как отдельные `SELECT`+`UPDATE` из кода.

**Критическое нарушение:** новая таблица без RLS; новая колонка в `types.ts` без соответствующей миграции (или наоборот); check-then-act операция, уязвимая к гонке двух одновременных запросов, реализованная без атомарной RPC-функции.

> **Отдельное, непреложное правило этого проекта:** миграции пишутся на диск, но **никогда не применяются** к реальной базе данных без явного разрешения пользователя. Architecture Guard проверяет только *наличие и корректность* файла миграции, не факт его применения.

### 3.9 API — **[ручная]**

**Что проверяется:** трёхслойный паттерн соблюдён на каждом новом эндпоинте: `server/functions/*.executor.ts` (проверка роли + вызов бизнес-логики) → `src/api/*.functions.ts` (`createServerFn` + zod-валидатор) → `src/api/*.ts` (тонкая клиентская обёртка). Каждый admin-only executor вызывает `require<Role>FromRequest()` **до** любой бизнес-логики. Входные данные валидируются zod-схемой на границе `*.functions.ts`, не полагаясь на TypeScript-типы времени компиляции (которые исчезают в рантайме на границе сети).

**Критическое нарушение:** `server/functions/*.executor.ts`, вызывающий бизнес-логику до проверки роли; `createServerFn` без `.validator()` там, где принимает пользовательский ввод; клиентский код, обращающийся к серверной логике в обход `src/api/`.

### 3.10 Frontend — **[ручная + частично скрипт]**

**Что проверяется:** `src/**` (кроме `src/api/`, `src/integrations/`) импортирует только `shared/contracts/` и `src/api/*` — никогда `@supabase/supabase-js` напрямую, никогда `server/**` (PL-01, PL-06). Новые admin-маршруты используют общий `AdminLayout` (Этап 1, `docs/admin-platform/IMPLEMENTATION_ORDER.md`), а не собственный, изобретённый заново каркас.

**Критическое нарушение:** компонент в `src/routes/**` (вне `src/integrations/`), напрямую импортирующий `@supabase/supabase-js` или файл из `server/`; новый admin-экран без `AdminLayout`.

### 3.11 Security — **[скрипт: Check 4; ручная — RLS-политики и ролевая модель]**

**Что проверяется:** ни одно серверное имя переменной окружения (`SUPABASE_SERVICE_ROLE_KEY`, `FINIK_API_KEY`, `TELEGRAM_BOT_TOKEN`) не встречается в коде, реально достижимом клиентским бандлом (PL-07); каждый защищённый ресурс проверяется как минимум одним `require<Role>FromRequest()`; RLS-политики на новых таблицах соответствуют ролевой модели (`private.has_role(auth.uid(), 'role')`, не устаревший `public.has_role`, удалённый миграцией `20260706112303`).

**Критическое нарушение:** секрет, буквально встречающийся в файле, достижимом клиентским бандлом (кроме документированных, поименованных исключений — `*.server.ts`-файлы и `src/lib/shopify.ts`'s `SHOPIFY_STOREFRONT_TOKEN`, см. комментарий в `scripts/architecture-guard.mjs`); новая таблица без RLS или с политикой `USING (true)` без обоснования.

### 3.12 Order Lifecycle — **[ручная]**

**Что проверяется:** любое изменение, затрагивающее статусы заказа или переходы между ними, проходит через `OrderLifecycleService`/`IOrderLifecyclePolicy` (единственный источник истины о допустимых переходах), не добавляет прямую проверку статуса в orchestrator-сервисе; буфер отмены и операционный каскад (`platform-lifecycle.md`, §3) остаются реализованными как ленивый идемпотентный sweep (нет cron/scheduler на Cloudflare Workers), а не как фоновый таймер, которого платформа не может гарантировать.

**Критическое нарушение:** новый переход статуса заказа, добавленный в обход `OrderLifecycleService` (например, прямой `UPDATE orders SET status = ...` из нового кода); нарушение инварианта «покупатель не уведомляется о начале операционной обработки, пока не истёк буфер отмены» (`platform-lifecycle.md`, §3).

### 3.13 Documentation — **[ручная]**

**Что проверяется:** `IMPLEMENTATION_ORDER.md` отражает фактически реализованное (не декларативно ожидаемое) по завершении этапа — списки файлов/API/модулей уточнены по факту, добавлена секция «Известные ограничения», если объём осознанно сужен. Каждый изменённый документ `docs/admin-platform/*.md`/`docs/architecture/*.md` сохраняет корректность перекрёстных ссылок (`dependency-map.md`, «Как пользоваться этой картой» — правки контракта требуют пересмотра связанных документов в тот же заход, не отложенно).

**Критическое нарушение:** этап помечен как `✅ Выполнен` в `IMPLEMENTATION_ORDER.md`, когда `typecheck`/`lint`/`tests`/`build`/Architecture Guard не пройдены; документ модуля противоречит `ADMIN_PLATFORM_MASTER_SPEC.md` без пометки о преднамеренном расхождении.

## 4. Финальное решение

Architecture Guard выдаёт **только одно из двух** решений — компромиссных или частичных состояний не существует:

```
☑ PASS
```

или

```
❌ FAIL
```

### Условие PASS

Все 13 категорий §3 пройдены: автоматическая часть (`npm run guard`) завершается кодом `0`, и ручная часть чек-листа не выявила ни одного критического нарушения, перечисленного в соответствующих подпунктах.

### Условие FAIL

Если хотя бы одна категория содержит критическое нарушение — Architecture Guard обязан выдать `FAIL` и перечислить **всё** нижеследующее, без сокращений:

1. **Нарушенные документы** — какой именно источник истины из §2 нарушен (например: `ARCHITECTURE_PRINCIPLES.md`).
2. **Нарушенные принципы** — конкретный идентификатор (например: `PL-03`, `CD-02`, `POL-04`) с точной формулировкой из источника.
3. **Нарушенные файлы** — полный путь к каждому файлу, содержащему нарушение, со строкой/фрагментом, если применимо.
4. **Причина запрета commit** — одно-два предложения, объясняющие, что конкретно сломается или станет невозможным (не абстрактное «нарушает архитектуру»), если это изменение попадёт в commit как есть.

**При FAIL commit запрещён безусловно.** Ни срочность задачи, ни объём уже проделанной работы не являются основанием обойти этот запрет — исправляется нарушение (или, если нарушение принципа осознанно и оправданно, сначала пишется новый ADR/пересматривается сам принцип отдельным, явным решением — см. §3.2), после чего Architecture Guard запускается заново.

## 5. Пример формата отчёта FAIL

```
❌ FAIL

Нарушенные документы:
  - ARCHITECTURE_PRINCIPLES.md

Нарушенные принципы:
  - PL-03 (Dependency Rule): "Domain depends on ports, but never on concrete adapters."

Нарушенные файлы:
  - server/domain/payout.service.ts:14 — прямой импорт
    `@server/adapters/supabase/payout.repository` вместо `@server/ports/payout.repository`

Причина запрета commit:
  PayoutService перестаёт быть тестируемым через fake-порт и жёстко привязывается
  к Supabase — замена провайдера потребует правки domain-кода, что напрямую
  нарушает PL-09 (Replaceable Adapters).
```

## 6. Ограничения Architecture Guard (честно задокументированы)

- Скрипт (`scripts/architecture-guard.mjs`) — это набор статических, текстовых проверок (grep-подобных), а не полноценный статический анализатор с построением графа импортов или AST. Он ловит прямые нарушения текстом импорта/конструктора, но не более сложные обходы (например, динамический `import()` строки, собранной во время выполнения). Это осознанный, задокументированный компромисс, а не скрытый пробел.
- Ручная часть чек-листа (§3.2, 3.7–3.10 частично, 3.12, 3.13) требует архитектурного суждения и выполняется тем, кто закрывает этап — сегодня AI-агентом, ведущим Prompt-последовательность, по этой самой инструкции.
