## 1. Назначение Platform Core

Platform Core — постоянно работающее инфраструктурное ядро платформы «Местный Базар». Его назначение: предоставлять один общий, предметно-нейтральный набор сервисов (идентичность, права, владение, события, аудит, конфигурация, уведомления, AI), которым пользуется любое рабочее пространство (Workspace), не зная и не заботясь о том, что это за пространство — покупательское, продавцовское, курьерское, складское или административное.

Platform Core существует, чтобы платформа могла расти числом Workspace без роста сложности самого ядра.

---

## 2. Цели Platform Core

1. **Один источник истины для идентичности и прав** — ни один Workspace не реализует свою собственную схему ролей, авторизации или аудита.
2. **Стабильность.** Core должен оставаться работоспособным и неизменным при добавлении, изменении или отключении любого Workspace.
3. **Предметная нейтральность.** Core ничего не знает о товарах, заказах, доставке, складе — только об абстракциях «актор», «право», «событие», «конфигурация».
4. **Расширяемость без модификации.** Новый Workspace подключается к Core через уже существующие точки расширения, не требуя правок внутри Core (см. §10, §12).
5. **Отделённость от Platform Initialization.** Core начинает свою постоянную работу независимо от того, как именно был создан первый Root Owner — Bootstrap для него не более чем один из способов, которым в его данных появилась запись владения (см. `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §13, §17).

---

## 3. Что такое Platform Core

Platform Core — это не сервис в смысле «один процесс» и не отдельный деплой. Это архитектурный слой: совокупность доменных сервисов, портов, адаптеров и Composition Root, которые не принадлежат ни одному конкретному Workspace, а обслуживают их все одновременно.

**Сопоставление с уже существующим кодом** (перенос понятий поверх уже существующей структуры, не новый код — детальный перечень в §5):
- Сегодня всё это физически живёт внутри общего `server/` наравне с бизнес-доменами Workspace'ов, без явного структурного разделения на два слоя. Это ожидаемо и честно фиксируется как факт: Architecture v2.0 вводит это деление концептуально; последующая реализация (не предмет этого документа) должна привести физическую структуру `server/` в соответствие с ним.

---

## 4. Границы ответственности Platform Core

Platform Core отвечает за вопросы вида **«кто это», «что ему разрешено», «кому принадлежит платформа», «что произошло», «как это настроено», «кого уведомить», «какую AI-операцию выполнить»** — универсально, для любого Workspace.

Platform Core не отвечает на вопросы вида **«что лежит в корзине», «сколько стоит доставка до этого района», «какой статус у этого заказа», «прошёл ли этот товар модерацию»** — это исключительно ответственность конкретного Workspace.

Граница проходит не по файлам и не по папкам, а по предмету: если сервис одинаково необходим и полезен для Customer Workspace, и для Seller Workspace, и для Courier Workspace без каких-либо предметных изменений в нём самом — это Platform Core. Если сервис содержит хотя бы одно правило, специфичное для конкретной бизнес-вертикали — это Workspace.

## 5. Что входит в Platform Core

### Identity (идентичность)
Разрешение «кто сейчас выполняет запрос» из предъявленного JWT. Существующий аналог: `server/auth/resolve-user.ts` (`resolveUserIdFromRequest`, `requireUserIdFromRequest`). Не хранит и не выдаёт токены — только читает уже выданный.

### Authentication (аутентификация)
Сама процедура входа делегирована внешнему провайдеру (Supabase Auth / Google OAuth) — Platform Core не реализует собственный механизм логина. Его ответственность — только принять уже выданный этим провайдером JWT и передать его в Identity. Существующий аналог: `src/integrations/supabase/client.ts`, `src/lib/auth.ts` (сторона инициации), `server/integrations/supabase/auth-middleware.ts` (сторона проверки).

### Authorization (авторизация)
Универсальный механизм Rule Engine (`order` / `applies()` / `evaluate()` / `terminal`) для принятия решений «можно/нельзя» — сам механизм, а не конкретные бизнес-правила. Существующий аналог: `server/domain/permission-policy/` (`PermissionPolicyService`, правила `AdminFullAccessRule`, `AdminFinanceScopeRule`, `AdminMarketingScopeRule`).

### Access (доступ на уровне ролей/scope)
Слой проверки принадлежности актора к роли/scope перед входом в конкретный Workspace — более грубый и более ранний фильтр, чем Authorization. Существующий аналог: `requireAdminFromRequest()`, `requireWarehouseFromRequest()`, `requireCourierFromRequest()`, `requireSellerFromRequest()` (все — `server/auth/resolve-user.ts`).

### Ownership (владение)
Кому принадлежит платформа как актив — Root Owner, Owner, Transfer Root Ownership. Спроектировано (Промпт №034), в текущем коде отсутствует — единственный элемент этого перечня, у которого пока нет существующего аналога в репозитории; появится как отдельный домен Platform Core на этапе реализации.

### Audit (аудит)
Запись значимых событий платформы для последующего разбора. Существующий аналог: `server/domain/audit-log/audit-log.service.ts`, `server/adapters/supabase/audit-log.repository.ts`, `server/domain/audit-log-query.service.ts`.

### Configuration (конфигурация)
Платформенные настройки, не привязанные к одному Workspace. Существующий аналог: `server/domain/settings.service.ts`, `server/config/env.ts` (валидация серверных переменных окружения).

### Event Bus (шина событий)
Синхронная, in-process публикация/подписка на события платформы, единая для всех Workspace. Существующий аналог: `server/ports/marketplace-events.port.ts` и его реализация в `server/di/container.ts`.

### Notification (уведомления)
Механизм доставки уведомлений (Telegram/WhatsApp/будущие каналы) как инфраструктура — не бизнес-контент конкретного уведомления (тот формируется Workspace'ом-инициатором события). Существующий аналог: `server/domain/notification-center.service.ts`, `server/domain/notification.service.ts`, `server/ports/notification.provider.ts`, `server/adapters/notifications/`.

### AI Services (горизонтальный сервис)
Оркестрация AI-операций как переиспользуемый механизм: реестр воркеров, планировщик исполнения, агрегатор результатов — сами воркеры (`ai-catalog.worker.ts`, `ai-media.worker.ts`) реализуют конкретные, предметно-специфичные операции, но сам оркестрационный механизм предметно нейтрален и одинаково пригоден для AI-задач любого Workspace. Существующий аналог: `server/domain/marketplace-ai/` (`AIWorkerRegistry`, `ai-orchestrator.ts`, `ai-execution-planner.ts`, `ai-result-aggregator.ts`). **Важно**: AI Services — горизонтальный сервис Platform Core, а не отдельный Workspace — он не имеет собственного пользовательского кабинета, а обслуживает запросы, поступающие из Workspace'ов (например, AI-инструменты в `/admin/ai` — это UI Administration Workspace, вызывающий горизонтальный сервис Core).

### Общие инфраструктурные сервисы
Composition Root (`server/di/container.ts`), доступ к базе данных как порт-инфраструктура (`server/adapters/supabase/client.server.ts`), сквозные технические механизмы (таймауты внешних вызовов, нормализация ошибок — `src/server.ts`, `src/start.ts`), общие для всех Workspace и не содержащие бизнес-решений.

## 6. Что категорически запрещено размещать внутри Platform Core

- ❌ Товары, каталог, категории — существующий аналог для сравнения: `server/domain` каталог-домены, `catalog` (Workspace-логика).
- ❌ Магазины/продавцы как бизнес-сущность (`seller_profiles`, верификация продавца, выплаты) — Seller Workspace.
- ❌ Заказы, корзина, оформление заказа, статусная машина заказа (`checkout.service.ts`, `order-lifecycle`) — Customer/Administration Workspace.
- ❌ Доставка, зоны, тарифы, расчёт стоимости и ETA (`delivery-pricing`) — отдельный Workspace-модуль.
- ❌ Складской учёт, остатки, резервирование (`warehouse`) — Warehouse Workspace.
- ❌ Любая бизнес-логика маркетплейса в целом — любое правило, которое перестаёт быть верным, если представить платформу без конкретного товара/заказа/доставки, не принадлежит Platform Core.
- ❌ UI любого конкретного Workspace.
- ❌ Специальное знание о том, что «Seller Workspace» или «Courier Workspace» существуют как названные, единственные в своём роде случаи внутри кода Core (см. §12).

## 7. Принципы взаимодействия Core с рабочими пространствами (Workspace)

1. **Workspace — потребитель, не часть Core.** Каждый Workspace обращается к сервисам Core через уже существующие обобщённые интерфейсы (порты, Rule Engine, Event Bus), не получая специального, персонального API.
2. **Core не инициирует бизнес-действий.** Core только отвечает на запросы Workspace и публикует/принимает события — он никогда сам не решает выполнить бизнес-операцию (например, отменить заказ).
3. **Односторонняя предметная слепота.** Core не знает, какие Workspace существуют по именам, кроме как через универсальные роли/scope, которые сам же и хранит. Добавление Courier Workspace для Core выглядит как «появилась ещё одна роль и ещё несколько типов событий», а не как «нужно научить Core понимать курьеров».
4. **Взаимодействие только через порты и события.** Ни один Workspace не обращается к внутренним деталям реализации Core (напрямую к таблицам, к внутренним классам) — только через порты (`server/ports/`) и Marketplace Events.
5. **Access → Authorization → Workspace.** Запрос сначала проходит через Access (роль/scope пропускает в Workspace вообще), затем — если Workspace предметно нуждается в более тонкой проверке — через Authorization (Rule Engine, конкретное разрешено ли действие). Только после этого Workspace выполняет свою бизнес-логику.

## 8. Диаграмма взаимодействия

```
                                Platform Core
   ┌──────────────────────────────────────────────────────────────────────┐
   │  Identity   Authentication   Authorization   Access   Ownership       │
   │  Audit      Configuration    Event Bus        Notification            │
   │  AI Services (горизонтальный)     Общие инфраструктурные сервисы      │
   └───────────────────────────┬────────────────────────────────────────--┘
                                │  порты · события · Rule Engine
        ┌───────────┬──────────┼──────────┬─────────────────┐
        ▼           ▼          ▼          ▼                 ▼
   Customer     Seller      Courier    Warehouse      Administration
   Workspace    Workspace   Workspace  Workspace         Workspace
        │           │          │          │                 │
        └───────────┴──────────┴──────────┴─────────────────┘
              каждый Workspace обращается к Core одинаково —
              через порты/события/Rule Engine, без специального
              персонального API и без знания Core о конкретном
              Workspace как о названном случае
```

## 9. Зависимости Platform Core

- **Внешние (адаптеры)**: Supabase (Postgres, Auth) — как реализация портов Identity/Audit/Configuration; Telegram/WhatsApp — как реализация порта Notification; всё через `server/adapters/`, заменяемо без изменения Core (принцип Replaceable Adapters, `ARCHITECTURE_PRINCIPLES.md` PL-09).
- **Внутренние**: Platform Core зависит только от `shared/contracts/` (DTO) и собственных портов — ни от одного Workspace.
- **От Platform Initialization**: ровно одна, однонаправленная, разовая зависимость — факт «Root Owner существует», получаемый через событие `system.bootstrap.completed` (см. `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §13). Никакой рантайм-зависимости от кода/состояния Bootstrap после этого момента не остаётся.
- **От Workspace — ни одной.** Ни при каких условиях Platform Core не импортирует и не вызывает код конкретного Workspace.

---

## 10. Принцип расширяемости Platform Core

Platform Core расширяется **добавлением**, а не изменением:
- Новая роль — новое значение в существующей схеме ролей, не новая ветка кода.
- Новое событие — новый тип в существующей шине Marketplace Events, не новый механизм доставки.
- Новое правило доступа — новый класс правила Rule Engine с собственным `order`, добавленный в существующий список правил в Composition Root — существующие правила не переписываются.
- Новый канал уведомлений — новый адаптер порта `INotificationProvider`, не новая логика внутри `NotificationCenterService`.
- Новый AI-воркер — новая реализация `IAIWorker`, зарегистрированная в `AIWorkerRegistry` — оркестратор не меняется.

Если для подключения нового Workspace требуется изменить сигнатуру существующего порта, добавить условную ветку `if (workspace === "courier")` внутри сервиса Core, или иным образом коснуться уже существующего файла Core предметно-специфичным образом — это признак нарушения принципа, а не нормальный путь расширения.

## 11. Architecture Invariants Platform Core

- ❌ Platform Core не может импортировать код из директории/модуля конкретного Workspace.
- ❌ Platform Core не может содержать условную логику, зависящую от того, какой именно Workspace сделал запрос («если это Seller Workspace — сделать иначе») — вся вариативность выражается через роли/scope/события, не через знание о конкретном Workspace.
- ❌ Не может существовать второй Event Bus, второй Identity-механизм или второй Rule Engine-движок, параллельный уже существующему в Platform Core.
- ❌ Ни один Workspace не может напрямую обращаться к таблицам/адаптерам Platform Core в обход портов.
- ❌ Platform Core не может зависеть от состояния или кода Platform Initialization после `Bootstrap Completed` (см. `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §17).
- ❌ Добавление нового Workspace не может требовать изменения файла внутри Platform Core предметно-специфичным образом (см. §10).
- ❌ AI Services не может быть превращён в отдельный Workspace с собственным кабинетом — он остаётся горизонтальным сервисом, вызываемым любым Workspace.

---

## 12. Почему новые рабочие пространства не должны требовать изменения Platform Core

Потому что единственное, что Platform Core обязан знать о любом Workspace — это универсальные факты: «есть роль», «произошло событие», «нужно проверить право». Ни Customer, ни Seller, ни Courier, ни Warehouse, ни Administration Workspace не являются для Core особыми случаями — они все проходят через одни и те же Identity → Access → Authorization → Event Bus, различаясь только *данными* (конкретной ролью, конкретным типом события), а не *механизмом*.

Если бы добавление, скажем, Courier Workspace требовало правки внутри `PermissionPolicyService` или `MarketplaceEventBus` специально под курьеров — это означало бы, что Core на самом деле уже содержит скрытое знание о бизнес-вертикалях, что прямо противоречит §1-§4 этого документа. Это и есть прямое практическое продолжение принципа `ARCHITECTURE_BASELINE_V1.md` §3 «Open for Extension, Never Replace», применённое здесь конкретно к границе Core/Workspace.

## 13. Жизненный цикл Platform Core после завершения Platform Initialization

```
Platform Initialization: Bootstrap → COMPLETED
                    │
                    │  событие system.bootstrap.completed
                    ▼
        Platform Core начинает постоянную работу
        (Identity/Authorization/Access/Ownership/Audit/
         Configuration/Event Bus/Notification/AI Services)
                    │
                    ▼
        Работает непрерывно, без пауз и перезапусков
        жизненного цикла, пока существует платформа —
        обслуживает все Workspace одновременно
                    │
                    ▼
        Единственные штатные изменения состояния Core
        после этого момента:
          • Transfer Root Ownership (Ownership-домен Core,
            постоянно доступная операция, не Bootstrap)
          • обычные, повседневные Access/Authorization-решения
          • подключение новых Workspace (аддитивно, см. §10)
```

Platform Core не имеет собственного «завершения» — в отличие от Platform Initialization, у которого жизненный цикл заканчивается на `COMPLETED` (см. `PLATFORM_INITIALIZATION_ARCHITECTURE.md` §3-4), жизненный цикл Platform Core равен жизненному циклу самой платформы: он начинается в момент `Bootstrap Completed` и не заканчивается, пока платформа существует.
