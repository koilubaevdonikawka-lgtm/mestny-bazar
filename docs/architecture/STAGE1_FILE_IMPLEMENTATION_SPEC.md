Ни Этап 2, ни архитектура, ни модель данных, ни роли не пересматриваются — везде, где это уместно, документ прямо ссылается на уже принятые решения вместо того, чтобы формулировать их заново.

## Файл 1 — SQL-миграция (спецификация, без SQL)

**1. Назначение.** Создать хранилище для домена Platform Ownership: статус владения, запись владения, статус и запись Ownership Transfer.

**2. Ответственность.** Исключительно аддитивное изменение схемы. Не содержит логики, не содержит данных для переноса, не трогает ни одну существующую таблицу.

**3. Публичный контракт.** Итоговая форма двух новых таблиц и двух перечислений — это контракт, под который пишутся Порт и Адаптер (Файлы 2-3). Состав — уже зафиксирован в `BOOTSTRAP_DATA_MODEL_ARCHITECTURE.md` §14, пп. 1-5: перечисление статуса владения (`ROOT_OWNER`/`OWNER`), таблица записи владения (ссылка на `auth.users`, статус, уникальность «одна запись на одного пользователя»), перечисление состояний Transfer (`PENDING`/`ACCEPTED`/`COMPLETED`/`CANCELLED`), таблица Ownership Transfer (инициатор и цель — обе ссылки на `auth.users`, состояние, выбор со-владения/полной передачи, временные метки), ограничение уникальности «не более одной `PENDING`-записи на целевую сторону».

**4. Допустимые зависимости.** Только `auth.users` (управляется Supabase Auth) — как объект внешнего ключа.

**5. Запрещённые зависимости.** Никаких ссылок на `user_roles`, `admin_scopes`, `seller_profiles`, `profiles` — Platform Ownership структурно отделён от Access-ролей (`PLATFORM_INITIALIZATION_ARCHITECTURE.md` §7, «ключевое архитектурное решение»). Никаких триггеров, изменяющих поведение существующих таблиц.

**6. Предоставляемые интерфейсы.** Две таблицы и два перечисления — потребляются исключительно Файлом 3 (Адаптер).

**7. Используемые интерфейсы.** Нет — это листовой артефакт схемы.

**8. Исключения.** Не применимо к миграции самой по себе; ограничения (уникальность, внешний ключ), которые она вводит, порождают исключения на уровне Файла 3 (Адаптер) при их нарушении.

**9. Тесты.** Прямых модульных тестов миграция не имеет (в проекте миграции не юнит-тестируются) — проверяется применением и прямым read-only запросом сразу после (`BOOTSTRAP_STAGE1_SPECIFICATION.md` §8, шаг 4).

**10. Архитектурные инварианты.** Только аддитивные операции (`CREATE TYPE`/`CREATE TABLE`); имя новых объектов не пересекается ни с одним из уже существующих 39 миграций (проверяется перед написанием, `BOOTSTRAP_STAGE1_SPECIFICATION.md` §8, шаг 1).

**11. Требования к расширяемости.** Новые статусы/столбцы добавляются последующими миграциями — эта миграция после применения не редактируется повторно.

**12. Требования к обратной совместимости.** Не применимо — ни один существующий код ничего не ожидает от этих объектов схемы, потому что их не существовало.

## Файл 2 — `server/ports/platform-ownership.repository.ts`

**1. Назначение.** Определить контракт доступа к данным владения, от которого зависит доменный сервис (Файл 4), не раскрывая деталей Supabase.

**2. Ответственность.** Только объявление сигнатур методов — ноль реализации, ноль специфики конкретного хранилища.

**3. Публичный контракт.** Интерфейс `IPlatformOwnershipRepository`, по образцу уже существующего `IUserAdminRepository` (`server/ports/user-admin.repository.ts`) — простые, независимые операции: получить запись владения по пользователю, создать запись владения, подсчитать записи по статусу, создать запись Ownership Transfer, получить запись Transfer по идентификатору, получить записи Transfer по статусу для целевой стороны. **Не включает** ни одного метода в форме «атомарная проверка + запись» (claim) — это относится к Этапу 2 (`BOOTSTRAP_STAGE1_SPECIFICATION.md` §4).

**4. Допустимые зависимости.** Только типы (локально определённые в этом файле или в `shared/contracts/`, если решение о создании отдельного контракта будет принято во время реализации — само по себе не архитектурное решение, а техническая деталь именования файла).

**5. Запрещённые зависимости.** Никакого импорта `@supabase/supabase-js`, никакого импорта из `server/adapters/`, никакого импорта другого доменного сервиса.

**6. Какие интерфейсы файл предоставляет.** `IPlatformOwnershipRepository` — единственный экспорт.

**7. Какие интерфейсы файл использует.** Ни одного — порт не зависит ни от чего, кроме собственных типов.

**8. Какие исключения должен обрабатывать.** Ни одного — интерфейс не содержит поведения, значит не может ни бросать, ни перехватывать исключения.

**9. Какие тесты должны существовать.** Ни одного — интерфейс без реализации не тестируется напрямую (аналогично тому, что `IUserAdminRepository` не имеет собственного тестового файла).

**10. Архитектурные инварианты.** Не может содержать методов, специфичных для Supabase (типов строк БД, PostgREST-специфичных параметров); не может содержать методов, относящихся к Access-ролям.

**11. Требования к расширяемости.** Новые методы (для Transfer state machine, Этап 4) добавляются позже как дополнения к этому же интерфейсу либо выносятся в отдельный порт — решение не принимается в Этапе 1.

**12. Требования к обратной совместимости.** Не применимо — новый файл.

## Файл 3 — `server/adapters/supabase/platform-ownership.repository.ts`

**1. Назначение.** Реализовать `IPlatformOwnershipRepository` поверх Supabase Postgres.

**2. Ответственность.** Перевод строк БД в форму, которую ожидает порт; перевод ошибок БД в понятные исключения. Никаких бизнес-решений.

**3. Публичный контракт.** Класс `SupabasePlatformOwnershipRepository implements IPlatformOwnershipRepository`, по образцу `SupabaseUserAdminRepository` (`server/adapters/supabase/user-admin.repository.ts`) — те же простые, независимые CRUD-подобные операции, без транзакционной claim-логики.

**4. Допустимые зависимости.** `supabaseAdmin` (`server/adapters/supabase/client.server.ts`, существующий, не создаётся заново), интерфейс порта (Файл 2), собственные локальные типы/мапперы строк.

**5. Запрещённые зависимости.** Никакого импорта доменного сервиса (Файл 4) — зависимость идёт строго в одну сторону (Dependency Rule, `ARCHITECTURE_PRINCIPLES.md` PL-03); никакого прямого импорта из `src/`.

**6. Какие интерфейсы файл предоставляет.** Реализацию `IPlatformOwnershipRepository`.

**7. Какие интерфейсы файл использует.** `IPlatformOwnershipRepository` (как контракт, который реализует), клиент Supabase.

**8. Какие исключения должен обрабатывать.** Бросает описательное исключение при ошибке БД (по образцу `throw new Error(...)` в `SupabaseUserAdminRepository`), не глотает ошибки молча; нарушение ограничения уникальности (см. Файл 1, п.10) должно давать различимое сообщение, а не общий `"unknown error"`.

**9. Какие тесты должны существовать.** Обязательны только если из адаптера выделяется нетривиальная чистая функция маппинга строки БД → внутреннее представление (паттерн `ARCHITECTURE_PRINCIPLES.md` CD-06, как `mapOrderRowToDto`) — тогда именно эта функция тестируется в изоляции. Если маппинг тривиален (поля совпадают один в один), отдельный тестовый файл для адаптера не обязателен в Этапе 1 — обязателен только тест доменного сервиса (Файл 4) через `fake<Port>()`.

**10. Архитектурные инварианты.** Не реализует атомарной операции (Этап 2); каждый метод — самостоятельная, независимая операция с БД, не составная транзакция.

**11. Требования к расширяемости.** Новые методы добавляются без изменения сигнатур уже существующих.

**12. Требования к обратной совместимости.** Не применимо — новый файл, потребителей ещё нет.

## Файл 4 — `server/domain/platform-ownership.service.ts`

**1. Назначение.** Единственная точка входа, через которую Этап 2 и далее будут работать с владением — тонкая обёртка над репозиторием.

**2. Ответственность.** Делегирование в репозиторий. **Не содержит** бизнес-правил Этапа 2 (проверка «минимум один Root Owner» при claim принадлежит следующему этапу, `BOOTSTRAP_STAGE1_SPECIFICATION.md` §4).

**3. Публичный контракт.** Класс `PlatformOwnershipService`, конструктор принимает **только** `IPlatformOwnershipRepository`.

**4. Допустимые зависимости.** Только `IPlatformOwnershipRepository` (порт) — согласно Dependency Rule (`ARCHITECTURE_PRINCIPLES.md` PL-03), домен зависит от порта, никогда от конкретного адаптера.

**5. Запрещённые зависимости.** **`IMarketplaceEventBus` не внедряется в этом файле** — в Этапе 1 сервису нечего публиковать (событие `system.bootstrap.completed` появляется в Этапе 2), поэтому конструктор следует уже существующему в проекте паттерну сервисов без событий (например, `SupplierService(suppliers)` — `server/di/container.ts:485`, без `marketplaceEvents`), а не паттерну `UserAdminService(userAdmin, marketplaceEvents)`, который применяется, когда сервису действительно есть что публиковать. Никакого прямого обращения к Supabase.

**6. Какие интерфейсы файл предоставляет.** Публичные методы сервиса, зеркалящие методы порта (без добавления бизнес-логики поверх них в этом этапе).

**7. Какие интерфейсы файл использует.** `IPlatformOwnershipRepository`.

**8. Какие исключения должен обрабатывать.** Пробрасывает исключения репозитория как есть, не перехватывает и не подменяет их — в Этапе 1 нет доменных правил, которые могли бы породить собственные, новые типы ошибок.

**9. Какие тесты должны существовать.** Обязательны — тесты сервиса через `fake<Port>()` (тот же паттерн, что `UserAdminService.test.ts` использует `fakeUserAdminRepository`), проверяющие: создание записи владения делегируется репозиторию; получение по пользователю возвращает `null`, если записи нет; подсчёт по статусу возвращает то, что вернул репозиторий, без искажения.

**10. Архитектурные инварианты.** Не содержит claim-логики; не проверяет инвариант минимума Root Owner (эта проверка появляется вместе с атомарной операцией в Этапе 2); не публикует события; не проходит через `PermissionPolicyService` (`PLATFORM_OWNERSHIP_ARCHITECTURE.md` §3 — владение не оценивается тем же Rule Engine, что Access-роли).

**11. Требования к расширяемости.** Методы для Transfer state machine (Этап 4) и claim-логика (Этап 2) добавляются как новые методы этого же класса либо выносятся в отдельный сервис — решение не принимается сейчас; конструктор в Этапе 1 не должен быть спроектирован так, чтобы это добавление требовало ломающего изменения сигнатуры.

**12. Требования к обратной совместимости.** Не применимо — новый файл, нет существующих потребителей.

## Файл 5 — `server/di/container.ts` (только спецификация разрешённых изменений)

**1. Назначение изменения.** Сделать репозиторий и сервис Platform Ownership доступными единственным архитектурно разрешённым способом — через Composition Root (`ARCHITECTURE_PRINCIPLES.md` PL-05).

**2. Ответственность изменения.** Исключительно проводка (импорт → поле интерфейса → конструирование → включение в возвращаемый объект). Ноль бизнес-логики внутри самого изменения.

**3. Публичный контракт.** Два новых поля в интерфейсе `ServiceContainer`: `platformOwnership: IPlatformOwnershipRepository` (рядом с существующим `userAdmin: IUserAdminRepository`, строка 209) и `platformOwnershipService: PlatformOwnershipService` (рядом с `userAdminService: UserAdminService`, строка 210).

**4. Допустимые зависимости.** Импорт `IPlatformOwnershipRepository`, `SupabasePlatformOwnershipRepository`, `PlatformOwnershipService` — три новых импорта, размещаемых рядом с существующими импортами `UserAdminService`/`PermissionPolicyService` (строки 16, 43).

**5. Запрещённые зависимости.** Ни одна уже существующая строка (импорты, поля интерфейса, конструирование, возвращаемый объект — для `userAdmin`, `userAdminService`, `permissionPolicy` и всех остальных) не переписывается и не перемещается.

**6. Какие интерфейсы файл предоставляет.** Расширенный `ServiceContainer` с двумя новыми полями.

**7. Какие интерфейсы файл использует.** `IPlatformOwnershipRepository`, `PlatformOwnershipService` (Файлы 2 и 4).

**8. Какие исключения должен обрабатывать.** Не применимо — конструирование в Composition Root не должно бросать исключений при штатном старте приложения; в этом смысле новый код ничем не отличается от уже существующего в этом файле.

**9. Какие тесты должны существовать.** Существующий `server/di/container.test.ts` обязан продолжать проходить без изменения собственного кода теста; допускается (не обязательно для Этапа 1) добавить отдельную, новую проверку присутствия новых полей в собранном контейнере.

**10. Архитектурные инварианты.** Единственная точка сборки зависимостей во всём проекте (PL-05); никакой оператор `new` для адаптера/сервиса не должен появляться ни в одном файле, кроме этого.

**11. Требования к расширяемости.** Поля для Этапа 2 (claim-related) и Этапа 4 (Transfer-related) добавляются по тому же образцу — рядом, не путём переименования или перемещения того, что добавлено в Этапе 1.

**12. Требования к обратной совместимости.** Обязательна и абсолютна: контейнер обязан продолжать собираться и предоставлять все уже существующие поля в точности так же, как до этого изменения — любое расхождение здесь ломает весь проект, а не только Bootstrap.

## Файл 6 — Тестовые файлы Этапа 1

**1. Назначение.** Подтвердить корректность Файлов 3-4 без обращения к реальной базе данных.

**2. Ответственность.** Ловить регрессии в коде Этапа 1; не тестировать то, чего в Этапе 1 не существует (claim, события, Transfer-переходы).

**3. Публичный контракт.** Не применимо — тесты не потребляются другим кодом.

**4. Допустимые зависимости.** `vitest`, интерфейс порта (Файл 2), локальная фабрика `fakePlatformOwnershipRepository(overrides)` — по уже существующему в проекте паттерну (`fakeUserAdminRepository` и аналогичные), определяемая либо в самом тестовом файле, либо в общем тест-хелпере, если такой уже используется для соседних доменов.

**5. Запрещённые зависимости.** Никакого реального обращения к Supabase, никакого сетевого вызова — согласуется с `ARCHITECTURE_PRINCIPLES.md` CD-09 («тесты никогда не зависят от живого внешнего сервиса»).

**6. Какие интерфейсы файл предоставляет.** Ни одного.

**7. Какие интерфейсы файл использует.** `IPlatformOwnershipRepository`, `PlatformOwnershipService`.

**8. Какие исключения должен обрабатывать.** Тесты явно проверяют, что сервис (Файл 4) пробрасывает исключения репозитория, а не поглощает их молча.

**9. Какие тесты должны существовать.** Как минимум: создание записи владения делегируется репозиторию с ожидаемыми аргументами; получение записи по пользователю, которого нет, возвращает `null`, не бросает исключение; подсчёт записей по статусу возвращает значение репозитория без искажения; (если применимо, см. Файл 3 п.9) — тест чистой функции маппинга строки БД.

**10. Архитектурные инварианты.** Не тестируют claim-логику, атомарность или события — их не существует в Этапе 1; тесты, написанные так, будто эти механизмы уже есть, являются признаком выхода за границы этапа (`BOOTSTRAP_STAGE1_SPECIFICATION.md` §4) и должны быть отклонены при код-ревью.

**11. Требования к расширяемости.** Новые тестовые файлы для claim-логики (Этап 2) и Transfer state machine (Этап 4) создаются отдельно, не дописываются в эти же файлы задним числом.

**12. Требования к обратной совместимости.** Не применимо — новые файлы.
