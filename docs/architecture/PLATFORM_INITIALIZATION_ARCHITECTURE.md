## 1. Назначение Platform Initialization

Platform Initialization — модуль, единственная задача которого: безопасно перевести платформу из состояния **«платформы не существует как управляемая единица»** в состояние **«у платформы есть подтверждённый Root Owner, и она готова работать»**.

Он решает ровно ту проблему, которая была зафиксирована как факт в ходе аудита (Промпт №034, §10): сегодня в репозитории физически нет ни одного легитимного, проходящего через Domain/Repository/API пути создания первого владельца платформы. Единственный существующий путь назначения роли (`assignRoleFn → requireAdminFromRequest() → UserAdminService.assignRole()`) требует уже существующего `admin` — то есть не работает для самого первого случая. Platform Initialization — это архитектурный ответ на этот конкретный, уже обнаруженный пробел, а не гипотетическая предосторожность.

Platform Initialization не администрирует платформу и не участвует в её повседневной работе. Он существует один раз, выполняет одну операцию, и после этого перестаёт быть активной частью системы.

---

## 2. Место Platform Initialization в общей Architecture v2.0

```
Platform  (верхний уровень архитектуры)
│
├── Platform Initialization      ← независимый модуль, тот же уровень, что и Platform Core
│     (существует только во время рождения платформы)
│
└── Platform Core                ← независимый модуль, постоянно работающее ядро
      │
      └── Workspace (строятся НА Platform Core, не являются его частью)
            ├── Customer Workspace
            ├── Seller Workspace
            ├── Courier Workspace
            ├── Warehouse Workspace
            └── Administration Workspace
```

Platform Initialization **не является частью** Platform Core и не является Workspace. Это отдельный модуль на том же архитектурном уровне, что и Platform Core, — они не вложены друг в друга и не зависят друг от друга в рантайме (см. §13).

**Честная оговорка относительно текущего кода**: сегодня в репозитории нет структурного разделения на «Platform Core» и «Workspace» — весь `server/domain/` (checkout, catalog, order-lifecycle, delivery-pricing, user-admin, permission-policy, marketplace-events и т.д.) существует как единый набор доменных сервисов без этого явного деления. Настоящий документ вводит это деление как часть Architecture v2.0 и ниже (§6, §11) явно указывает, какие из уже существующих модулей relocate в понятие Platform Core, а какие остаются Workspace-модулями. Это классификация поверх существующего кода, а не описание уже осуществлённого рефакторинга.

## 3. Полный жизненный цикл Platform Initialization

Platform Initialization выполняет единственный процесс — **Bootstrap**. У Bootstrap есть ровно три состояния, и переход между ними необратим:

1. **ELIGIBLE** — платформа развёрнута, Root Owner ещё не существует (`COUNT(*) FROM platform_ownership WHERE role = 'ROOT_OWNER' = 0`). Claim-операция доступна.
2. **CLAIMING** — кто-то выполняет операцию становления первым Root Owner. Переходное, короткое состояние одной транзакции.
3. **COMPLETED** — первый Root Owner подтверждён. Состояние постоянно и не имеет обратного перехода ни в `ELIGIBLE`, ни в `CLAIMING`.

Как только достигнуто `COMPLETED`, Platform Initialization как активный модуль прекращает свою работу — не удаляется физически из кодовой базы (код продолжает существовать для аудита/истории и для теоретического повторного разворачивания платформы «с нуля» на новом окружении), но не имеет ни одной операции, доступной к выполнению против уже инициализированной платформы.

---

## 4. Диаграмма жизненного цикла

```
                    Платформа развёрнута
                    Root Owner = 0
                            │
                            ▼
                  ┌───────────────────┐
                  │     ELIGIBLE      │  ← claim-операция доступна
                  └─────────┬─────────┘
                            │  claim() вызван
                            ▼
                  ┌───────────────────┐
                  │     CLAIMING      │  ← одна транзакция, переходное состояние
                  └─────────┬─────────┘
                            │  claim успешен
                            ▼
                  ┌───────────────────┐
                  │     COMPLETED     │  ← постоянно, необратимо
                  └─────────┬─────────┘
                            │
                            │  событие: system.bootstrap.completed
                            ▼
              Platform Initialization деактивирован навсегда.
              Начинается жизненный цикл Platform Core.
```

Не существует стрелки, ведущей из `COMPLETED` обратно в `ELIGIBLE` или `CLAIMING`. Это единственная диаграмма состояний во всей платформе, где явно нет пути назад — намеренное архитектурное решение (см. §16).

## 5. Диаграмма расположения Platform Initialization относительно Platform Core

```
        ┌─────────────────────────────┐        ┌──────────────────────────────────┐
        │   Platform Initialization   │        │           Platform Core           │
        │                              │        │                                    │
        │   Жизненный цикл: Bootstrap  │        │   Жизненный цикл: постоянная       │
        │   Активен: один раз          │        │   работа платформы                  │
        │                              │        │                                    │
        │   Не знает о Business        │        │   Не знает о Platform              │
        │   Platforms                  │        │   Initialization                    │
        └───────────────┬──────────────┘        └──────────────────┬─────────────────┘
                        │                                          │
                        │   создаёт факт "Root Owner существует"   │
                        └─────────────────────►┌────────────────────┘
                                                │
                                        (однонаправленно,
                                         только в момент COMPLETED,
                                         не рантайм-зависимость)
```

Стрелка идёт только в одну сторону и только один раз — Platform Initialization передаёт Platform Core факт («Root Owner создан»), но Platform Core никогда не обращается обратно к Platform Initialization и не проверяет его состояние во время своей обычной работы (см. §17).

## 6. Описание Platform Core

Platform Core — это постоянно работающее инфраструктурное ядро платформы: общие для всех Workspace механизмы идентичности, ролей, владения, событий и правил, не содержащие ни одного бизнес-правила конкретной вертикали (не знает, что такое заказ, товар, доставка или склад).

**Сопоставление с уже существующим кодом** (перенос понятий, не новый код):
- `server/domain/permission-policy/` — механизм Rule Engine для прав доступа (генерик-движок, а не сами бизнес-правила).
- `server/domain/user-admin.service.ts` + новый `platform-ownership` домен (Промпт №034) — идентичность, роли, владение.
- `server/ports/marketplace-events.port.ts` — шина событий.
- `server/di/container.ts` — Composition Root.
- `server/auth/resolve-user.ts` — разрешение сессии/идентичности из JWT.

**Явно НЕ входит в Platform Core** (остаётся Workspace-модулями): `server/domain/checkout.service.ts`, `catalog`, `order-lifecycle`, `delivery-pricing`, `warehouse`, `courier-order`, `seller-product` и все остальные предметно-специфичные домены — они используют сервисы Platform Core (Rule Engine как механизм, Event Bus, идентичность), но сами являются его потребителями, а не частью.

---

## 7. Границы ответственности Platform Initialization

Отвечает **только** за: обнаружение состояния «Root Owner отсутствует», выполнение единственной claim-операции, запись факта COMPLETED, публикацию единственного события `system.bootstrap.completed`.

Не отвечает за: повседневное управление ролями, повседневную авторизацию запросов, любую бизнес-логику, любой UI кроме экрана самого Bootstrap.

---

## 8. Границы ответственности Platform Core

Отвечает за: идентичность и сессию (кто сейчас аутентифицирован), хранение и проверку ролей/владения (кто чем управляет), механизм Rule Engine как таковой (`order/applies/evaluate/terminal`), шину событий, Composition Root.

Не отвечает за: конкретные бизнес-правила любой вертикали (правила оформления заказа, правила ценообразования доставки, правила публикации товара — это Workspace-логика, использующая механизм Rule Engine Platform Core, но не являющаяся его частью).

---

## 9. Что относится к Platform Initialization

- Состояния Bootstrap (ELIGIBLE / CLAIMING / COMPLETED) и переходы между ними.
- Единственная claim-операция становления первым Root Owner.
- Проверка «Root Owner ещё не существует» как условие доступности claim-операции.
- Событие `system.bootstrap.completed`.
- Экран/UI, показываемый ровно один раз — при первом развёртывании платформы.

## 10. Что категорически запрещено размещать внутри Platform Initialization

- ❌ Любая бизнес-логика конкретного Workspace (заказы, доставка, каталог).
- ❌ Повседневное управление ролями персонала (Administrator, Support, Courier и т.д.) — это Platform Core / Platform Administration, не Bootstrap.
- ❌ Transfer Root Ownership — это отдельная, постоянно доступная операция Platform Core (Platform Ownership домена), а не часть одноразового Bootstrap (см. §16 — разница между «создать первого владельца» и «передать владение существующим»).
- ❌ Постоянно работающий сервис или API-эндпоинт, доступный после COMPLETED.
- ❌ Любая зависимость Platform Core от кода Platform Initialization (обратная стрелка запрещена — см. §17).

## 11. Что относится к Platform Core

- Механизм Rule Engine (генерик: `order`, `applies()`, `evaluate()`, `terminal`) — как переиспользуемая инфраструктура, а не конкретные правила.
- Хранение и проверка ролей/scope (Platform Administration) и владения (Platform Ownership, включая Transfer Root Ownership — постоянно доступная операция, в отличие от одноразового Bootstrap).
- Разрешение идентичности/сессии (`requireUserIdFromRequest` и аналоги).
- Шина Marketplace Events.
- Composition Root (`server/di/container.ts` и его развитие).
- Инфраструктурные сервисы, общие для всех Workspace: доступ к БД через порты, отправка уведомлений как механизм (не бизнес-контент уведомлений), аудит-лог как механизм (не бизнес-события конкретной вертикали).

## 12. Что категорически запрещено размещать внутри Platform Core

- ❌ Любое конкретное бизнес-правило вертикали (расчёт стоимости доставки, матрица переходов статуса заказа, правила публикации товара) — это Workspace-логика.
- ❌ Прямая зависимость от Platform Initialization/Bootstrap — Platform Core не должен импортировать, вызывать или проверять состояние Bootstrap ни в одной точке своей постоянной работы.
- ❌ Знание о конкретных кабинетах (Seller Workspace, Courier Workspace и т.д.) как о специальных случаях — новый кабинет должен подключаться через уже существующие обобщённые механизмы (роли, события, Rule Engine), не требуя новой ветки логики внутри Platform Core.
- ❌ UI конкретного Workspace.

---

## 13. Принципы взаимодействия Initialization → Core

1. **Однонаправленность.** Platform Initialization может влиять на Platform Core (создать факт «Root Owner существует»), но не наоборот.
2. **Разовость.** Взаимодействие происходит один раз, в момент перехода COMPLETED. После этого канал взаимодействия закрыт навсегда.
3. **Через факт, не через рантайм-зависимость.** Platform Core не «спрашивает» Platform Initialization о его состоянии во время работы — Platform Core просто видит результат (запись владения) как обычные данные, точно так же, как видел бы её, будь она создана любым другим легитимным способом (например, Transfer Root Ownership).
4. **Через событие, не через прямой вызов.** Единственный канал сообщения — `system.bootstrap.completed`, публикуемый в ту же шину Marketplace Events, что используют все остальные модули платформы — не отдельный, специальный механизм связи.

---

## 14. Состояния платформы

| Состояние | Значение | Кто в нём работает |
|---|---|---|
| **Not Initialized** | Платформа развёрнута, Root Owner отсутствует | Только Platform Initialization (Bootstrap: ELIGIBLE) |
| **Initializing** | Claim-операция выполняется | Platform Initialization (Bootstrap: CLAIMING) |
| **Operational** | Root Owner подтверждён, Bootstrap завершён навсегда | Только Platform Core и все Workspace |

Платформа не может находиться одновременно в `Not Initialized`/`Initializing` и в `Operational` — это взаимоисключающие, монотонно сменяющие друг друга состояния (стрелка только вперёд, см. §4).

---

## 15. Что означает Bootstrap Completed

`Bootstrap Completed` — постоянный, единожды записываемый факт системы: «у платформы есть как минимум один Root Owner, и он появился через легитимный, проходящий через Domain/Repository/API механизм, а не через ручное вмешательство в базу данных». Это не UI-статус и не настройка — это инвариант, проверяемый на уровне Domain-слоя при каждой попытке снова обратиться к claim-операции (см. §10).

С момента COMPLETED дальнейшее изменение владения платформой происходит исключительно через Transfer Root Ownership (постоянная операция Platform Core, домен Platform Ownership) — не через повторное обращение к Bootstrap.

---

## 16. Почему Bootstrap является одноразовым жизненным циклом

Потому что его единственная причина существования — закрыть разрыв между «платформы ещё нет как управляемой единицы» и «у платформы есть первый ответственный владелец». Как только этот разрыв закрыт хотя бы один раз, повторное открытие этого же механизма перестаёт решать какую-либо легитимную задачу и начинает представлять собой чистый риск: постоянно доступная (или переоткрываемая) операция «стать Root Owner в обход существующих владельцев» — это готовый бэкдор для захвата платформы в обход Transfer Root Ownership, у которого (в отличие от Bootstrap) есть обязательное согласие обеих сторон и полный аудиторский след (см. Промпт №034, §9-10). Одноразовость Bootstrap — не эксплуатационное ограничение, а сознательная граница безопасности.

---

## 17. Почему Platform Core не должен зависеть от Bootstrap

Потому что Platform Core обязан работать **постоянно**, включая всё время жизни платформы уже после того, как Bootstrap перестал существовать как активный процесс. Если бы Platform Core на каждый обычный запрос («какая у пользователя роль», «кто владелец») обращался к логике или состоянию Bootstrap, это означало бы:

1. Postoянную рантайм-зависимость вечно работающего ядра от кода, который по определению предназначен исполниться ровно один раз — то есть Platform Core никогда не смог бы считаться независимым модулем (нарушение §2).
2. Риск того, что ошибка/откат/пересборка модуля Bootstrap (который не тестируется и не эксплуатируется в проде после первого запуска) способна сломать постоянно работающую часть платформы.
3. Смешение двух разных по своей природе жизненных циклов (разовый и постоянный) в одной цепочке рантайм-вызовов — прямое нарушение принципа «Open for Extension, Never Replace» уже зафиксированного в `ARCHITECTURE_BASELINE_V1.md` §3.

Именно поэтому взаимодействие построено как одностороннее событие (§13), а не как вызов «спроси у Bootstrap».

## 18. Какие будущие Workspace смогут использовать Platform Core

```
                         Platform Core
        (идентичность, роли, владение, Rule Engine, Event Bus, DI)
                                │
        ┌───────────┬──────────┼──────────┬────────────────┐
        ▼           ▼          ▼          ▼                ▼
  Customer      Seller     Courier    Warehouse      Administration
  Workspace     Workspace  Workspace  Workspace          Workspace
```

Каждый из этих Workspace — независимый потребитель одних и тех же, уже существующих инфраструктурных сервисов Platform Core: идентичности (кто вошёл), ролей (что этому пользователю разрешено), Rule Engine (как механизм для СВОИХ собственных бизнес-правил), Event Bus (публикация и подписка на события), Composition Root (регистрация своих сервисов).

**Почему появление нового Workspace не должно менять Platform Core**: Platform Core предоставляет только обобщённые, предметно-нейтральные примитивы (роль, событие, правило, идентичность) — он не содержит понятия «курьер», «склад» или «продавец» как специальных случаев внутри себя. Courier Workspace подключается так же, как уже подключены Customer Workspace и Seller Workspace: новой ролью в существующей схеме ролей, новыми событиями в существующей шине, новыми правилами в существующем механизме Rule Engine, новым доменным сервисом, зарегистрированным в существующем Composition Root. Это прямое продолжение уже зафиксированного в `ARCHITECTURE_BASELINE_V1.md` принципа **PWA First** («каждая новая точка входа для новой роли — отдельное PWA поверх общего backend») и **Open for Extension, Never Replace** — Platform Initialization Architecture лишь формализует эту же логику применительно к владению и ролям.

Если добавление новой Workspace потребовало бы изменения кода внутри Platform Core — это признак того, что в Platform Core просочилась бизнес-специфичная логика, и такое изменение само по себе является нарушением архитектуры (см. Architecture Invariants, §20).

## 19. Полный список архитектурных принципов новой модели

1. **Platform — верхний уровень.** Platform Initialization и Platform Core — два независимых модуля одного уровня внутри Platform, не вложенные друг в друга.
2. **Ownership ≠ Administration.** Владение платформой (Root Owner/Owner) и операционное администрирование (Administrator и ниже) — независимые домены с разными жизненными циклами прав (см. Промпт №034, §6).
3. **Bootstrap — процесс, не сервис.** Platform Initialization реализует ровно один процесс — Bootstrap — а не постоянно работающий сервис.
4. **Необратимость COMPLETED.** Переход Bootstrap в COMPLETED необратим; нет технического пути вернуть платформу в ELIGIBLE.
5. **Однонаправленная связь.** Platform Initialization может повлиять на Platform Core один раз; обратной рантайм-зависимости не существует.
6. **Platform Core предметно нейтрален.** Ядро не содержит бизнес-правил ни одной конкретной вертикали.
7. **Workspace — потребители, не части Core.** Каждый новый Workspace подключается через уже существующие обобщённые механизмы, не требуя правок внутри Core.
8. **Минимум один Root Owner всегда.** Инвариант, проверяемый на уровне Domain при любой операции, способной уменьшить число Root Owner (см. Промпт №034, §10).
9. **Root Owner отзывается только добровольно.** Никто, включая других Root Owner, не может принудительно лишить конкретного Root Owner его статуса — только сам держатель через Transfer Root Ownership.
10. **Транспарентность через события.** Каждое значимое изменение состояния (Bootstrap Completed, Transfer инициирован/принят/завершён) публикуется в общую шину Marketplace Events — не создаётся отдельный, специальный канал коммуникации.

---

## 20. Architecture Invariants

Правила, которые запрещено нарушать при любой будущей реализации:

- ❌ Bootstrap не может быть вызван повторно после COMPLETED — ни через UI, ни через прямой вызов API/скрипта.
- ❌ Platform Core не может импортировать, вызывать или проверять состояние модуля Platform Initialization в рамках своей постоянной работы.
- ❌ Platform Initialization не может содержать бизнес-логику Workspace.
- ❌ Platform Core не может содержать бизнес-логику конкретного Workspace.
- ❌ Ни одна операция не может привести число Root Owner к нулю.
- ❌ Новый Workspace не может требовать изменения кода Platform Core для своего подключения — только регистрацию через уже существующие обобщённые точки расширения (роли, события, Rule Engine, Composition Root).
- ❌ Не может существовать второй, параллельный механизм становления первым владельцем платформы в обход Platform Initialization (никаких ручных SQL/скриптов как штатной практики — ровно та проблема, что была зафиксирована в Промпте №023 и закрывается этим модулем).
