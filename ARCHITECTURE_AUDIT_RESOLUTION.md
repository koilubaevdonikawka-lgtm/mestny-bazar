## 2. Root causes

### A. Stale generated Supabase types (errors #1–4, 16 of 23 original error sites)

`src/integrations/supabase/types.ts` — a file whose own header states *"This file is automatically generated.
Do not edit it directly"* — had not been regenerated since **before five migrations** were added:

| Migration | Schema change | Reflected in `types.ts`? |
|---|---|---|
| `20260716120000_warehouse_role.sql` | `app_role` enum += `'warehouse'` | No |
| `20260716130000_courier_role.sql` | `app_role` enum += `'courier'` | No |
| `20260716140000_seller_role.sql` | `app_role` enum += `'seller'`; adds `products.seller_id` | No |
| `20260716150000_product_publication_status.sql` | new enum `product_publication_status`; adds `products.publication_status` | No |
| `20260716100000_guest_checkout_nullable_user.sql` | `ALTER TABLE orders ALTER COLUMN user_id DROP NOT NULL` | No |

The last one was a new finding made during this fix — not previously isolated in `ARCHITECTURE_AUDIT.md`. It
explains error #3 (`order.repository.ts`) via the exact same drift mechanism as `publication_status`: the code
already assumed `orders.user_id` could be `null` (guest checkout), but the generated type still required
`string`.

Regeneration via the Supabase CLI (`npx supabase gen types typescript`) remained blocked in this environment —
first by a missing `SUPABASE_ACCESS_TOKEN` (`LegacyPlatformAuthRequiredError`), then, once a token was supplied,
by an authorization failure (`LegacyGenTypesUnexpectedStatusError` — "Your account does not have the necessary
privileges to access this endpoint"), confirmed by `npx supabase projects list` returning `{"projects":[],...}`
for that account. In place of CLI regeneration, the type file was corrected by hand directly from the migration
SQL (the authoritative source of the real schema), which is a fully determinate transcription for the columns/
enums involved — not a guess.

### B. Genuine type-narrowing/interface bugs, unrelated to schema drift (errors #5, #6, #8, #9)

- **#9 (`server/ports/order.repository.ts`) + #5 (`checkout.service.ts`), same root cause:**
  `CreateOrderRequest.zoneId` and `.addressId` are declared `string | undefined` (optional) in the shared DTO
  contract (`shared/contracts/order.ts`), but the internal `CreateOrderData` port type needs `string | null` for
  both — "explicitly no zone/address" is a real, distinct domain value (checkout.service.ts assigns `?? null`
  for exactly this case), not merely "field omitted." `CreateOrderData` redeclared `zoneId` but not `addressId`,
  so the interface-extension check failed for `zoneId` (#9) and the assignment check failed for `addressId` (#5).
- **#6 (`marketplace-events.service.ts`):** storing a `MarketplaceEventHandler<T>` (handler scoped to one event
  type) into a `Set<MarketplaceEventHandler>` (the unparameterized, all-events form) via a direct `as` cast is
  rejected by TypeScript because function-parameter contravariance means the two shapes don't "sufficiently
  overlap." The cast is safe in practice — `publish()` only ever invokes a handler with the event type it was
  registered under — but TypeScript needs that stated explicitly via `as unknown as X`, the standard idiom for
  this "heterogeneous callback map" pattern.
- **#8 (`seller-publish.rule.ts`):** `new Set([ProductPublicationStatus.DRAFT, ProductPublicationStatus.HIDDEN])`
  was inferred as `Set<ProductPublicationStatus.DRAFT | ProductPublicationStatus.HIDDEN>` from its literal
  members, rather than the intended `Set<ProductPublicationStatus>`, so passing the full enum type to `.has()`
  was rejected.
- **#7 (`notification-center.service.ts`)** was not an independent bug — it cleared once the other errors in the
  same compilation graph were fixed, consistent with it having been a cascade/error-recovery artifact of an
  earlier failure rather than a real defect.

(`server/functions`, `server/di`, `server/domain`, `server/adapters`, `server/ports`, `server/config`, `src`,

```
$ grep -rln "application/seller-product" server/functions server/di server/domain server/adapters server/ports server/config src shared
(no output)

$ grep -rln "platform/governance" server/functions server/di server/domain server/adapters server/ports server/config src shared
(no output)
```

Zero matches in both cases. Note the naming trap this confirms: `server/application/seller-product/` is a
**different, orphaned implementation** of seller-product logic, sharing a name with the real, wired
`server/domain/seller-product.service.ts` (constructed at `server/di/container.ts:181`, error-free). The two are
easy to conflate by name alone; only the reachability check distinguishes them. `server/platform/governance/` was
already established as unreachable in `ARCHITECTURE_AUDIT.md` §F1/F2 (reachable only via the dead
`server/bootstrap/composition-root.ts` bridge).

## 7. Recommendation for handling the orphan architecture

Unchanged from the recommendation given earlier in this audit, restated here for the record since it directly
governs how the remaining 11 errors should be treated:

- **Do not extend it further.** Every file added to `server/application`, `server/infrastructure`,
  `server/platform`, `server/api/modules`, or `server/bootstrap` following the existing pattern adds proven-dead
  weight — confirmed unreachable by static import-graph tracing and absent from the actual compiled
  `.output/server` bundle.
- **Do not attempt a blanket migration into the real application either.** There is no single target domain
  model to migrate into — `server/domain/{order,catalog,product}/` (rich DDD aggregates) and the flat
  `server/domain/*.service.ts` files (what actually ships) already model the same concepts two different, mutually
  inconsistent ways, entirely independent of the orphan `application`/`infrastructure`/`platform` tree. Migrating
  the orphan tree "in" would first require resolving which of two already-existing internal models is canonical.
  This applies directly to the two files above: neither is a deferred feature waiting for wiring, and treating
  them as bugs to fix would perpetuate the anti-pattern this audit exists to flag.
- **The remaining 11 errors do not need to be fixed as part of this task.** They are inert: proven unreachable,
  absent from the shipped build, and fixing malformed syntax in code nothing runs would not change any observable
  behavior of the application. They should be revisited only alongside a deliberate decision on the orphan tree's
  fate (delete vs. quarantine vs. selectively re-implement — see `ARCHITECTURE_AUDIT.md` §3 Conclusions), not
  fixed piecemeal.
